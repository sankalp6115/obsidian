# 25. Real-Time Backends

## 1. Introduction: From Request-Response to Event-Driven Push

Traditional backend engineering is built around the request-response paradigm: the client asks, the server answers, and the connection closes. 

However, modern digital experiences—collaborative canvases (Figma, Miro), instant messaging (Slack, WhatsApp), live financial tickers, real-time sports updates, multiplayer gaming, and streaming LLM chat interfaces—require **real-time backends** where the server **pushes updates to the client the millisecond an event occurs**.

## 2. The Architectural Spectrum: Short Polling to WebSockets

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                               REAL-TIME COMMUNICATION PARADIGMS                                 │
├────────────────────┬─────────────────┬───────────────────────────────┬──────────────────────────┤
│ Technology         │ Direction       │ Connection Model              │ Protocol & Overhead      │
├────────────────────┼─────────────────┼───────────────────────────────┼──────────────────────────┤
│ **Short Polling**  │ Pull (Client)   │ Periodic new HTTP connections │ HTTP/1.1; Massive waste  │
│ **Long Polling**   │ Push emulation  │ Hanging HTTP request + retry  │ HTTP/1.1; Moderate waste │
│ **Server-Sent (SSE)│ Server ──▶ Client│ Single persistent HTTP stream │ HTTP/1.1 or HTTP/2; Low  │
│ **WebSockets**     │ Bidirectional   │ Single persistent TCP socket  │ WebSocket protocol; Min. │
└────────────────────┴─────────────────┴───────────────────────────────┴──────────────────────────┘
```

### 2.1 Short Polling
- **How It Works:** The client fires an HTTP request at a regular interval (e.g., every 3 to 5 seconds: `GET /api/notifications`).
- **The Catastrophic Inefficiencies:**
  - **Resource Wastage:** 95%–99% of polling requests return empty data (`{ "messages": [] }`), yet each request forces a complete TCP handshake, TLS negotiation, HTTP header parsing, and database query.
  - **Latency Jitter:** An event occurring immediately after a poll will not be visible to the user until the next poll cycle 5 seconds later.

### 2.2 Long Polling (Comet)
- **How It Works:** The client sends an HTTP request. Instead of responding immediately, the server **holds the request open** (sleeps/hangs) until new data becomes available or an internal timeout (e.g., 30s) expires.
- Once data arrives, the server returns the HTTP response, closes the connection, and the client immediately issues a new long-polling request.
- **Limitation:** Incurs constant HTTP reconnection overhead and header re-transmission.

### 2.3 Server-Sent Events (SSE)
- **How It Works:** A standardized, unidirectional streaming protocol from Server to Client over standard HTTP.
- The client initiates a connection using the browser's native `EventSource` API:
  - Header: `Accept: text/event-stream`
  - Server Response: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`
- The HTTP connection remains open indefinitely. The server streams text events formatted according to the SSE standard:

```
event: task_updated
id: 1042
retry: 5000
data: {"taskId": 98, "status": "COMPLETED", "assignedTo": "Alice"}

```

- **Inherent Features:**
  - **Automatic Reconnection:** Browsers natively reconnect if the connection drops.
  - **Event IDs & Resumption:** Sends `Last-Event-ID` header upon reconnecting to resume missed messages.
  - **Ideal Use Cases:** LLM token streaming (ChatGPT), live dashboards, stock tickers, order status trackers.

## 3. WebSockets Deep-Dive: The Protocol Upgrade

WebSockets provide **full-duplex, bidirectional, low-latency communication over a single persistent TCP connection**.

```
                       The WebSocket Handshake Flow
                       ════════════════════════════

  Client Browser                                             Backend Server
        │                                                           │
        │ 1. Standard HTTP GET with Upgrade Request                 │
        │    GET /ws HTTP/1.1                                       │
        │    Host: api.example.com                                  │
        │    Upgrade: websocket                                     │
        │    Connection: Upgrade                                    │
        │    Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==           │
        │    Sec-WebSocket-Version: 13                              │
        ├──────────────────────────────────────────────────────────▶│
        │                                                           │
        │                                   2. Validates Upgrade    │
        │                                      Computes SHA-1 hash  │
        │                                      with Magic GUID      │
        │ 3. HTTP 101 Switching Protocols                          │
        │    HTTP/1.1 101 Switching Protocols                       │
        │    Upgrade: websocket                                     │
        │    Connection: Upgrade                                    │
        │    Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=     │
        │◀──────────────────────────────────────────────────────────┤
        │                                                           │
        │ ═════════════════════════════════════════════════════════ │
        │    TCP SOCKET UPGRADED OUT OF HTTP INTO WEBSOCKET MODE   │
        │ ═════════════════════════════════════════════════════════ │
        │                                                           │
        │ 4. Lightweight Bidirectional Framing (2 - 10 bytes header)│
        │◀─────────────────────────────────────────────────────────▶│
```

### 3.1 The Handshake Cryptography
- The client generates a random 16-byte base64 string (`Sec-WebSocket-Key`).
- The server appends a globally standardized constant GUID (`258EAFA5-E914-47DA-95CA-C5AB0DC85B11`), hashes the concatenated string using SHA-1, base64-encodes the result, and returns it in `Sec-WebSocket-Accept`.
- This handshake guarantees that both the client and server explicitly agreed to upgrade the protocol and prevents caching proxies from mistakenly serving stale HTTP responses.

### 3.2 WebSocket Framing Overhead vs. HTTP
- Standard HTTP requests carry **500 to 2,000 bytes of headers** (Cookies, User-Agent, Referer, Accept) for every single interaction.
- Once upgraded, WebSocket data frames carry an overhead of **only 2 to 10 bytes** of framing metadata. This micro-overhead is why WebSockets achieve sub-millisecond round trips.

## 4. Scaling WebSockets Horizontally: The Multi-Server Pub/Sub Dilemma

Scaling stateless REST APIs is trivial: add 10 server nodes behind a round-robin load balancer. 

**WebSockets are stateful TCP connections.** This creates the fundamental distributed systems problem of real-time backends:

```
                            The Distributed WebSocket Problem
                            ═════════════════════════════════

  [ User A (Alice) ]                                             [ User B (Bob) ]
          │                                                             │
          │ Persistent TCP Socket                                       │ Persistent TCP Socket
          ▼                                                             ▼
┌──────────────────┐                                          ┌──────────────────┐
│ WebSocket Node 1 │                                          │ WebSocket Node 2 │
└──────────────────┘                                          └──────────────────┘
         ▲                                                             ▲
         │ Alice sends chat message intended for Bob                   │ Bob is waiting here!
         │ Node 1 has NO socket to Bob!                                │ Node 2 has the socket!
         └──────────────────────────────┬──────────────────────────────┘
                                        │
                         How does Node 1 reach Node 2?
```

### The Solution: Distributed Redis Pub/Sub Backbone

```
                                  Client Sockets
                                 ┌──────────────┐
                    ┌────────────┤ Load Balancer├────────────┐
                    │            └──────────────┘            │
                    ▼                                        ▼
          ┌──────────────────┐                     ┌──────────────────┐
          │ WebSocket Node 1 │                     │ WebSocket Node 2 │
          │ (Houses Alice)   │                     │ (Houses Bob)     │
          └────────┬─────────┘                     └────────▲─────────┘
                   │                                        │
                   │ PUBLISH channel:chat_room_42           │ Receives broadcast
                   ▼                                        │
         ┌──────────────────────────────────────────────────┴─────┐
         │             Central Distributed Message Bus            │
         │                  (Redis Pub/Sub / NATS)                │
         └────────────────────────────────────────────────────────┘
```

1. When Alice sends a message intended for `chat_room_42`, Node 1 publishes the event to Redis:
   `PUBLISH channel:chat_room_42 '{"sender":"Alice","text":"Hello Bob"}'`
2. Every WebSocket server instance in the cluster subscribes to Redis channels for rooms currently occupied by its local clients.
3. Node 2 receives the Redis message, checks its local memory map for connected sockets belonging to `chat_room_42`, finds Bob's socket, and writes the frame down Bob's TCP connection.

## 5. Connection Hygiene: Heartbeats, Pings/Pongs & Ghost Connections

### 5.1 The Ghost Connection Problem (Half-Open Sockets)
If a user on a laptop closes their laptop screen or drives into a tunnel, the client does not send a graceful TCP `FIN` packet.
- The server still believes the TCP socket is alive and healthy.
- Intermediate network devices (NAT routers, cloud firewalls, AWS ALBs) silently terminate idle TCP sessions after 60 to 120 seconds of silence.
- The server continues allocating memory, file descriptors, and goroutines/buffers for non-existent "ghost" connections.

### 5.2 Heartbeat Ping/Pong Mechanism
- The WebSocket specification defines native protocol control frames: **Ping (opcode `0x9`)** and **Pong (opcode `0xA`)**.
- The server runs an interval timer (e.g., every 30 seconds) sending a Ping frame to the client.
- The client must respond with a Pong frame within a strict timeout (e.g., 10 seconds).
- If the Pong response is missed, the server forcibly terminates the dead socket, frees operating system file descriptors, and clears local memory structures.

## 6. Server Resource Tuning for High Concurrency (100k+ Connections)

A production server managing 100,000 concurrent persistent WebSocket connections requires low-level OS and runtime configuration:

1. **File Descriptors (`ulimit -n`):** Every TCP connection consumes one OS file descriptor. The default Linux limit (often 1,024) will crash with `EMFILE: too many open files`. Increase `nofile` to `1,000,000` in `/etc/security/limits.conf`.
2. **Socket Buffer Sizing:** Linux allocates read and write buffers for each TCP socket (default 128KB–256KB). 100,000 sockets $\times$ 256KB = **25 GB of RAM** just in kernel socket buffers! Reduce default buffer sizes in `sysctl.conf` (`net.ipv4.tcp_rmem` and `tcp_wmem`) to ~4KB–8KB for high-density WebSocket servers.
3. **Runtime Goroutine / Worker Overhead:** In Go, an idle connection with separate read and write pumps uses 2 goroutines (~4 KB to 8 KB RAM). In Node.js, event listeners and V8 object wrappers consume ~10 KB–20 KB per socket.

## 7. Key Takeaways Summary

- **Choose the right tool:** Use **Server-Sent Events (SSE)** for unidirectional server-to-client streaming (dashboards, notifications, AI token generation); use **WebSockets** for true bidirectional, interactive applications (chat, gaming, collaborative editing).
- **WebSockets upgrade from HTTP via status 101**, shedding massive HTTP header overhead and reducing frame size to 2–10 bytes.
- **Scale horizontally using distributed Pub/Sub (Redis / NATS)** so that server nodes can broadcast messages across instances without knowing where individual clients are connected.
- **Always implement bidirectional Ping/Pong heartbeats** to detect and reclaim half-open ghost connections.
- **Tune OS file descriptor limits (`ulimit -n`) and TCP socket buffers** when scaling past 10,000 concurrent connections.
