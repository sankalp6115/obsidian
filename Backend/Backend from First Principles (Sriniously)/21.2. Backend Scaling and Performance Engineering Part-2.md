# 21.2. Backend Scaling and Performance Engineering: Part-2

While Part 1 focused on latency mechanics, queueing theory, basic indexing, and in-memory caching, **Part 2 dives into distributed architectural patterns**: database read replicas, sharding, distributed SQL, Content Delivery Networks (CDNs), Edge Computing, asynchronous event-driven pipelines, microservices trade-offs, and serverless computing.

Scaling at this level requires transitioning from single-node optimizations to managing **distributed systems, eventual consistency, and physical network topology**.

## 2. Advanced Horizontal Scaling & Load Balancing

When distributing traffic across multiple application instances, load balancers govern how work is assigned.

```
                                  Client Requests
                                         │
                                         ▼
                            ┌─────────────────────────┐
                            │ Load Balancer (ALB/NLB) │
                            └────────────┬────────────┘
               ┌─────────────────────────┼─────────────────────────┐
               ▼                         ▼                         ▼
      ┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
      │ Backend Node #1 │       │ Backend Node #2 │       │ Backend Node #3 │
      └─────────────────┘       └─────────────────┘       └─────────────────┘
               │                         │                         │
               └─────────────────────────┼─────────────────────────┘
                                         ▼
                        ┌─────────────────────────────────┐
                        │ Distributed Session Store (Redis│
                        └─────────────────────────────────┘
```

### 2.1 Load Balancing Algorithms
1. **Round Robin:** Cycles through servers sequentially ($1 \rightarrow 2 \rightarrow 3 \rightarrow 1$). Works well when requests have uniform computational weight.
2. **Weighted Round Robin:** Assigns more requests to servers with higher hardware capacity.
3. **Least Connections:** Routes new requests to the instance with the fewest active TCP connections. **Superior for varied workloads** (e.g., short health checks mixed with long file downloads).
4. **IP Hash:** Hashes the client IP address to consistently route the same client to the same server.

### 2.2 The Anti-Pattern of Sticky Sessions
- **Sticky Sessions (Session Affinity):** The load balancer inspects a cookie or IP to route a given user to the exact same server instance that handled their login.
- **Why Sticky Sessions Break Scalability:**
  - **Uneven Load Distribution:** A few power users hitting one server can overload it while other instances sit idle.
  - **Downtime Vulnerability:** If Server B crashes, all users "stuck" to Server B have their active sessions wiped out and must log in again.
- **The Modern Standard:** Completely eliminate sticky sessions by externalizing all session and token data to a distributed Redis cluster.

## 3. Database Scaling: Replicas, Sharding & Distributed SQL

Relational databases (PostgreSQL, MySQL) inevitably hit vertical scaling limits when data size and concurrent write volumes surpass single-machine boundaries.

### 3.1 Read-Write Separation (Primary-Replica Replication)
In typical consumer web platforms, **70% to 90% of traffic consists of read queries** (`SELECT`), while only 10% to 30% are writes (`INSERT`, `UPDATE`, `DELETE`).

```
                            API Write Traffic      API Read Traffic
                                   │                      │
                                   ▼                      ▼
                        ┌─────────────────────┐   ┌───────────────────────┐
                        │   Primary (Master)  │   │  Read Replicas Pool   │
                        │   (Handles Writes)  │   │  (Handles All Reads)  │
                        └──────────┬──────────┘   └───────────────────────┘
                                   │ Asynchronous
                                   │ Replication
                                   ▼
                        ┌─────────────────────┐
                        │     Read Replica    │
                        └─────────────────────┘
```

#### The Replication Lag Trap (Read-Your-Own-Writes Consistency)
- Because replication from Primary to Replicas is **asynchronous** (to avoid blocking write transactions), there is always a tiny propagation delay (**Replication Lag**, usually 10ms–500ms).
- **The Problem:** A user updates their profile name from "Alice" to "Bob" (written to Primary). The frontend immediately redirects and fetches `GET /profile`. The read request hits a Read Replica that hasn't received the replication stream yet. The user still sees "Alice", assumes the save failed, and clicks submit repeatedly.
- **Architectural Solution:** Enforce **Read-Your-Own-Writes Consistency**:
  - Route read queries for an authenticated user to the **Primary database for a short window (e.g., 3–5 seconds)** immediately following any mutating write operation by that user.
  - After the replication lag window elapses, route subsequent reads back to the read replica pool.

### 3.2 Database Partitioning & Sharding
When a single table grows to hundreds of millions or billions of rows, a single database instance cannot store or index the dataset.

```
                            Horizontal Sharding by Tenant ID
                                           │
                            Incoming Request (Tenant: 42)
                                           │
                                           ▼
                               ┌───────────────────────┐
                               │ Hash Function / Router│ (42 % 3 = Shard 0)
                               └───────────┬───────────┘
                ┌──────────────────────────┼──────────────────────────┐
                ▼                          ▼                          ▼
      ┌──────────────────┐       ┌──────────────────┐       ┌──────────────────┐
      │     Shard 0      │       │     Shard 1      │       │     Shard 2      │
      │ Tenants: 0, 3, 6 │       │ Tenants: 1, 4, 7 │       │ Tenants: 2, 5, 8 │
      └──────────────────┘       └──────────────────┘       └──────────────────┘
```

- **Vertical Partitioning:** Separating distinct domains into separate databases (e.g., moving `orders` and `products` to different database clusters).
- **Horizontal Sharding:** Splitting rows of the *same* table across multiple discrete database servers using a **Shard Key** (e.g., `tenant_id` or `user_id`).
- **The Pain Points of Sharding:**
  - Cross-shard `JOIN` operations become virtually impossible or prohibitively slow.
  - Distributed transactions across multiple shards require complex protocols like Two-Phase Commit (2PC).
  - **Hot Shards:** If a celebrity user or giant enterprise tenant shares a shard, that shard suffers severe resource starvation.

### 3.3 Modern Distributed SQL Databases
Modern NewSQL engines automatically handle distributed consensus, replication, and sharding under the hood using protocols like Raft or Paxos:
- **CockroachDB:** Highly resilient, PostgreSQL-compatible, distributed ACID database.
- **YugabyteDB:** Distributed PostgreSQL engine offering horizontal write scalability.
- **Google Cloud Spanner:** Globally distributed database using atomic clocks for synchronization.

## 4. Edge Computing & Content Delivery Networks (CDNs)

### 4.1 The Physical Speed of Light Constraint
Network packets travel through fiber-optic cables at approximately two-thirds the speed of light.
- A round-trip request between Sydney, Australia and a server in Northern Virginia, USA spans ~20,000 kilometers.
- The physical speed-of-light propagation latency alone is **120ms–160ms**, completely ignoring routing hops and server compute!

```
Traditional Architecture (High Latency)
[ User in Tokyo ] ──────────────── (180ms transit) ────────────────▶ [ Server in US-East ]

Edge / CDN Architecture (Low Latency)
[ User in Tokyo ] ── (5ms) ──▶ [ Tokyo CDN Edge PoP ] (Cached Response / Edge Worker)
```

### 4.2 Content Delivery Networks (CDNs)
- **Providers:** Cloudflare, Fastly, AWS CloudFront.
- CDNs deploy hundreds of Points of Presence (PoPs) globally.
- Static assets (images, JavaScript bundles, CSS, video segments) are cached at the edge, returning responses in 5ms–15ms directly from the user's city.

### 4.3 Edge Computing (Cloudflare Workers, Vercel Edge, Lambda@Edge)
- Allows running lightweight backend logic (V8 isolates) directly on edge nodes closest to the user.
- **Ideal For:** Geolocation redirects, authentication header verification, A/B testing, bot detection, HTML rewrites.
- **The Edge Fallacy:** If your Edge Worker in Tokyo still needs to query a PostgreSQL database located in `us-east-1`, you have not eliminated latency; the worker will still wait 180ms for the database query round-trip.

## 5. Asynchronous Processing & Event-Driven Architecture

In synchronous request-response models, the client connection stays open while the backend completes every operational step. This binds threads, consumes connection pools, and increases p99 latency.

```
Synchronous (Blocking):
[ Request ] ──▶ [ Validate ] ──▶ [ Write DB ] ──▶ [ Generate PDF (3s) ] ──▶ [ Send Email (1s) ] ──▶ [ Response (4.2s) ]

Asynchronous Event-Driven:
[ Request ] ──▶ [ Validate ] ──▶ [ Write DB ] ──▶ [ Enqueue Job (5ms) ] ──▶ [ Immediate Response 202 (25ms) ]
                                                        │
                                                        ▼
                                             ┌──────────────────────┐
                                             │ Task Queue (BullMQ)  │
                                             └──────────┬───────────┘
                                                        ▼
                                             ┌──────────────────────┐
                                             │  Background Workers  │
                                             │  (Process in bg)     │
                                             └──────────────────────┘
```

### Architectural Advantages:
1. **Traffic Spike Buffering:** If 10,000 users register simultaneously, background workers process tasks at a steady, sustainable pace without crashing downstream email or payment providers.
2. **Failure Isolation & Retries:** If the external email service fails, the main user registration still succeeds. The queue worker automatically retries the email task with exponential backoff.

## 6. Monoliths vs. Microservices: Honest Trade-Offs

Microservices are often marketed as the default modern architecture, but they introduce massive operational complexity.

```
┌───────────────────────────────────────┬───────────────────────────────────────┐
│           MODULAR MONOLITH            │             MICROSERVICES             │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ • In-memory function calls (0.001ms)  │ • Network RPC / HTTP calls (5ms-50ms) │
│ • Single deployment pipeline          │ • Dozens of independent CI/CD pipelines│
│ • Strong ACID database transactions   │ • Distributed transactions / Saga     │
│ • Simple local debugging and logging  │ • Distributed tracing (OpenTelemetry) │
│ • Easy refactoring across domains     │ • Hard API contracts & versioning     │
└───────────────────────────────────────┴───────────────────────────────────────┘
```

### When Microservices Actually Make Sense:
1. **Organizational Scale:** When engineering teams grow past 50–100 engineers and developers constantly step on each other’s toes in a single repository.
2. **Divergent Hardware Requirements:** When one specific module requires specialized hardware (e.g., a Rust/C++ video encoding service requiring high GPU/CPU vs. a CRUD user service requiring minimal RAM).
3. **Independent Scalability:** When one service handles $100\times$ the throughput of the rest of the application.

> [!TIP]
> **Best Practice:** Start with a well-architected **Modular Monolith** with clean boundaries between domain modules. Only extract a module into an independent microservice when performance bottlenecks or team organization genuinely require it.

## 7. Serverless Computing (FaaS): Promises & Pitfalls

Serverless (AWS Lambda, Google Cloud Functions) executes functions in ephemeral, event-triggered containers.

### Strengths:
- **Zero Idle Cost:** Costs nothing when traffic drops to zero.
- **Effortless Scalability:** Automatically scales from 1 instance to thousands of concurrent executions.

### The Critical Pitfalls:
1. **Cold Starts:** When a function hasn't been invoked recently, the cloud provider must spin up a new container and initialize runtime environments, adding 200ms–2,000ms latency to the initial request.
2. **Database Connection Exhaustion:** Serverless functions cannot maintain shared persistent connection pools. 1,000 concurrent Lambda instances will attempt to open 1,000 direct database connections to PostgreSQL, crashing it instantly unless an intermediate proxy like **AWS RDS Proxy** or **Prisma Accelerate** is deployed.
3. **Vendor Lock-in & Debugging Complexity:** Difficult to test and profile complex distributed serverless flows locally.

## 8. The Golden Engineering Rule: Measure Before Optimizing

> [!IMPORTANT]
> *"Premature optimization is the root of all evil."* — Donald Knuth

Before writing complex caching layers, sharding tables, or breaking apart microservices:
1. **Profile First:** Instrument your application with distributed tracing (OpenTelemetry) and query analyzers (`EXPLAIN ANALYZE`).
2. **Identify the True Bottleneck:** Never assume where latency originates; let telemetry data guide your engineering priorities.
3. **Benchmark Continuously:** Measure baseline p95/p99 before and after every optimization to confirm real performance improvements.

---

## 9. Key Takeaways Summary

- **Ditch sticky sessions:** Scale horizontally by keeping application servers strictly stateless and externalizing session data to Redis.
- **Implement Read-Write separation:** Offload read-heavy traffic to Read Replicas while guaranteeing Read-Your-Own-Writes consistency.
- **Use sharding only as a last resort:** Exhaust vertical scaling, indexing, read replicas, and caching before introducing the immense operational overhead of database sharding.
- **Leverage CDNs and Edge Computing** to conquer the speed-of-light physical distance barrier for global users.
- **Decouple heavy operations asynchronously** with task queues to preserve sub-second HTTP response times.
- **Start with a modular monolith;** transition to microservices only when organizational size or specialized computational workloads justify the complexity.
