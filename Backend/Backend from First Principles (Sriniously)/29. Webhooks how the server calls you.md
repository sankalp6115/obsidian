# 29. Webhooks: How the Server Calls You

## 1. Introduction: The Reverse API Paradigm

In traditional backend interactions, your application acts as the client, actively making HTTP requests to external services (Stripe, GitHub, Twilio, Resend). 

**Webhooks invert this relationship.** A webhook is a **user-defined HTTP callback**—a pattern where an external service makes an HTTP `POST` request **to your backend** as soon as an asynchronous real-world event occurs.

```
                           Traditional API vs. Webhook
┌───────────────────────────────────────┬───────────────────────────────────────┐
│        Traditional Polling (Pull)     │             Webhook (Push)            │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ [ Your Backend ]                      │ [ External Provider (Stripe) ]        │
│        │                              │        │                              │
│        │ GET /charges?status=paid     │        │ Event occurs:                │
│        ├─────────────────────────────▶│        │ "payment_intent.succeeded"   │
│        │ (Repeated every 5 seconds)   │        │                              │
│        │ "Nothing yet..."             │        │ POST /webhooks/stripe        │
│        │◀─────────────────────────────┤        ├─────────────────────────────▶│
│        │                              │        │ [ Your Backend ]             │
│ • High bandwidth & CPU waste          │ • Instant, zero-latency notification  │
│ • Hits provider rate limits           │ • Zero wasted polling requests        │
└───────────────────────────────────────┴───────────────────────────────────────┘
```

## 2. Anatomy of a Webhook Payload

External providers deliver event notifications as structured JSON bodies accompanied by contextual delivery headers:

```http
POST /api/webhooks/stripe HTTP/1.1
Host: api.yourcompany.com
Content-Type: application/json; charset=utf-8
User-Agent: Stripe/1.0 (+https://stripe.com/docs/webhooks)
Stripe-Signature: t=1762089200,v1=5257a869e7eceedd79f10f1709d66a23e62e5e47c5193d3806e6100f3171d32d

{
  "id": "evt_1Nu0ABC123xyz",
  "object": "event",
  "api_version": "2024-06-20",
  "created": 1762089200,
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "id": "pi_3Nu0DEF456",
      "amount": 9900,
      "currency": "usd",
      "customer": "cus_98124",
      "status": "succeeded"
    }
  }
}
```

- **`id`:** Globally unique event delivery identifier (critical for deduplication).
- **`type`:** Machine-readable event name indicating what occurred.
- **`created`:** Unix timestamp when the event was recorded.
- **`data.object`:** The actual entity payload.

## 3. Webhook Security: Verification & Replay Protection

Because webhook endpoints are public HTTP URLs, **anyone on the internet can send POST requests to them**. If an attacker sends a fake `payment_intent.succeeded` payload, your backend might fulfill orders without receiving any money!

### 3.1 Cryptographic HMAC Signatures (The Production Standard)
Leading providers (Stripe, GitHub, Shopify) secure webhooks using **HMAC-SHA256 (Hash-based Message Authentication Code)**:

```
                            HMAC Signature Verification
                                         │
        ┌────────────────────────────────┴────────────────────────────────┐
        ▼                                                                 ▼
 [ External Provider ]                                             [ Your Backend ]
 1. Takes raw request body + timestamp                             1. Reads raw bytes before JSON parse
 2. Signs with shared Webhook Secret Key                            2. Extracts timestamp and signature
    HMAC_SHA256(secret, timestamp + "." + body)                    3. Recomputes HMAC locally
 3. Sends signature in header: Stripe-Signature                     4. Compares using timingSafeEqual()
```

#### The Raw Body Prerequisite:
> [!CAUTION]
> **Signature verification requires the exact, unparsed raw byte body.** If your web framework automatically parses incoming JSON into an object (`JSON.parse`) and you re-stringify it (`JSON.stringify`), key ordering, indentation, and Unicode escapes will change, completely invalidating the cryptographic HMAC check!

```typescript
// Express.js configuration to preserve raw body for webhooks:
app.post(
  '/api/webhooks/stripe',
  express.raw({ type: 'application/json' }),
  (req, res) => {
    const rawBody = req.body; // Buffer of raw bytes
    const signature = req.headers['stripe-signature'];
    
    // Verify using SDK or crypto
    const event = stripe.webhooks.constructEvent(
      rawBody,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET
    );
    // Verified authentic!
  }
);
```

### 3.2 Defending Against Replay Attacks
In a **Replay Attack**, an attacker intercepts a legitimate webhook payload and signature and repeats the exact same request 50 times to receive 50 subscription renewals.

**Mitigation:**
1. Providers include a timestamp `t` in the signature header (`t=1762089200,v1=...`).
2. The backend extracts `t` and checks:
   $$|\text{Current System Time} - t| > 300\text{ seconds (5 minutes)}$$
3. If the timestamp is older than 5 minutes, reject the webhook immediately, neutralizing replay attacks.

## 4. Handling Delivery Failures, Retries & Idempotency

### 4.1 At-Least-Once Delivery
Webhook systems operate under **At-Least-Once Delivery guarantees**:
- If your server experiences a momentary network blip, returns a 500 error, or takes too long to respond, the provider assumes delivery failed and automatically retries with exponential backoff.
- **The Guarantee:** You will inevitably receive the exact same webhook event multiple times.

### 4.2 Idempotency & Deduplication
To prevent duplicate state mutations (e.g., charging a card twice, shipping duplicate products), webhook handlers must be strictly **idempotent**:

```sql
-- Create an idempotent tracking table
CREATE TABLE processed_webhooks (
    event_id VARCHAR(255) PRIMARY KEY,
    provider VARCHAR(50) NOT NULL,
    processed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

```typescript
// Idempotent handler pattern
async function handleWebhook(event: WebhookEvent) {
  // 1. Try to record event ID in DB
  const inserted = await db.query(
    `INSERT INTO processed_webhooks (event_id, provider)
     VALUES ($1, $2)
     ON CONFLICT (event_id) DO NOTHING
     RETURNING event_id;`,
    [event.id, 'stripe']
  );

  // If already processed, acknowledge with 200 OK and ignore
  if (inserted.rowCount === 0) {
    logger.info(`Duplicate webhook ${event.id} ignored.`);
    return;
  }

  // 2. Execute business logic for new event
  await processPayment(event.data);
}
```

## 5. Architectural Pattern: Fast Acknowledgment & Queue Decoupling

Providers like Stripe and GitHub enforce strict HTTP timeouts (typically **5 to 10 seconds**). If your backend takes 12 seconds to generate a PDF invoice, query multiple tables, and email the customer, the provider cuts the connection, marks the webhook as failed, and triggers retries.

> [!IMPORTANT]
> **Production Best Practice:** Never execute heavy business logic synchronously inside the webhook HTTP request lifecycle. Decouple ingestion from processing using a background task queue.

```
                  Fast Acknowledgment Architecture (<50ms)
                  ════════════════════════════════════════

[ Stripe / GitHub ] ──▶ [ Webhook Route ]
                              │ 1. Verify HMAC Signature
                              │ 2. Check Idempotency Table
                              │ 3. Enqueue Job into BullMQ / Redis
                              ▼
                        [ Immediate Response: HTTP 200 OK ] ──▶ (Returns in 25ms!)
                              │
                              ▼
                        [ Background Task Queue (Redis) ]
                              │
                              ▼
                        [ Background Worker ]
                        ├─ Generate PDF Invoice
                        ├─ Update PostgreSQL Inventory
                        └─ Dispatch Customer Confirmation Email
```

## 6. Publishing Webhooks: The Transactional Outbox Pattern

When your own platform allows customers to register webhook URLs (e.g., notifying them when a task is completed), you face the **Dual-Write Problem**:
- What if you update the database, but your server crashes before making the HTTP webhook call?
- What if you make the HTTP call, but the database transaction fails and rolls back?

### The Transactional Outbox Pattern Solution
Instead of dispatching webhooks directly from application business logic, use an **Outbox Table** committed within the same ACID transaction:

```
Step 1: Single ACID Database Transaction
┌────────────────────────────────────────────────────────────────────────┐
│ BEGIN TRANSACTION;                                                     │
│   UPDATE orders SET status = 'COMPLETED' WHERE id = 1042;              │
│   INSERT INTO webhook_outbox (event_type, payload, status)             │
│   VALUES ('order.completed', '{"order_id":1042}', 'PENDING');         │
│ COMMIT;                                                                │
└────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
Step 2: Asynchronous Outbox Poller / Change Data Capture (CDC)
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Background worker polls PENDING outbox records                      │
│ 2. Calculates HMAC signature with customer's secret key                │
│ 3. Dispatches HTTP POST with exponential backoff retries               │
│ 4. Updates outbox record to DELIVERED or FAILED                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 7. Key Takeaways Summary

- **Webhooks are reverse APIs:** The external provider calls your HTTP server when events happen.
- **Never trust unverified webhooks:** Always verify cryptographic **HMAC-SHA256 signatures** using the unparsed raw request body bytes.
- **Protect against replay attacks** by asserting that the signature timestamp is within a 5-minute tolerance window.
- **Design for At-Least-Once delivery:** Store event IDs in an idempotency table to safely ignore duplicate retries.
- **Always respond fast (<100ms):** Validate signature, enqueue the payload into a background queue, and return `200 OK` immediately.
- **When publishing webhooks, implement the Transactional Outbox Pattern** to guarantee consistency between database updates and event dispatch.
