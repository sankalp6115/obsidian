## 1. Traditional Definition of a Backend

- A **computer listening for requests** (HTTP, WebSocket, gRPC or any other kind) through an **open port** (e.g. 80 or 443) that is accessible over the internet, so that clients or other frontends can connect to it, send data to it, or receive data from it.
- It's called a **server** because it **serves** content: static files (images, JavaScript, HTML) or JSON. It also accepts data if the client sends something.
- This is a fair definition, but the goal here is a **holistic view**: seeing the components physically and how they work together behind the scenes.

## 2. Tracing a Request: Browser → Backend Server (AWS demo)

Setup: a backend server deployed on AWS, serving sample "users" data. The request is made from the browser with the Network tab open and cache disabled (so the appropriate status code shows). Request and response themselves are covered in a later video; here the focus is the flow.

### Hop 1 – DNS

- The request URL has a **domain name** with a **subdomain**, so the first stop is the **DNS server**.
- DNS is a huge topic; basics only:
    - **A records** point a name to a particular **IP address**.
    - **CNAME records** point to a particular domain name or subdomain.
- In the demo there are two A records; one is the `backend demo` subdomain, pointing to a specific IP address.

### Hop 2 – AWS EC2 instance

- That IP is the **public IP address of an EC2 instance** (verified in the AWS console: EC2 → Instances → the deployed instance).
- So the request reaches the EC2 instance through that IP.

### Hop 3 – Firewall (AWS Security Group)

- Before reaching the computer, the request passes through the **AWS-native firewall**, configured via the **security group** assigned to the instance.
- The security group specifies which **ports** are allowed/accessible over the internet. Three are allowed in the demo:
    - One port for logging into the instance via terminal/command line (SSH)
    - **HTTPS (443)**
    - **HTTP (80)**
- If ports 443 and 80 aren't allowed, **AWS blocks the request right there** and it never reaches the server.

### Hop 4 – Reverse proxy (Nginx)

- A **reverse proxy** is a server that **sits in front of other servers**, so redirects/configs can be managed from a centralized place instead of in every server.
- Nginx is used here. Parts of the config:
    - Certbot (transcribed "sbot") is used to **assign SSL certificates automatically** (not a focus of the demo). It handles **listening on port 80 and redirecting to port 443 (HTTPS)**.
    - `server_name` defines the domain/subdomain (`backend demo`). Requests to this domain are already routed to the instance by DNS.
    - Nginx **forwards every request for this domain to `localhost:3001`**, the port the Node server runs on.

### Hop 5 – The Node server

- Processes are managed with **PM2** (`pm2 list`): two processes — one frontend, one backend. The backend is a **Node server**.
- From the instance's point of view, the Node server just runs on localhost; **Nginx and domain names route requests to it over the internet**.
- Calling `localhost:3001/users` on the instance gives the same response as via the domain. Likewise, during local development, `localhost:3000/users` in the browser gives the same response.

### Summary of the flow

**Browser → DNS server → AWS (firewall) → EC2 instance → Nginx → `localhost:3001` (Node server)**

## 3. Why Do We Need Backends?

### Example: liking a post on Instagram

Between clicking "like" and your friend receiving a notification:

1. The app sends a **request to the server**.
2. The server parses the request and identifies the user (name/ID).
3. It **persists/saves** the action (usually in a **database**).
4. It finds who owns the post you liked (that user's ID).
5. It **triggers an action that sends a notification** to that user's phone.

- There has to be a **centralized computer** holding information about all users, because each user's app is customized to their profile, the people they follow and the actions they can perform; your friend only receives notifications intended for them. A server must hold all kinds of information and all kinds of state, so it has to be **centralized**.

### Condensed to one word: **Data**

- The need to **fetch** data, **receive** data and **persist** data somewhere — and every action that deals with data.

## 4. Why Not Do Everything on the Frontend?

The question: the frontend is also a device/computer — why not connect to the database there and perform every action servers do? Everything would be distributed, with (technically) better performance. To answer, first look at how frontends work.

### 4.1 How a frontend works (Next.js demo)

- A **Next.js application** deployed on the same AWS EC2 instance.
- In the Network tab on refresh:
    - The first document the browser fetches is an **HTML file** (from the frontend domain).
    - All other resources — **JavaScript files, images, fonts, CSS files** — are fetched in **separate requests**.
- Same path as the backend: DNS record for the `frontend demo` subdomain → same EC2 public IP → ports 443/80 allowed → Nginx. The Nginx config is the same (same Certbot config) except it listens for the frontend domain and **redirects to `localhost:3000`** instead of 3001.
- The request reaches the **Next.js frontend server**, which serves the JS, CSS and HTML files over the network to the browser.

### What the browser does after getting the HTML

- Fetches resources one by one.
- Once **CSS** is fetched, the browser **paints** the window (styles, black background, fonts, button styles).
- Once **JavaScript** is fetched, the browser **hydrates** event listeners for buttons and other interactions. (Example: clicking a button redirects to another page because the browser fetched the JS and added the event listeners.)

### Key difference

- Frontend logic/JavaScript is **fetched from the server and executed by the browser on the client's machine** — **the browser is the runtime**.
- In a traditional backend (the EC2 example), the server **processes the request** and sends back the result: the processing happens on the server.
- Frontend is the **opposite**: the server sends code, and the browser runs it.

### 4.2 Browser sandboxing

- Browser runtimes are **sandboxed**: isolated from the operating system, processes and file system. Code can only access a limited set of resources:
    - The **DOM**
    - Browser APIs, e.g. **localStorage**, **cookies**
    - **External APIs**, but only if the external API sends the required headers (CORS)
- **CORS** (to be covered in more depth in a future video) can be thought of as a **browser security policy** that restricts JavaScript from calling external APIs on a different domain than the current one. Example: a frontend at `frontend demo` can only fetch resources/call APIs on the same domain; calling a different domain gets blocked by the browser due to CORS policy. There are ways around it via HTTP headers (explored later).
- The sandboxing and security restrictions make sense: the browser fetches code from a remote server and executes it on the user's machine. Without isolation, a website's unknown code could access the user's file system, copy files and sensitive details, and send them to its own servers — "a very scary idea," hence browser security policies.

### 4.3 Reasons backend logic can't live in the frontend

1. **Security**
    
    - Browser security policies are very restrictive. Backends often need access to the underlying **file system** (e.g. writing to a log file) or **environment variables**; browsers won't allow that.
2. **External API calls**
    
    - You can't call external APIs freely unless they send the right CORS headers, and you don't control all external APIs. Backend servers often need to connect to other servers and fetch data from multiple places, so this restriction is a deal breaker.
3. **Databases**
    
    - The server runtime has access to **native database drivers** (e.g. `pg` for Postgres, MongoDB drivers) that communicate efficiently with databases. These drivers work in environments that can handle **socket connections**, **binary data** and **persistent connections** — things browsers can't do.
    - Backend servers maintain a **connection pool** to the database server so they don't create and destroy connections repeatedly. Servers receive thousands of requests per second; doing connect/destroy per request would overwhelm the database server.
    - Browsers aren't designed to maintain persistent database connections. Even if they could, each user would need their own dedicated connection, overwhelming the database with too many connections. There's also no easy way to manage connection pooling or efficient query execution from browser environments.
    - (How backends communicate with databases will be explored later.)
4. **Computing power**
    
    - Frontends run everywhere: smartphones, desktops, laptops — even a computer with 256 MB of RAM and a single-core processor. A user may not have enough computing power for heavy business logic, so things lag and sometimes break.
    - A **centralized backend server** serving a large number of clients can easily have its **memory and CPU increased** whenever needed to handle the load.

- The list could continue, but the conclusion: **keeping backend logic in the frontend is not a good idea** (assuming it could even be done in the first place).
