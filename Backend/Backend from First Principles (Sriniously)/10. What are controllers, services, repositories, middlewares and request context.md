# Handlers, Services, Repositories, Middlewares, and Request Context

---

## 1. Architectural Overview: Handlers, Services, and Repositories

Splitting backend responsibilities into three distinct layers is not a strict language or runtime mandate—a single handler could theoretically run all server code. Instead, this three-tier architecture is a design pattern used to make applications scalable, maintainable, easier to extend with new features, and simpler to debug.

```
Client (HTTP Request)
       │
       ▼
Routing Mechanism
       │
       ▼
[ Handler / Controller ]  <──  HTTP-level concerns, binding, validation, response format
       │
       ▼
   [ Service ]            <──  Core business logic, orchestration, external calls
       │
       ▼
  [ Repository ]          <──  Database queries, direct data persistence/retrieval

```

---

### Layer 1: Handler (Controller) Layer

* **Primary Role:** Serves as the primary entry point after routing. It controls data flow across the network boundary (client-to-server and server-to-client) and handles all HTTP-specific concerns.
* **Default Arguments:** Almost all major backend environments (e.g., Go, Node.js/Express, Python) supply two foundational objects/variables to handlers by default:
* **Request Object:** Used to inspect and extract incoming request data.
* **Response Object:** Used to set HTTP status codes, configure response headers, and write the response body.


* **Key Responsibilities:**
1. **Data Extraction & Ingestion:**
* Extract query parameters (common in `GET` requests).
* Extract request bodies (common in `POST`, `PUT`, `PATCH`, and some `DELETE` requests).
* Extract path parameters and headers.


2. **Deserialization / Binding:**
* Clients send data serialized as JSON over the network.
* The handler deserializes this raw JSON payload into the programming language's native data structure (e.g., a `struct` in Go or Rust, a `dict` or class instance in Python, or a native JavaScript object parsed by upstream middleware in Node.js).
* *Failure Handling:* If deserialization or binding fails, the handler halts execution immediately and returns an **HTTP 400 (Bad Request)** to the client.


3. **Validation & Transformation:**
* **Validation:** Enforces that all mandatory fields are present and conform to required types and boundaries, preventing malicious payloads or missing values from passing downstream.
* **Transformation:** Adjusts input data into a convenient internal format before calling deeper layers.
* *Best Practice:* Design query parameters to be optional wherever possible.
* *Setting Defaults:* For an endpoint like `GET /books?sort=date`, if the client omits `sort`, the transformation step sets a safe default (e.g., defaulting `sort` to `"date"` or `"name"`). This prevents branching checks (e.g., `if sort == null`) inside the service layer.




4. **Delegation:** Passes sanitized, validated, and transformed native data to the service layer, alongside essential metadata (such as authentication identity and permissions).
5. **HTTP Response Generation:**
* Awaits output from the service layer.
* Determines and sets appropriate status codes:
* **Success:** `200 OK` (e.g., returning a list of books), `201 Created`, or `204 No Content` (standard for `DELETE` operations where no body is returned).
* **Client Failure:** `4xx` series (e.g., `400 Bad Request`).
* **Server Failure:** `5xx` series (e.g., `500 Internal Server Error`).


* Formats and returns the final serialized response body to the client.





---

### Layer 2: Service Layer

* **Primary Role:** Contains the actual **business logic** and execution flow of the application.
* **HTTP Decoupling:**
> A service method should look like a standard, isolated function. From inspecting its signature and implementation, you should not be able to tell that it belongs to an HTTP API.


* It must have **zero knowledge** of HTTP request objects, response objects, status codes, or web-specific headers.


* **Key Responsibilities:**
* Takes plain, validated data inputs, processes them, and returns raw data or execution statuses (e.g., returning `{ success: true }`).
* **Orchestration:** Can invoke multiple repository methods, merge/filter disparate database results, and extract necessary fields.
* **External Integrations:** Coordinates non-database tasks such as dispatching emails, triggering device push notifications, or calling third-party webhooks.
* Can function purely without database access (e.g., a notification service whose only task is sending an email to a user).



---

### Layer 3: Repository (Database) Layer

* **Primary Role:** Directly interfaces with the persistence engine (relational databases, document stores, key-value caches like Redis).
* **Key Responsibilities:**
* Receives structured query or filtering parameters from the service layer.
* Constructs and executes database queries (reads, inserts, updates, deletes).
* Returns direct, un-orchestrated database output back to the service layer.


* **Single Responsibility Rule:**
* **Each repository function should do exactly one thing.**
* *Anti-Pattern:* Writing a single function that returns either a single record or all records based on an optional parameter.
* *Correct Pattern:* Maintain separate, explicit functions:
* `getBookById(id)` → Returns a single book.
* `getAllBooks(sortParam)` → Returns all books.


* If results need to be combined or structured across tables/methods, that logic belongs in the **service layer**, not the repository.

## 2. Middlewares

### What is a Middleware?

Middlewares are modular functions executed in the middle of the request-response lifecycle—positioned along the boundaries between the initial server entry point, the routing mechanism, the controller handlers, and the final response dispatch.

```
Request Entry Point
       │
       ▼
[ Middleware 1 (e.g., CORS) ]
       │  (via next())
       ▼
[ Middleware 2 (e.g., Logging) ]
       │  (via next())
       ▼
 Routing Engine
       │
       ▼
[ Middleware 3 (e.g., Auth) ]
       │  (via next())
       ▼
Handler / Controller ───► Service ───► Repository
       │
       ▼
[ Error Handling Middleware ]
       │
       ▼
Response to Client

```

* **Core Signature:** Typically receives three arguments from the server runtime:
1. `req` (Request object)
2. `res` (Response object)
3. `next` (Function)


* **The `next()` Function:** Explicitly delegates control to the subsequent middleware or execution context (e.g., moving to the router or the handler). Calling `next()` crosses the boundary to the next execution step.
* **Short-Circuiting Ability:** Because a middleware has direct access to both `req` and `res`, it can evaluate conditions, write a response, and **terminate the request immediately** without ever invoking `next()`. This prevents unauthorized or malformed requests from consuming downstream processing or database resources.
* **Why Use Middlewares?**
* **Code Reusability / DRY Principle:** Rather than re-implementing repetitive checks (such as parsing tokens or calculating rate limits) across hundreds of separate route handlers, common operational logic is extracted into reusable middleware steps.



---

### Common Middleware Implementations

| Middleware Type | Functional Purpose | Typical Action on Pass | Action on Fail / Short-Circuit |
| --- | --- | --- | --- |
| **CORS** | Enforces Cross-Origin Resource Sharing based on browser Same-Origin policies. | Checks request `Origin`. If allowed, attaches appropriate CORS access headers and calls `next()`. | If unapproved, omits access headers (causing the browser to block the client response). |
| **Security Headers** | Injects baseline defense headers into the response (e.g., Content Security Policy). | Sets security headers on `res` and calls `next()`. | N/A |
| **Authentication** | Extracts and verifies credentials (JWT, Session IDs) from headers or bodies. | Decodes token, injects user metadata (ID, role) into **Request Context**, calls `next()`. | Halts immediately and returns `401 Unauthorized`. |
| **Rate Limiting** | Throttles incoming client requests within defined time windows (e.g., max 30 calls / 2 sec per IP). | Increments counter; calls `next()` if under limit. | Halts immediately and returns `429 Too Many Requests`. |
| **Logging & Monitoring** | Records structured diagnostic records for auditing and debugging (method, path, body, timing). | Emits logs to console/file/monitoring agent and calls `next()`. | N/A |
| **Data Parsing / Binding** | Handles automated body deserialization from raw network streams. | Parses raw payloads into native representations on `req.body`. | Rejects unparseable data with `400 Bad Request`. |
| **Response Compression** | Compresses heavy payload bodies (e.g., using Gzip) to optimize transfer times. | Intercepts outbound response, encodes payload, sets compression headers. | Modern browsers decompress the stream back to native text/JSON automatically. |
| **Global Error Handling** | Consolidates application-wide errors into clean, structured responses. | Receives uncaught errors from upstream handlers/services, maps them to `4xx` or `5xx`, and formats consistent client payloads. | Placed at the end of the middleware pipeline. |

---

### Why Middleware Ordering Matters

Middlewares execute linearly in one direction. Their placement sequence directly affects security, performance, and stability:

1. **CORS First:** Must verify whether an origin has rights to interact before wasting CPU cycles on downstream logic.
2. **Early Authentication & Rate Limiting:** Prevents unauthorized or abusive requests from hitting deep application services or the database.
3. **Global Error Handling Last:** Because errors flow downstream from handlers and preceding middlewares, a centralized error handler must reside at the very end of the pipeline. If placed earlier, it cannot catch exceptions thrown downstream.

## 3. Request Context

### Definition

A **Request Context** is an isolated, request-scoped key-value state store attached to a single HTTP request lifecycle.

* **Lifecycle:** It is initialized when the request reaches the server and is garbage collected once the response is returned to the client.
* **Scope Isolation:** Completely private to the specific request; data stored in one user's request context cannot leak into concurrent requests from other users.
* **Decoupling Benefit:** Allows disparate middlewares and handlers along the pipeline to share data without having to mutate or tightly couple function argument signatures.

```
Incoming Request
       │
       ▼
[ Auth Middleware ] ───► Injects { userId: "usr_42", role: "admin" } into Context
       │
       ▼
 [ Handler Layer ]  ───► Reads { userId, role } from Context
       │                 (Avoids trusting spoofable client-supplied payload IDs)
       ▼
 [ Service Layer ]  ───► Executes business action on behalf of authenticated user

```

---

### Core Use Cases of Request Context

#### 1. Propagating Authentication & Authorization Data

* **The Security Risk:** Never trust client-supplied identity fields (e.g., reading `userId` from an incoming JSON body). A malicious user could tamper with this field to modify or access data owned by another user.
* **Context Solution:**
1. The authentication middleware verifies the incoming JWT or session token.
2. Upon verification, it extracts trusted metadata (e.g., `userId`, `role`, `permissions`) and sets it directly into the request context.
3. Downstream handlers read this verified `userId` directly from the context when creating resources or querying records.



#### 2. Distributed Tracing & Request Tracking (`X-Request-ID`)

* An upstream middleware generates a unique identifier (such as a UUID) per request and saves it into the context.
* This ID is stamped into application log entries and attached as an `X-Request-ID` header when dispatching downstream HTTP calls to external microservices.
* Simplifies tracing end-to-end request journeys across distributed services when reviewing logs or debugging incidents.

#### 3. Request Timeouts, Deadlines, and Cancellations

* The context can store timeouts, cancellation signals, and deadlines (native to runtimes like Go's `context.Context`).
* If a client disconnects prematurely or a database operation exceeds its allotted deadline, the context emits an abort/cancellation signal downstream to terminate long-running processes, preventing server threads from hanging indefinitely.
