# 27. The Twelve-Factor App

## 1. Introduction & Background

Authored in 2011 by Adam Wiggins and the engineering team at Heroku, **The Twelve-Factor App** is a seminal architectural methodology for engineering cloud-native, Software-as-a-Service (SaaS) backend applications.

### The Core Objectives of the 12 Factors:
1. **Declarative Automation:** Use declarative formats to setup automation, minimizing time and cost for new engineers onboarding to the project.
2. **Clean System Contract:** Maintain a clean, explicit contract with the underlying OS, ensuring maximum portability between execution environments.
3. **Cloud-Native Compatibility:** Architect systems optimized for modern cloud platforms, container orchestrators (Kubernetes), and serverless runtimes.
4. **Continuous Deployment (Dev/Prod Parity):** Minimize divergence between development and production to enable rapid, safe continuous deployment.
5. **Frictionless Elastic Scaling:** Scale up dynamically without requiring fundamental redesigns of tooling, architecture, or code.

### Factor 1: Codebase
> **"One codebase tracked in revision control, many deploys."**

- **Rule:** A 12-factor app is always tracked in a single version-control system repository (Git). 
- **Many Deploys:** A deploy is a running instance of the app (Production, Staging, QA, Local Dev). All deploys share the **exact same codebase** (tracking different branches or commit tags).
- **Multi-Repo vs. Multi-App:** If multiple microservices exist, each is an independent 12-factor app with its own repo. Never share code across distinct apps via copy-pasting; package shared code into private libraries/packages.

---

### Factor 2: Dependencies
> **"Explicitly declare and isolate dependencies."**

- **Never rely on implicit system-wide tooling:** Never assume that the host server has `curl`, `imagemagick`, or a specific Python version pre-installed globally.
- **Explicit Declaration:** Enforce package manifests (`package.json`, `go.mod`, `Gemfile`, `requirements.txt`) specifying exact locked dependency versions.
- **Dependency Isolation:** Use containerization (Docker) to isolate dependencies from the host OS. Docker effectively solved Factor 2 for modern engineering.

---

### Factor 3: Config
> **"Store config in the environment."**

- **Strict Separation:** An application's code and its configuration must be completely decoupled.
- **Config vs. Code:** Config includes anything that changes between deployment targets (database connection URLs, credentials, API tokens, port bindings, log levels).
- **The Litmus Test:** *Could the entire codebase be open-sourced on GitHub this very second without leaking any internal credentials or passwords?* If not, config is incorrectly hardcoded in the codebase.
- **Mechanism:** Inject configuration via Operating System **Environment Variables** (`process.env`, `os.environ`), avoiding environment-specific configuration files (`dev.json`, `prod.json`) committed to Git.

---

### Factor 4: Backing Services
> **"Treat backing services as attached resources."**

- **Backing Services:** Any service the app consumes over the network as part of its normal operation (PostgreSQL, Redis, RabbitMQ, SMTP mailers, AWS S3).
- **Attached Resources:** The codebase makes no distinction between local and third-party services. Both are attached via a **Resource Handle** (URL + credentials):
  - Local Dev: `DATABASE_URL=postgres://localhost:5432/myapp`
  - Production: `DATABASE_URL=postgres://user:pass@rds.us-east-1.amazonaws.com:5432/myapp`
- Swapping an on-premise datastore for a cloud provider (e.g., local Redis for Amazon ElastiCache) requires only modifying an environment variable; **zero code changes**.

---

### Factor 5: Build, Release, Run
> **"Strictly separate build, release, and run stages."**

```
Codebase (Commit) ──▶ [ Build Stage ] ──▶ Compiled Artifact (Docker Image)
                                                 │
                                                 ▼
Environment Config ─────────────────────▶ [ Release Stage ] ──▶ Immutable Release (v42)
                                                                       │
                                                                       ▼
                                                                [ Run Stage ] (Execute Pods)
```

1. **Build Stage:** Translates source code into an executable bundle or container image (compiles binaries, bundles assets, resolves dependencies).
2. **Release Stage:** Combines the immutable build artifact with environment-specific configuration, creating a unique, numbered Release (e.g., `Release v104`). Releases cannot be mutated; changes require a new release.
3. **Run Stage:** Runs the application release in the execution environment.
- **Rule:** Never edit code directly in the runtime environment! Any fix must flow through Build $\rightarrow$ Release $\rightarrow$ Run.

---

### Factor 6: Processes
> **"Execute the app as one or more stateless processes."**

- **Stateless & Share-Nothing:** Application processes are completely disposable and share zero state in local memory or local disk.
- Any state that must survive across requests must be stored in a stateful backing service (PostgreSQL for data, Redis for sessions, S3 for files).
- **No Sticky Sessions:** Never rely on load balancer sticky sessions; any server instance must be able to satisfy any user request at any time.

---

### Factor 7: Port Binding
> **"Export services via port binding."**

- Traditional web applications were frequently injected into monolithic web application containers (e.g., deploying a Java `.war` into an Apache Tomcat server or PHP into Apache HTTPD).
- **12-Factor App:** The application is completely self-contained. It packages its own HTTP runtime engine and binds directly to a listening TCP port specified via environment variables (`PORT=8080`).

---

### Factor 8: Concurrency
> **"Scale out via the process model."**

- Take inspiration from the Unix process model. Structure workloads into distinct, specialized process types:
  - `web`: Handles incoming HTTP traffic.
  - `worker`: Consumes background tasks from queues (e.g., BullMQ, Celery).
  - `clock`: Fires scheduled cron jobs.
- **Independent Scaling:** Scale process types independently according to demand. If queue tasks back up, scale `worker` from 2 to 20 instances while keeping `web` at 3 instances.

---

### Factor 9: Disposability
> **"Maximize robustness with fast startup and graceful shutdown."**

- Processes must be **disposable**—capable of starting or terminating at a moment's notice.
- **Fast Startup:** Reduces deployment rollout windows and enables responsive autoscaling when traffic spikes.
- **Graceful Shutdown:** Upon receiving `SIGTERM`, processes stop accepting new work, drain active requests, close database connections, and exit cleanly.

---

### Factor 10: Dev/Prod Parity
> **"Keep development, staging, and production as similar as possible."**

Historically, projects experienced massive gaps between dev and prod, causing the classic *"It works on my machine!"* excuse.

| Gap Dimension | Historical Reality | Twelve-Factor Standard |
| :--- | :--- | :--- |
| **Time Gap** | Developer writes code; deployed months later. | Code is written and deployed within **hours**. |
| **Personnel Gap** | Devs write code; Ops deploys it. | Developers actively deploy and monitor their code. |
| **Tools Gap** | SQLite in dev; PostgreSQL in prod. | **Identical backing services** across all environments via Docker Compose. |

> [!WARNING]
> Never substitute backing services locally (e.g., SQLite locally vs. PostgreSQL in production). Differences in SQL dialects, concurrency locking, and type casting inevitably cause production outages.

---

### Factor 11: Logs
> **"Treat logs as event streams."**

- An application must **never route, store, or rotate its own log files**. It should not write to `/var/log/app.log`.
- Instead, the app writes its unbuffered event stream directly to standard output (**`stdout`**) and standard error (**`stderr`**).
- The underlying environment (Docker daemon, Kubernetes kubelet, systemd) captures stdout and routes the stream to log indexing backends (Grafana Loki, Elasticsearch, Datadog).

---

### Factor 12: Admin Processes
> **"Run admin/management tasks as one-off processes."**

- Tasks such as running database migrations (`npx prisma migrate deploy`), executing one-off data backfills, or opening an interactive REPL shell.
- **Rules:**
  - Admin processes must run against the **exact same release** (identical code build and environment configuration) as the live application processes.
  - Run admin tasks using the same container image and tooling (`kubectl exec` or one-off Docker run).

---

## 3. Key Takeaways Summary

- The Twelve-Factor methodology remains the universal blueprint for modern cloud-native software.
- **Containerization (Docker) and Kubernetes natively implement many of these factors** (isolation, port binding, disposability, stdout logging).
- **Stateless processes + externalized configuration + attached backing services** form the trifecta that enables seamless horizontal scaling.
- **Maintain zero divergence between development and production tools** to eliminate deployment surprises.
