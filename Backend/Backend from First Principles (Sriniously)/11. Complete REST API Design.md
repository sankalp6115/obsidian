# Complete REST API Design

---

## 1. Introduction & The Core Problem in API Design

* **Importance:** API design is one of the foundational skills of a backend engineer. While there are multiple API paradigms available today (such as **RPC**, **GraphQL**, and **REST**), **REST (Representational State Transfer)** remains one of the most widely used standards.
* **The Confusion in Early-Stage Engineering:** Despite decades of research and industry experience, engineers frequently encounter ambiguous design decisions:
* Should URI path segments use singular or plural nouns (`/book` vs. `/books`)?
* When updating an entity, should the method be `PUT` or `PATCH`?
* If an operation is a **non-CRUD action** (not standard create, read, update, or delete, but a custom server-side task), which HTTP method fits best?
* What exact HTTP status codes should be returned across various edge cases?


* **Why the Confusion Exists:**
* When foundational HTTP standards were drafted, the web was dominated by **MPAs (Multi-Page Applications)** where server-rendered HTML was the norm.
* Modern architecture is dominated by **SPAs (Single-Page Applications)** and heavy client-side applications where browsers download JavaScript bundles once, manage client-side routing, and exchange raw JSON payloads over network APIs.


* **Goal of Standardization:**
* Not to invent new arbitrary rules, but to extract and consistently follow established guidelines from existing standards.
* Consistency frees backend engineers from repeatedly questioning design choices, eliminating guesswork so they can focus on writing core business logic.

## 2. Historical Context & The Evolution of REST

### Tim Berners-Lee & The World Wide Web (1990)

* **Goal:** Created the World Wide Web project to facilitate global knowledge and information sharing.
* **Foundational Inventions (within roughly a year):**
1. **URI (Uniform Resource Identifier):** Standardized mechanism to identify web resources.
2. **HTTP (Hypertext Transfer Protocol):** Underlying communication protocol between clients and servers (evolved from HTTP 1.0 $\to$ 1.1 $\to$ 2.0 $\to$ 3.0).
3. **HTML (Hypertext Markup Language):** The structural skeleton/markup language of web pages.
4. The first web server.
5. The first web browser.
6. The first WYSIWYG (What You See Is What You Get) HTML editor built directly into the browser.


* **The Scalability Crisis:** The web grew exponentially. The original architectural assumptions had not accounted for such massive traffic volumes, pushing the initial web infrastructure toward breakdown.

### Roy Fielding & Architectural Constraints (1993–2000)

Around 1993, Roy Fielding (co-founder of the Apache HTTP Server project) addressed this scalability crisis. He collaborated with Tim Berners-Lee to author the **HTTP 1.1 specification** and formalized the web’s architectural principles in his **2000 Ph.D. dissertation**, introducing **REST (Representational State Transfer)**.

Fielding defined **six core architectural constraints**:

1. **Client-Server:**
* Strict separation of concerns: Clients handle user interface (UI) and user experience (UX); servers handle business logic, data processing, and persistent storage.
* Enables independent evolution of frontend and backend systems, improving scalability.


2. **Uniform Interface:**
* Simplifies system architecture by enforcing a standardized contract across all components.
* Governed by four sub-constraints:
* *Resource identification* (e.g., via URIs).
* *Resource manipulation through representations* (e.g., modifying state via JSON/XML).
* *Self-descriptive messages* (messages contain metadata explaining how to parse them).
* *HATEOAS (Hypermedia As The Engine Of Application State)*.




3. **Layered System:**
* Systems are composed of hierarchical, isolated layers where each layer can only see and communicate with the immediate layer below it.
* Allows the seamless introduction of intermediaries (proxies, load balancers, API gateways) without impacting application code or client logic.


4. **Cache / Cacheability:**
* Server responses must explicitly label themselves as cacheable or non-cacheable.
* Clients and intermediaries can reuse responses to reduce server load, decrease network latency, and improve performance.


5. **Statelessness:**
* Every incoming client request must contain all the contextual data needed to authenticate, understand, and process it.
* The server retains no client session context between requests.
* *Scalability Benefit:* Requests can be routed via round-robin or load balancers across multiple identical backend servers, as any node can process any request independently.


6. **Code on Demand (Optional):**
* Servers can temporarily extend client functionality by transmitting executable code (such as JavaScript scripts) directly to the browser.

## 3. Deconstructing "REST" (Representational State Transfer)

```
[ Resource: User / Cart ]
       │
       ├─ Representation ──► Formatted as JSON, XML, or HTML depending on consumer
       ├─ State          ──► Current data snapshot/properties (e.g., items, quantities, price)
       └─ Transfer       ──► Exchanged over HTTP methods (GET, POST, PUT, PATCH, DELETE)

```

1. **Representational:**
* Resources (entities/data objects) do not travel as raw database records; they travel as specific **representations**.
* The same resource can have different representations based on client requirements:
* Server-to-server or API client $\to$ `application/json`.
* Browser / UI client $\to$ rendered `HTML`.
* Legacy / enterprise integration $\to$ `XML`.




2. **State:**
* Refers to the current conditions, values, or attributes of a resource at a given point in time.
* *Example:* The state of an e-commerce shopping cart includes its item IDs, quantities, selected variants, and calculated total price.


3. **Transfer:**
* The actual movement/exchange of these resource representations and states between client and server via standardized HTTP verbs (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, etc.).

## 4. URL Anatomy & Route Design Guidelines

### Anatomy of a URL

* **Scheme:** `http://` or `https://` (production APIs should always enforce encrypted `https://`).
* **Authority / Domain:** e.g., `sky.xyz` or `example.com`.
* **Path / Resource:** e.g., `/books/harry-potter`.
* **Forward Slash (`/`):** Denotes a **hierarchical relationship** between resources (e.g., going from a parent collection to a specific entity or sub-resource).
* **Query Parameters:** Key-value pairs (`?sort=asc&limit=10`) used predominantly in `GET` requests for filtering, pagination, and sorting.
* **Fragments:** e.g., `#section-1` (client-side anchor navigation to scroll the viewport).

### API URL Best Practices

* **Subdomains & Versioning:** Industry standard practice separates API traffic using dedicated subdomains and explicit URI versioning:
```
https://api.example.com/v1/resources

```


* **Plural Nouns for Resources:**
* All resources in path segments must use **plural nouns**, regardless of whether the operation targets the entire collection or a single record.
* *Correct:* `GET /books` (list all books) and `GET /books/123` (get single book).
* *Anti-Pattern:* Switching to singular for individual records (`GET /book/123`). The resource type is still the collection of "books".


* **URL Formatting, Slugs & Casing:**
* **No spaces or underscores:** Never use spaces or `_` inside URI segments or slugs.
* **Kebab-case:** Always use lowercase with hyphens for multi-word paths or human-readable slugs.
* *Slug Example:* `"Harry Potter"` $\to$ convert to lowercase $\to$ replace space with hyphen $\to$ `/books/harry-potter`.
* *Reasoning:* URLs pass through diverse servers, network proxies, operating systems, and client runtimes; kebab-case avoids casing mismatches and URL-encoding bugs (like `%20`).

## 5. HTTP Methods & Idempotency

### What is Idempotency?

An operation is **idempotent** if performing it multiple times produces the exact same side-effect and outcome on the server state as performing it once.

> *Note:* Idempotency concerns **server-side state mutation**, not necessarily the returned response status code.

| HTTP Method | Idempotent? | Semantic Purpose | Typical Request Body | Expected Success Status Code |
| --- | --- | --- | --- | --- |
| **GET** | **Yes** | Retrieve data without altering server state. | None | `200 OK` |
| **PUT** | **Yes** | Completely replace an existing resource with the incoming payload. | Full resource representation | `200 OK` |
| **PATCH** | **Yes** | Partially update specific fields of an existing resource. | Partial field payload | `200 OK` |
| **DELETE** | **Yes** | Remove an existing resource from storage. | None | `204 No Content` |
| **POST** | **No** | Create a brand-new resource or execute an open-ended custom action. | Resource payload / action data | `201 Created` (creation) or `200 OK` (action) |

### In-Depth Method Analysis

#### `GET` (Idempotent)

* Merely retrieves information; produces zero side effects on the server.
* Even if external concurrent writes alter the data between successive reads, `GET` itself remains idempotent because the caller's action caused no state mutation.

#### `PUT` vs. `PATCH` (Both Idempotent)

* **`PUT` (Full Replacement):** The client sends every field representing the resource. Missing fields are overwritten or wiped.
* **`PATCH` (Partial Update):** The client sends only the specific attributes requiring modification (e.g., updating `{ "status": "active" }`).
* *Modern SPA Reality:* In JSON-heavy SPAs, partial updates are far more common than full replacements. Therefore, `PATCH` is the dominant real-world choice.
* *Why they are idempotent:* Setting field `name = "B"` changes the value from `"A"` to `"B"` on the first request. Repeating the request with `name = "B"` keeps the value as `"B"`. The resulting server state is identical.

#### `DELETE` (Idempotent)

* The first call deletes the record from the database.
* A subsequent call targeting the same ID finds the record gone, returning `404 Not Found`.
* It is still **idempotent** because the subsequent requests cause no additional side effects or mutations on the server—the resource remains deleted.

#### `POST` (Non-Idempotent & Open-Ended)

* **Creating Entities:** Calling `POST /books` repeatedly with the same payload creates multiple unique records with distinct database-generated IDs (UUIDs or serial keys). Server state changes with each invocation.
* **Custom Actions (Non-CRUD Operations):**
* Certain business operations do not cleanly map to basic CRUD (e.g., `send-email`, `archive`, `clone`).
* In the REST specification, **`POST` is intentionally open-ended** and serves as the standard fallback for executing arbitrary actions and operational workflows.

## 6. The API Design Lifecycle (Before Writing Code)

A critical principle of backend engineering: **APIs are designed first, not coded right away.**

```
Step 1: Wireframes / Figma (Understand end-user interaction with data)
         │
         ▼
Step 2: Resource Identification (Extract nouns: Organization, Project, Task)
         │
         ▼
Step 3: Database Schema Modeling (Tables, columns, relations)
         │
         ▼
Step 4: API Interface Design (Define routes, methods, payloads, status codes in Insomnia/Postman)
         │
         ▼
Step 5: Interactive Documentation & Review (Swagger / OpenAPI specifications)
         │
         ▼
Step 6: Backend Implementation (Writing server code in Go, Node.js, Python, etc.)

```

1. **Start with UI/UX Wireframes (Figma):** Understand how the human user interacts with the platform. This bridges the high-level user interface down to low-level database entities.
2. **Identify Resources as Nouns:** Scan wireframes, user stories, and feature requirements for nouns (e.g., for a Jira/Linear-like project management app: `Organization`, `Project`, `Task`, `User`, `Tag`).
3. **Database Schema Design:** Establish data tables, fields, constraints, and foreign key relationships.
4. **API Interface Design:** Before touching backend code, build and test endpoints using API design clients like **Insomnia** or **Postman**. Define the contract: routes, headers, body structures, and expected responses.

## 7. Comprehensive CRUD & Custom Action Walkthrough

*(Using a Project Management SAS with `Organization`, `Project`, and `Task` entities)*

### A. List Resources (with Pagination, Sorting & Filtering)

* **Route:** `GET /organizations`
* **Response Status:** `200 OK`
* **Crucial Rule on Empty Results:** If a query or filter matches zero records, **never return `404 Not Found**`. A 404 means the endpoint/resource route itself does not exist. For a list query yielding no results, return `200 OK` with an empty data array:
```json
{
  "data": [],
  "total": 0,
  "page": 1,
  "totalPages": 0
}

```



#### 1. Pagination Mechanics: Offset vs. Cursor (Keyset)

* **Why paginate?** Serializing/deserializing thousands of JSON records over the network degrades server performance, consumes bandwidth, and causes UI lag. Users only view a small subset at a time.

##### Approach 1: Offset Pagination (Page & Limit)
* **Query Parameters:** `page` (default 1), `limit` (default 10 or 20).
* **SQL Implementation:** `SELECT * FROM organizations ORDER BY created_at DESC LIMIT 10 OFFSET 20;`
* **Response Envelope:**
```json
{
  "data": [
    { "id": "org_5", "name": "Org 5", "status": "active" },
    { "id": "org_4", "name": "Org 4", "status": "active" }
  ],
  "total": 5000,
  "page": 3,
  "totalPages": 250
}
```
* **Critical Flaws of Offset Pagination:**
  1. **Performance Degrades at High Offsets ($O(N)$):** For `OFFSET 1000000 LIMIT 20`, the database must scan and discard 1,000,000 rows in memory before returning 20 rows!
  2. **Page Drift / Duplicate Records:** If a new row is added while a user navigates from Page 1 to Page 2, all existing rows shift down by one position, causing the user to see the last item of Page 1 repeated on Page 2.

##### Approach 2: Cursor-Based (Keyset) Pagination (Production Standard for Feeds)
* **How It Works:** Uses a pointer (an indexed unique identifier or timestamp) to fetch the next slice:
  - Request: `GET /organizations?cursor=org_5&limit=10`
  - SQL: `SELECT * FROM organizations WHERE id < 'org_5' ORDER BY id DESC LIMIT 10;`
* **Response Envelope:**
```json
{
  "data": [...],
  "nextCursor": "org_15",
  "hasMore": true
}
```
* **Advantages:** Constant $O(1)$ performance using B-Tree index seeks regardless of depth; completely immune to duplicate/skipped items during real-time writes. Ideal for infinite scrolling.



#### 2. Sorting Mechanics

* Databases do not guarantee record retrieval order unless an explicit `ORDER BY` is executed.
* **Query Parameters:**
* `sortBy` (attribute name: `name`, `createdAt`, `id`).
* `sortOrder` (`asc` or `desc`).


* **Sane Defaults:** If omitted, default to sorting by `createdAt` in `desc` order (newest records first).

#### 3. Filtering Mechanics

* Pass exact fields as query parameters:
* `GET /organizations?status=active`
* `GET /organizations?status=archived`
* `GET /organizations?name=Org4`



---

### B. Create Resource

* **Route:** `POST /organizations`
* **Request Body (JSON):**
* Do **not** accept server-managed fields from the client (`id`, `createdAt`, `updatedAt`).
* Only include client-provided business fields:
```json
{
  "name": "Org 1",
  "status": "active",
  "description": "Some description"
}

```




* **Response Status:** `201 Created`
* **Response Body:** Returns the newly persisted entity, populated with its generated server metadata:
```json
{
  "id": "uuid_generated_by_server",
  "name": "Org 1",
  "status": "active",
  "description": "Some description",
  "createdAt": "2026-11-02T06:06:00Z",
  "updatedAt": "2026-11-02T06:06:00Z"
}

```



---

### C. Get Single Resource

* **Route:** `GET /organizations/:id` (e.g., `GET /organizations/org_6`)
* **URL Structure:** Uses dynamic path parameters maintaining hierarchical depth: `/resources/:id`.
* **Success:** `200 OK` with the record object.
* **Failure (Record missing/deleted):** `404 Not Found` with an error message:
```json
{
  "error": "Organization not found"
}

```



---

### D. Update Single Resource (Partial Update)

* **Route:** `PATCH /organizations/:id`
* **Request Body (JSON):** Only the fields to be mutated:
```json
{
  "status": "active"
}

```


* **Response Status:** `200 OK`
* **Response Body:** Returns the complete, updated record reflecting the modified state.

---

### E. Delete Single Resource

* **Route:** `DELETE /organizations/:id`
* **Request Body:** None.
* **Response Status:** `204 No Content`
* **Response Body:** Empty. Indicates the server completed the deletion successfully and has no payload content to return.
* *Subsequent Requests:* Running `GET` or `DELETE` on the same ID immediately afterward yields `404 Not Found`.

---

### F. Custom Actions (Non-CRUD Operations)

Custom actions represent domain operations that trigger server-side side effects, cascades, or workflows beyond simple column mutations.

#### Example 1: Archiving an Organization

* *Why not just `PATCH` status to "archived"?* Archiving may require cascading deletions/updates across child projects and tasks, revoking user permissions, or triggering notification emails.
* **Endpoint Design:** Append the action name as a sub-path verb using `POST`:
```
POST /organizations/:id/archive

```


* **Response:** `200 OK` (returns the updated entity, since no *new* resource was created).

#### Example 2: Cloning a Project

* *Why not standard `POST /projects`?* The client could read the original project and attempt a create call, but the server must manage cloning all associated child tasks, resetting tracking states, and assigning ownership.
* **Endpoint Design:**
```
POST /projects/:id/clone

```


* **Response:** `201 Created` (because a complete duplicate project resource was created in the database).

## 8. Critical Rules for Professional API Design

1. **Provide Sane Defaults:**
* Never require clients to pass obvious, predictable parameters.
* *List APIs:* Default `page = 1`, `limit = 10`, `sortBy = createdAt`, `sortOrder = desc`.
* *Create APIs:* Default fields when intuitive (e.g., if `status` is omitted during organization creation, automatically default to `"active"`).


2. **Absolute Consistency Across Resources:**
* **Payload Keys:** If an organization defines a description field as `"description"`, never abbreviate it to `"desc"` in projects or tasks.
* **Case Convention:** Standard JSON fields (both incoming payloads and outbound responses) must strictly follow **`camelCase`**.
* **Route Plurality:** Keep path nouns plural across the entire API (`/organizations`, `/projects`, `/tasks`). Inconsistencies force client developers to constantly cross-reference documentation.


3. **Avoid Abbreviations:**
* Never shorten field names or parameters (use `description`, not `desc`; `organizationId`, not `orgId`). The backend engineer's internal domain knowledge should not be an assumed prerequisite for external API consumers.


4. **Maintain Hierarchical Resource Relationships:**
* Paths should naturally read like a tree: `/parentCollection/:parentId/action` or `/parentCollection/:parentId/childCollection`.


5. **Interactive Documentation (Swagger / OpenAPI):**
* High-quality backend engineers treat interactive API documentation (e.g., Swagger/OpenAPI UI) as a first-class deliverable.
* Provides consumer teams an interactive playground to inspect schemas, validate payloads, and test live calls without guess-and-check development.

## 9. The Richardson Maturity Model

Developed by Leonard Richardson, this model grades an API's adherence to RESTful constraints:

```
                          Level 3: Hypermedia Controls (HATEOAS)
                                       ▲
                                      / \
                         Level 2: HTTP Verbs & Status Codes
                                     ▲
                                    / \
                       Level 1: Individual Resources (URIs)
                                   ▲
                                  / \
                     Level 0: The Swamp of POX (Plain Old XML/JSON)
```

1. **Level 0 (The Swamp of POX):** Uses HTTP strictly as a transport tunnel. All requests hit a single URI (`POST /api`) with custom actions and parameters encoded in the body (e.g. SOAP, XML-RPC, basic JSON-RPC). HTTP verbs and status codes are ignored (always returns 200 OK).
2. **Level 1 (Resources):** Introduces distinct URIs for individual resources (`/users`, `/orders/123`), but continues using a single HTTP method (typically POST) for all interactions.
3. **Level 2 (HTTP Verbs & Status Codes):** Employs standard HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) according to their defined semantics and returns appropriate HTTP status codes (`200`, `201`, `204`, `400`, `404`, `500`). **This is where 95% of industry REST APIs operate.**
4. **Level 3 (Hypermedia Controls / HATEOAS):** *"Hypermedia As The Engine Of Application State"*. Responses include hypermedia links pointing to allowable subsequent actions:
```json
{
  "id": "ord_102",
  "status": "UNPAID",
  "total": 99.00,
  "_links": {
    "self": { "href": "/orders/ord_102" },
    "pay": { "href": "/orders/ord_102/payment", "method": "POST" },
    "cancel": { "href": "/orders/ord_102", "method": "DELETE" }
  }
}
```
Clients dynamically discover available workflow actions through the links returned in responses rather than hardcoding business state transitions.
