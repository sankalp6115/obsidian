# Error Handling & Building Fault-Tolerant Systems: Complete Notes

## 0. Core Mindset
- Errors are a normal part of backend development. The question is not *whether* they happen but *how you handle them*.
- Database queries fail, external APIs time out, users send bad data, and business logic hits edge cases.
- This video covers no tools, frameworks, or code, only a **fault-tolerant mindset**. You are responsible for core business logic and for every transaction and user activity going smoothly, so be ready to **detect, prevent, and fix** errors.
- Best practices apply whether you're at a startup, an enterprise, or an open-source project.

## 1. Types of Errors (5 types)

### A. Logic Errors
- The most dangerous and sneakiest type. They don't crash the app, they make it do the wrong thing: the code runs fine but the results are wrong or unexpected.
- **Example:** an e-commerce store applies a discount twice, giving negative shipping costs. The app doesn't crash, but the platform loses money on every order.
- They can go unnoticed for weeks or months if you aren't monitoring and users don't report them, so the loss grows every week.
- **Causes:**
  - **Misunderstanding requirements:** confusing client/PM discussions lead to wrong notes, the wrong feature gets built, and with little testing it reaches users.
  - **Incorrect algorithm implementation:** e.g., complex discount logic based on user behavior and purchase history, where one slight miscalculation causes losses.
  - **Not thinking about edge cases:** unexpected user behavior in payment or discount workflows.
- Especially dangerous around payments, money, and security. They can corrupt data and produce wrong business results over time without detection.

### B. Database Errors
Most backends rely heavily on the DB, so DB errors can bring the whole system down.

- **Connection errors:** the app can't talk to the DB.
  - Causes: network down, DB server overloaded, connection pool exhausted.
  - Result: 500 errors and empty frontend screens. The app can't function without its data source.
  - **Connection pooling:** the backend keeps several TCP connections to the DB open so it doesn't repeat the TCP handshake on every request. It's an optimization, but the pool itself can run out and cause errors.
- **Constraint violations:** operations that break DB rules.
  - **Unique constraint:** e.g., creating a user with an existing email. If unhandled, it bubbles up as a 500 instead of a friendly message.
  - **Foreign key violation:** e.g., inserting into `orders` with a `customer_id` that doesn't exist in `customers` (non-nullable FK).
  - Root cause is often a weak validation layer (both frontend and backend), so strengthen it.
  - Unique violations can't be fully prevented, since only the DB knows if a value is unique. Focus on **error formatting**, sending a user-friendly message like "this email already exists, try a different one."
- **Query errors:** malformed SQL, such as typos in table names (e.g., a mistyped `select * from customers`), or overly complex queries that time out.
- **Deadlocks:** multiple DB operations wait on each other in a circular dependency. Tricky to deal with.

### C. External Service Errors
- Modern SaaS apps depend on payment processors, email providers, cloud/object storage (S3), Redis, and auth providers (Auth0, Clerk).
- Each is a **point of failure you don't control**. You can't avoid dependencies (rebuilding complex systems from scratch isn't practical), so expect failures and plan fallbacks.
- **Reasons for failure:**
  1. **Network issues:** HTTP, TCP, or WebSocket connections all run over an imperfect internet. Expect connection timeouts, DNS failures, and network partitions (affected by routing).
  2. **Authentication errors:** external services reject requests due to bad credentials, expired tokens, or insufficient permissions.
     - Using an external auth provider doesn't make you automatically secure. Your own backend can still cause issues, e.g., exposing sensitive user info in logs.
  3. **Rate limiting:** services like OpenAI or Resend limit requests per time window to stop abuse by malicious users. Your platform can trigger it through heavy user activity or a logic error that hammers their API, and you then get **HTTP 429 (Too Many Requests)**.
     - **Strategy: exponential backoff.** On 429, wait 1 min, then 2, then 4, doubling until requests succeed. Expect this beforehand and implement it.
  4. **Service outages:** major providers (GCP, AWS services) go down from incidents or maintenance, and many clients go down with them. You can't control it.
     - Handle gracefully with **fallbacks**, e.g., if Redis goes down, use in-memory caching or a second Redis node, so critical functions like payments and order processing aren't affected.

### D. Input Validation Errors
- Caused by users sending data that doesn't meet system requirements. Validation is the **first line of defense** against bad or malicious input, applied at the backend's entry point.
- (The creator has a separate validation video in the playlist.)
- **Types of validation:**
  - **Format:** valid email, phone number, date, or custom data. Be clear about the exact format expected and accept **only** that format, for security and fault tolerance.
  - **Range:** max amount too high, min too low, string too long or short, array with fewer than 3 or more than 100 items.
  - **Required fields:** mandatory fields must be present.
- Typically returns **400 Bad Request**.
- These are the **easiest to expect and handle**, since you already know your data requirements. This contrasts with external dependencies (no control) and logic errors (hard to detect). Build a robust validation layer in every backend.

### E. Configuration Errors
- Can prevent the app from starting or make production behave unexpectedly. They typically appear when moving between **development, staging, and production**.
- **Example:** you add `OPENAI_API_KEY` to your `.env` locally, merge the PR, and forget to add it to the production environment variables (whether manual or via AWS Parameter Store, etc.).
- **Best case:** you validate all required config at startup, and the app fails to start.
  - Validate every required (non-optional) variable, from env vars or remote stores, **before the server starts**. If any is missing or corrupt, fail there.
  - With **blue-green deployments**, the old deployment keeps running until the new one starts successfully, so there's no downtime.
  - The failure message should be meaningful so the infrastructure operator can fix the config and restart.
- **Worst case:** no startup validation. The app starts, and when a user hits an API handler that uses the missing variable (e.g., an OpenAI image generation endpoint), it errors out with a 500 at runtime.
- **Rule:** always prefer crashing at startup over failing while serving real users.

## 2. Prevention: Proactive Error Detection
**Key principle: the best error handling starts *before* the error happens.** Find errors the moment they occur, before they do damage. This holds for frontend, backend, and infrastructure alike.

### Health Checks
- **Basic server health check:** expose an endpoint like `/health` or `/status`. The **response code** matters, not the body: **200** means running, **4xx/5xx** means something is wrong. External tools can keep pinging it.
- **Not enough on its own.** Also verify that services are actually *doing their job*:
  - **Database health checks:**
    - Connectivity
    - Query performance (a query that took 500ms and suddenly takes 4–5s signals a problem)
    - Data integrity
    - A simple ping isn't enough. Run a representative query and check the results, the time taken, and the average time.
  - **External service health checks:**
    - **Payment processors:** test transactions, so a successful test 5 minutes ago gives confidence for real ones
    - **Email services:** send test messages to internal addresses to verify delivery and connectivity
    - **Auth services:** generate test tokens and validate them against the provider's validation endpoints
  - **Core functionality checks:**
    - Configuration loaded properly (fail at startup with a meaningful message if not)
    - Necessary caches populated for production workloads
    - Internal data structures (config, external service state) consistent
- Together these form **proactive error detection**.

### Monitoring & Observability
(Covered in depth two videos later. This is only a high-level overview.)
- Detects errors quickly, **while they're happening**, and gives enough context to debug.
- **Don't just track error rates.** Also monitor **performance metrics**, since degradation is an early sign a service will soon fail.
- Cover many error sources: **HTTP errors, database errors, external service failures, business logic errors**.
- **Performance metrics:** response times, resource usage, throughput.
- **Business metrics:** e.g., a sudden drop in successful transactions or authentications can indicate a technical problem *even when error rates look normal*.
- **Logging best practices:**
  - Use **structured logging** (e.g., **JSON logs**), which is easily parsed and can carry extra metadata.
  - Use log aggregation tools like **Grafana / Loki** to parse logs, view error rates on visual dashboards, search, and store them externally.

## 3. Philosophies for Handling Errors

### A. Immediate Error Response
Your immediate response decides whether an error stays minor or becomes a major failure. The strategy depends on the error type and context.
- **Recoverable errors** (e.g., an email send failing at Resend, network errors, temporary resource shortages, running out of DB connections):
  - Sending an email isn't time-critical, so a delay is acceptable.
  - Use **retry mechanisms and exponential backoff**.
  - **Caution:** don't overwhelm an already-stressed system. Your retry/backoff logic must not add more stress.
- **Non-recoverable errors:**
  - Use **containment and graceful degradation**.
  - Examples: serve cached data, disable non-essential features, provide alternative functionality or fallbacks, and contain the scope of the damage.

### B. Error Recovery Strategies
Depends on the error's nature and the functionality's criticality.
- **Automatic recovery** (handles many errors without human intervention):
  - Automatically restart a failed or unresponsive service or process.
  - Clean up corrupted caches.
  - Switch to backup systems or fallback data.

#### The Circuit Breaker Pattern
When an external service (e.g. payment gateway or recommendation API) is down, continually sending thousands of requests exhausts server threads and deepens the outage.
- **Closed State (Normal):** Requests pass through. The circuit breaker counts failures.
- **Open State (Tripped):** If the failure rate crosses a threshold (e.g., 50% errors over 10 seconds), the circuit **trips Open**. All subsequent calls fail immediately (Fast-Fail) with a fallback or cached value **without even attempting the network call**.
- **Half-Open State (Probing):** After a reset timeout (e.g. 30 seconds), the circuit transitions to **Half-Open**, allowing a small percentage of trial requests through. If they succeed, the circuit resets to **Closed**; if they fail, it immediately trips back to **Open**.

```
                   The Circuit Breaker Lifecycle
                   ┌───────────────────────────┐
                   │       CLOSED STATE        │
                   │ (Normal Traffic Passes)   │
                   └─────────────┬─────────────┘
                                 │ Failure threshold breached
                                 ▼
                   ┌───────────────────────────┐
                   │        OPEN STATE         │
                   │ (Fails Fast Immediately)  │
                   └─────────────┬─────────────┘
                                 │ Sleep window elapses
                                 ▼
                   ┌───────────────────────────┐
     ┌─────────────┤      HALF-OPEN STATE      ├─────────────┐
     │ Probe fails │ (Test probe traffic sent) │ Probe passes│
     ▼             └───────────────────────────┘             ▼
[ Back to OPEN ]                                     [ Back to CLOSED ]
```

#### Exponential Backoff with Full Jitter
- **The Thundering Herd Problem:** If 1,000 client requests fail simultaneously and all retry after exactly $2^1 = 2\text{s}$, then $2^2 = 4\text{s}$, they create synchronized retry spikes that knock the recovering server down repeatedly.
- **Full Jitter Formula:**
  $$\text{Sleep} = \text{random}(0, \min(\text{MaxWait}, \text{BaseWait} \times 2^{\text{attempt}}))$$
- Adding randomized jitter distributes retries evenly across time, smoothing the load and allowing the downstream service to recover safely.

- **Manual recovery** (needs human judgment and decisions):
  - **Document** the processes (Runbooks / Playbooks) so all team members know what to do in an incident or service failure.
  - **Test** them in advance (chaos testing) so they work quickly under stress.
- **Data recovery strategies:**
  - Data is the most important part of the app. Code and services are replaceable, but data (users, transactions, orders) is the core asset.
  - **Data integrity is the #1 priority.** Never corrupt data.
  - Methods: automated snapshots, continuous Point-In-Time Recovery (PITR) via WAL replaying, and audited recovery runbooks.

### C. Propagation Control
- Not all errors should be handled exactly where they occur. Sometimes they should propagate to a higher level with more context (this is where **stack traces** come in).
- Intentionally bubble errors up to a primary or secondary process, and keep the whole bubbling workflow **under your control**. Otherwise errors can spread to other services or shut down the main service.
- **Exception handling hierarchies** (try/catch in JavaScript and Python) give the structure:
  - Catch low-level exceptions and **wrap them with enough context** (business context)
  - Bubble them up so you can log appropriate data, send a meaningful error to the frontend, or trigger a recovery strategy
- This is common in nearly all backend apps and is also called **global error handling**.

### D. Error Boundaries
- The last point where errors are stopped from propagating further. In service architectures they stop one service's errors from affecting others.
- Use **separate processes** rather than one shared process.
- Implement **timeouts** to protect service-level boundaries.
- Use **message queues (e.g., RabbitMQ)** for asynchronous communication, so a bug in one service doesn't cause another to fail.

### E. Global Error Handling: "The Final Safety Net"
The creator's favorite mechanism. You spend time on it once when setting up the platform, then only tweak it or add conditions. It's a one-time effort that pays off immediately and is the most important error handling strategy in a backend app.

**Typical backend architecture:**
1. **Routing layer:** decides which handler takes the request
2. **Handler:** extracts data from the payload, deserializes, validates, binds, then calls a service method
3. **Service:** an orchestrator that calls one or more repository methods
4. **Repository:** leaf nodes that do one thing, usually one DB query (e.g., `getUserById`). They're kept unit-level and limited to a single DB operation. The service decides which repository methods to call and how many (e.g., one service returns a user plus their posts by calling two).

**The pattern:**
- No matter which layer an error occurs in, **bubble it up to a global error handler middleware**. Middleware is used because it has access to all incoming requests and outgoing responses.
- In exception-based languages (JS, Python): **throw** and catch in the middleware.
- In languages like **Go**: keep **returning** the error from repository to service to handler until it reaches the middleware.
- Errors come from different layers: DB errors from repository, internal errors from service, validation errors from handler. Every language lets you create **custom errors**.
- The middleware reads the error, performs different operations depending on its type, and returns an appropriate response to the user.

**Worked example (book management platform):**

| Scenario | Layer | Error | Response |
|---|---|---|---|
| Create book, name is 700 chars (limit 500) | Handler (validation) | Validation error | **400** + validation messages/field errors so the user can fix data |
| Create book, name already exists | Repository (`insertNewBook`, Postgres) | Unique constraint violation | **400** "book already exists" (caused by user-sent data) |
| `GET /books/123`, book doesn't exist (`select * from books where id = 123`) | Repository | **"No rows"** error (common in relational DB drivers) | **404** "book with ID 123 does not exist" |
| Create book with non-existent `author_id` (FK to `authors`) | Repository | Foreign key violation | **404** "author ID doesn't exist" |

- Even for DB errors, there are different ways and message formats to deal with each kind.
- **HTTP error structure:** typically `code` (status code), `message`, and optional form-field errors (array of objects/dicts/JSON).

**Two major advantages:**
1. **More robust and secure:** you can't forget a condition in some layer. If a repository method forgets to handle a unique violation, the error is normally converted to a **500 Internal Server Error** ("something went wrong, try later") instead of a meaningful message. A central handler is the final safety net that catches all possible errors.
2. **Reduces redundancy:** without it, every repository method would need the same checks (unique violation? FK violation?) repeated, which increases code size and bugs.

## 4. Security in Error Handling

### A. Don't Leak Internal Details in Error Messages
- Be mindful of what leaves your backend. Leaked details can expose user info and harm users, which is **worse than compromising the platform itself** because it damages goodwill and market trust.
- DB errors can contain **table names, indexes, constraint names**. If your global handler passes the raw lower-layer message to the `message` field, malicious users can use it to craft more advanced attacks (e.g., more advanced SQL injection) and make your platform a target.
- Keep control of messages: understand the error type and its layer, and generate a user-appropriate message.
- **Default/fallback case:** return **500** with a generic message ("something went wrong" / "Internal Server Error"). Reaching the default means you've already checked validation, unique violation, business errors, etc. and don't know the cause, so the raw message likely contains internal details.

### B. Authentication Endpoints (Login)
- Auth is one of the **most targeted modules** for attackers. Follow security practices from resources like the **OWASP Cheat Sheet** (advice for authentication and other workflows).
- **Login flow:** take email and password, check if the user exists, then check the password.
- **Don't** return "user with this email doesn't exist" or "your password is incorrect." Return a generic **"Invalid email or password."**
- **Attack if you do:** an attacker tries many emails with one password and keeps getting "user doesn't exist." When they finally get "password is incorrect," they know that email is a real user. They then try common passwords against it and compromise the account.
- Weaknesses in error handling alone can compromise your platform and users.

### C. Logging Security
- Don't expose sensitive info (user emails, passwords, API keys, credit card numbers) in logs. Logs seem limited to your own infrastructure, but that's often not true.
- Big companies generate **hundreds of GBs of logs daily** and use multiple external services for storage, analysis, and observability. In major breaches, logs get leaked, and if they contain sensitive data it ends up with many malicious users.
- On errors (e.g., an auth error), log the **user ID instead of their email**, plus a **correlation ID** to keep enough context.

## Key Takeaways
1. Expect errors and build a fault-tolerant mindset.
2. Know the five error types: logic, database, external service, input validation, and configuration.
3. The best error handling starts **before** errors happen: health checks, monitoring (including performance and business metrics), and startup config validation.
4. Recoverable errors get retries with exponential backoff (without stressing the system). Non-recoverable errors get containment and graceful degradation.
5. Plan automatic recovery carefully, document and test manual recovery, and put data integrity first.
6. Control error propagation, wrap errors with context, and use error boundaries (separate processes, timeouts, message queues).
7. Centralize handling in a **global error handler middleware**, the final safety net, for robustness and less redundancy.
8. Never leak internal details in error messages, use generic login errors, and keep sensitive data out of logs.
