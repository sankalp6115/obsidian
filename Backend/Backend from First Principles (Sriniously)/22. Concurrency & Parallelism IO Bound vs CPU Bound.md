# 22. Concurrency & Parallelism: IO Bound vs. CPU Bound

## 1. Introduction: Concurrency vs. Parallelism

Although frequently conflated in everyday developer conversations, **Concurrency** and **Parallelism** represent fundamentally different concepts in computer science.

As Go co-designer Rob Pike famously stated:
> **"Concurrency is about *dealing with* lots of things at once. Parallelism is about *doing* lots of things at once."**

```
Concurrency (Single Core - Interleaved Execution)
Time ──▶
Core 0: [ Task A ] ──▶ [ Task B ] ──▶ [ Task A ] ──▶ [ Task C ] ──▶ [ Task B ]
        (Rapid context-switching creates the illusion of simultaneous progress)

Parallelism (Multi-Core - Simultaneous Execution)
Time ──▶
Core 0: [ Task A ────────────────────────────────────────── ]
Core 1: [ Task B ────────────────────────────────────────── ]
Core 2: [ Task C ────────────────────────────────────────── ]
        (Multiple computations execute physically at the exact same instant)
```

- **Concurrency:** A structural property of a program. It is the ability to decompose a problem into discrete, out-of-order execution units that can make progress independently. A concurrent program can run on a single CPU core via rapid context switching.
- **Parallelism:** An execution property of the underlying hardware. It is the simultaneous physical execution of multiple computational tasks across distinct physical CPU cores or execution units.

## 2. Workload Classification: I/O-Bound vs. CPU-Bound

Optimizing a backend requires identifying whether an operation is constrained by the processor or by external waiting.

```
┌───────────────────────────────────────┬───────────────────────────────────────┐
│          I/O-BOUND WORKLOADS          │          CPU-BOUND WORKLOADS          │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ • Database queries (PostgreSQL, MySQL)│ • Password hashing (Argon2id, bcrypt) │
│ • Network HTTP calls to external APIs │ • Image / video resizing & encoding   │
│ • Reading / writing files to disk     │ • Data compression (gzip, zstd)       │
│ • Waiting for incoming socket data    │ • Cryptographic encryption/decryption │
│ • CPU is idle 95%-99% of the time     │ • CPU is saturated at 100% capacity   │
│ • Solution: Async I/O, Event Loops    │ • Solution: Multi-core, Worker Threads│
└───────────────────────────────────────┴───────────────────────────────────────┘
```

### 2.1 I/O-Bound Operations
In typical web backends, the overwhelming majority of requests are **I/O-bound**. When your server queries a database for a user profile:
1. The server serializes a query string and sends it over a TCP socket.
2. The database executes the query (taking, say, 20ms–50ms).
3. During those 50ms, the backend server's CPU has zero work to do. It is purely waiting for network packets to arrive back on the socket.
- **Goal:** Never let an idle I/O wait block a CPU thread from processing other user requests.

### 2.2 CPU-Bound Operations
CPU-bound operations demand intensive mathematical or logic calculations directly on physical registers and ALU cores.
- **The Event Loop Trap:** Running CPU-intensive logic (like calculating 50,000 iterations of a crypto algorithm or parsing a 100MB JSON string) inside a single-threaded event loop (like Node.js) **freezes the entire server**. No other user can connect or receive responses until that calculation finishes.

## 3. Concurrency Models in Backend Runtimes

Backend architectures handle concurrency through three dominant models:

```
                          Three Major Concurrency Models
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
[ Thread-per-Request ]        [ Single-Thread Event Loop ]      [ M:N Virtual Threads ]
• Traditional Java / Puma     • Node.js (libuv), Python asyncio • Go (Goroutines), Java 21 Loom
• 1 OS thread per request     • Non-blocking kernel polling     • Lightweight user-space threads
• Blocks thread during I/O    • epoll / kqueue / IOCP           • Multiplexed over small OS pool
• High memory per thread      • Zero blocking on main thread    • Tiny 2KB initial call stacks
```

### 3.1 Model 1: Thread-per-Request (Traditional Multithreading)
- **Implementations:** Classic Java Servlet containers (Tomcat), Ruby on Rails (Puma), Apache HTTP Server, Python WSGI.
- **How It Works:** A fixed pool of Operating System (OS) threads is maintained. When a client connects, the thread pool assigns one dedicated OS thread to handle that request from start to finish.
- **The Trade-Offs:**
  - **Simplicity:** Code is written sequentially and synchronously (`data = queryDB(); print(data);`).
  - **Memory Overhead:** Each OS thread allocates a fixed stack size in memory (typically **1MB to 8MB** in Linux). Allocating 5,000 concurrent threads consumes 10GB–40GB of RAM purely for thread stacks.
  - **Context Switching Cost:** When thousands of OS threads compete for 8 physical cores, the CPU kernel spends excessive clock cycles saving/restoring CPU registers and invalidating L1/L2 hardware caches rather than executing application code.

### 3.2 Model 2: Single-Threaded Event Loop with Non-Blocking I/O
- **Implementations:** Node.js (powered by `libuv`), Python (`asyncio`), Nginx, Redis.
- **How It Works:** A single main thread executes all application logic. When an I/O operation (database query, network fetch) begins, the runtime registers the underlying file descriptor with the operating system’s asynchronous event notification facility:
  - **Linux:** `epoll`
  - **macOS / BSD:** `kqueue`
  - **Windows:** `IOCP` (I/O Completion Ports)
- The main thread does **not wait**. It immediately returns to the event loop to pick up the next incoming HTTP request.
- When the OS kernel signals that the network packet has arrived, the event loop queues the associated callback / promise continuation for execution.

```
                        The Event Loop Architecture
                                     │
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
             Call Stack (JS)                  Kernel Polling
          [ Sync Logic Runs ] ──▶ I/O Call ──▶ [ epoll / kqueue ]
                    ▲                                 │ Socket data ready
                    │                                 ▼
                    └─────── [ Task / Microtask Queue ]
```

> [!WARNING]
> **The Golden Event Loop Rule:** *"Never block the event loop!"* Never execute heavy synchronous loops, massive JSON parses, or blocking disk I/O on the main thread. Offload CPU-heavy tasks to worker threads or external worker pools.

### 3.3 Model 3: Coroutines / Goroutines / Virtual Threads ($M:N$ Scheduler)
- **Implementations:** Go (`goroutines`), Java 21+ (`Project Loom Virtual Threads`), Erlang/Elixir (`BEAM processes`).
- **How It Works:** Decouples user-space threads from kernel OS threads using an **$M:N$ Scheduler**:
  - $M$ user-space lightweight green threads are multiplexed onto $N$ physical OS kernel threads (where $N \approx \text{number of CPU cores}$).
  - A goroutine starts with an ultra-lightweight stack of **only ~2 KB** (growing and shrinking dynamically).
  - A single machine can easily run **500,000+ concurrent goroutines** without memory exhaustion.
- **Cooperative Scheduling:** When a goroutine makes an I/O call or awaits a channel, the Go runtime scheduler parks that goroutine and seamlessly swaps another runnable goroutine onto the physical OS thread—entirely in user space, with zero kernel context-switching penalty.

## 4. Evolution of Asynchronous Syntax

Handling non-blocking asynchronous operations has evolved through three distinct paradigms:

### 4.1 Callbacks & "Callback Hell"
Early asynchronous programming relied on passing callback functions:
```javascript
// ❌ Callback Hell (Pyramid of Doom)
getUser(userId, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);
    calculateDiscount(orders, (err, discount) => {
      if (err) return handleError(err);
      // Hard to read, brutal error handling
    });
  });
});
```

### 4.2 Promises
Introduced standardized state containers (`Pending`, `Fulfilled`, `Rejected`) enabling clean chaining:
```javascript
getUser(userId)
  .then(user => getOrders(user.id))
  .then(orders => calculateDiscount(orders))
  .catch(err => handleError(err));
```

### 4.3 Async / Await
Syntactic sugar over Promises and Generators, allowing developers to write asynchronous non-blocking code that reads with the linear clarity of synchronous code:
```typescript
try {
  const user = await getUser(userId);
  const orders = await getOrders(user.id);
  const discount = await calculateDiscount(orders);
} catch (err) {
  handleError(err);
}
```

## 5. The Perils of Concurrency: Shared Memory & Race Conditions

Why is concurrent programming notoriously challenging? **Shared Mutable State.**

When multiple threads or coroutines read and modify the exact same memory address concurrently without synchronization, non-deterministic bugs arise.

```
                    The Classic Bank Account Race Condition
                Initial Shared Balance in Memory: $150.00
                Two concurrent withdrawals of $100.00 each:

      Thread 1 (Withdraw $100)                     Thread 2 (Withdraw $100)
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│ 1. Read balance: $150                │     │                                      │
│ 2. Check: 150 >= 100 (Passes)        │     │                                      │
│ ──▶ [ Context Switch to Thread 2 ]   │     │                                      │
│                                      │     │ 1. Read balance: $150                │
│                                      │     │ 2. Check: 150 >= 100 (Passes)        │
│                                      │     │ 3. New Balance = $150 - $100 = $50   │
│                                      │     │ 4. Write back balance: $50           │
│ ──▶ [ Context Switch to Thread 1 ]   │     │                                      │
│ 3. New Balance = $150 - $100 = $50   │     │                                      │
│ 4. Write back balance: $50           │     │                                      │
└──────────────────────────────────────┘     └──────────────────────────────────────┘
                  Final Balance: $50 (User withdrew $200 from a $150 account!)
```

### Synchronization Remedies

#### 1. Mutexes (Mutual Exclusion Locks)
A Mutex ensures that only one execution context can enter a critical section at any given moment:
```go
var mu sync.Mutex
var balance = 150

func withdraw(amount int) bool {
    mu.Lock()
    defer mu.Unlock() // Guarantees release even on panic
    
    if balance >= amount {
        balance -= amount
        return true
    }
    return false
}
```

> [!CAUTION]
> **Deadlocks:** If Thread A locks Mutex 1 and waits for Mutex 2, while Thread B locks Mutex 2 and waits for Mutex 1, both threads block forever (**Deadlock**). Always acquire locks in a globally consistent order or use timeout-based lock acquisition.

#### 2. Atomic Operations
Hardware-level atomic CPU instructions (e.g., Compare-And-Swap / CAS) that update numerical values in memory in a single clock cycle without software locks.

#### 3. Communicating Sequential Processes (CSP & Channels)
Instead of locking shared memory addresses, processes pass ownership of data via typed channels:
> *"Do not communicate by sharing memory; instead, share memory by communicating."*

#### 4. Database-Level Locking (Pessimistic vs. Optimistic)
- **Pessimistic Locking (`SELECT ... FOR UPDATE`):** Locks the row in PostgreSQL until the transaction commits. Prevents any other transaction from reading or modifying it.
- **Optimistic Locking:** Adds a `version` column. On update: `UPDATE accounts SET balance = $1, version = version + 1 WHERE id = $2 AND version = $3`. If another transaction updated the row first, the version mismatch aborts the query, allowing the application to retry.

## 6. Key Takeaways Summary

- **Concurrency is composition; parallelism is simultaneous execution.**
- **Identify your bottleneck:** Web backends are typically 95% I/O-bound (waiting on DB, network, disks).
- **Single-threaded event loops** achieve massive I/O concurrency via non-blocking OS notification APIs (`epoll`, `kqueue`), but **must never be blocked with CPU-heavy computations**.
- **User-space Virtual Threads (Goroutines / Loom)** deliver the readability of synchronous code with the scalability of non-blocking I/O ($M:N$ scheduling).
- **Beware of shared mutable state:** Prevent race conditions using Mutexes, Atomic operations, CSP message channels, or database locks (`SELECT FOR UPDATE` / Optimistic versioning).
