# 26. Testing for Backend Engineers: Mocks, TDD, and Coverage

## 1. Introduction: Why Testing is a Core Backend Engineering Skill

In backend engineering, tests are not written to satisfy arbitrary administrative metrics or vanity coverage reports. **Tests are an automated safety harness** that empowers engineers to:
- Refactor complex architectures with zero fear of introducing silent regressions.
- Provide executable, living documentation of system requirements.
- Accelerate development velocity by catching defects minutes after writing code, rather than weeks later in production.

---

## 2. The Testing Pyramid: Sizing and Strategy

Originally formulated by Mike Cohn, the **Testing Pyramid** governs the healthy distribution of tests in a production backend:

```
                                  The Testing Pyramid
                                         ▲
                                        / \
                                       /   \
                                      / E2E \       ◀── Few (Slow, Flaky, Expensive)
                                     /───────\
                                    / Integr- \     ◀── Moderate (Real DB, Services)
                                   /  ation    \
                                  /─────────────\
                                 /     Unit      \  ◀── Many (Fast, Isolated, Cheap)
                                /─────────────────\
```

| Test Level | Scope | Speed & Execution | Cost & Maintenance | Primary Target |
| :--- | :--- | :--- | :--- | :--- |
| **Unit Tests** | Isolated pure functions, domain rules, calculation logic | **Milliseconds** (thousands run in seconds) | Minimal cost; rarely brittle | Business calculations, validations, parsers, state machines |
| **Integration Tests** | Handlers $\leftrightarrow$ Services $\leftrightarrow$ Database/Cache layers | **Seconds** (Docker containers, DB queries) | Moderate cost; tests wire glue | Repositories, SQL queries, cache sync, middleware pipelines |
| **End-to-End (E2E)** | Full deployment stack from HTTP ingress to DB | **Minutes** | High maintenance; prone to network flakiness | Critical user paths (User registration, Stripe checkout flow) |

## 3. Test Doubles: Demystifying Mocks, Stubs, Fakes, and Spies

Engineers frequently misuse the word "mock" as a catch-all term for any simulated dependency. In standard software engineering taxonomy (Gerard Meszaros), **Test Doubles** comprise five distinct types:

```
                            Taxonomy of Test Doubles
                                       │
        ┌──────────────┬───────────────┼───────────────┬──────────────┐
        ▼              ▼               ▼               ▼              ▼
     [ Dummy ]      [ Stub ]        [ Spy ]         [ Mock ]       [ Fake ]
    Passed but    Returns canned   Records calls   Pre-programmed Working shortcut
    never used    fixed values    & invocation    expectations;   (e.g., In-Memory
                                  parameters      verifies calls  SQLite / Redis)
```

### 3.1 Detailed Definitions & Code Scenarios

#### 1. Dummy
Objects passed into a constructor or method simply to satisfy type signatures, but never actually invoked or inspected during the test:
```typescript
const dummyLogger: Logger = { info: () => {}, error: () => {} };
const authService = new AuthService(userRepo, dummyLogger);
```

#### 2. Stub
Provides hardcoded, canned responses to method calls made during test execution:
```typescript
// Stubbing a user repository to always return an active user
const userRepoStub = {
  findById: async (id: string) => ({ id, name: "Alice", status: "ACTIVE" })
};
```

#### 3. Spy
A stub that secretly records operational metadata about how it was called (e.g., number of invocations, arguments passed):
```typescript
// Inspecting whether an email service was called with the correct recipient
const emailSpy = {
  sentEmails: [] as string[],
  sendWelcomeEmail: async (email: string) => { emailSpy.sentEmails.push(email); }
};
// Assertion:
expect(emailSpy.sentEmails).toContain("alice@example.com");
```

#### 4. Mock
An object configured with strict **behavioral expectations** before the test runs, and evaluated via **interaction verification**:
```typescript
// Expecting that userRepo.delete() must be called exactly once with ID 'usr_123'
const mockUserRepo = jest.mock();
mockUserRepo.expects('delete').once().withExactArgs('usr_123');
await userService.deleteAccount('usr_123');
mockUserRepo.verify();
```

#### 5. Fake
A genuine, working implementation of a dependency that takes programmatic shortcuts making it unsuitable for production:
- **Examples:** Using an **In-Memory SQLite** database or **In-Memory Hash Map** to replace PostgreSQL or Redis during testing. Fakes run at in-memory CPU speeds without requiring external network daemons.

## 4. State Verification vs. Interaction Verification & The Over-Mocking Trap

```
┌───────────────────────────────────────┬───────────────────────────────────────┐
│          STATE VERIFICATION           │       INTERACTION VERIFICATION        │
├───────────────────────────────────────┼───────────────────────────────────────┤
│ • Asserts outputs, return values, or  │ • Asserts that specific internal      │
│   persisted changes in state.         │   methods were called with parameters.│
│ • Example: `expect(order.status)      │ • Example: `expect(repo.save)         │
│   .toBe('PAID')`                      │   .toHaveBeenCalledTimes(1)`          │
│ • Resilient to refactoring            │ • Extremely brittle; couples tests to │
│ • Tests WHAT the system does          │   internal implementation details     │
└───────────────────────────────────────┴───────────────────────────────────────┘
```

> [!WARNING]
> **The Over-Mocking Anti-Pattern:** When tests heavily mock every internal service, collaborator, and repository method, they cease testing real behavior and instead test **how the code was written today**. If you refactor a private function or alter an internal helper without changing external behavior, all your mock tests explode.
> 
> **Rule of Thumb:** Default to **State Verification**. Use interaction verification and mocks sparingly, primarily for external system boundaries (e.g., sending money via Stripe, firing SMS via Twilio).

## 5. Hermetic Integration Testing & Database Isolation

A test suite is **Hermetic** when it is completely self-contained, isolated, and runs reliably anywhere (on a developer's disconnected laptop, in a Docker container, or in CI) without relying on shared external test environments.

### 5.1 Real Databases vs. In-Memory Fakes
While in-memory SQLite is fast, it does not support PostgreSQL-specific features: JSONB operators, CTEs, window functions, custom enum types, or row-level locking (`FOR UPDATE`). Testing against SQLite often gives false confidence.

### 5.2 The Two Clean Database Integration Patterns
1. **Ephemeral Containers (Testcontainers):**
   - The test runner automatically boots an ephemeral PostgreSQL Docker container via the Testcontainers library.
   - Runs database migrations once at test suite initialization.
2. **Transaction Rollback Pattern (Per-Test Isolation):**
   - Every individual test starts an explicit database transaction (`BEGIN`).
   - The test executes real `INSERT`, `UPDATE`, and `SELECT` queries against the real PostgreSQL container.
   - Upon test teardown, the test runner issues an unconditional **`ROLLBACK`**.
   - The database remains 100% clean for the next test without requiring expensive table truncations or re-running migrations.

## 6. Test-Driven Development (TDD): The Red-Green-Refactor Cycle

TDD is a software development discipline where tests are written **before** implementation code.

```
                         The TDD Feedback Loop
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
         1. [ RED ]                                2. [ GREEN ]
    Write a failing test                      Write the minimal code
    defining desired behavior                 to make the test pass
              ▲                                         │
              │                                         ▼
              └──────────────── 3. [ REFACTOR ] ────────┘
                             Clean code, eliminate
                             duplication, optimize
```

### 6.1 The Three Phases
1. **Red:** Write a concise unit test for a single requirement before the production function exists. Watch the test fail.
2. **Green:** Write the fastest, simplest code possible to make the test pass—even if it hardcodes return values or violates clean code principles.
3. **Refactor:** Now that the test is green, refactor the implementation: extract clean functions, improve naming, optimize algorithmic complexity. The passing test guarantees zero regressions.

### 6.2 When TDD Shines vs. When It Stumbles
- **Where TDD is Exceptional:** Core business calculation engines, input validation rules, custom serialization parsers, finite state machines, and payment logic.
- **Where TDD is Inefficient:** Exploratory architectural spikes, rapidly evolving UI layouts, and early prototypes where data schemas are actively changing.

## 7. Code Coverage Fallacies & Cyclomatic Complexity

### 7.1 The Myth of 100% Line Coverage
> [!CAUTION]
> **High line coverage does not equal high software quality.** It only indicates that a line was executed by the runtime; it does not prove that edge cases, boundary conditions, or null pointers were tested.

```typescript
// 100% Line Coverage, 0% Real Reliability!
function divide(a: number, b: number): number {
  return a / b;
}

// Test:
test('divides numbers', () => {
  expect(divide(10, 2)).toBe(5); // Executes 100% of the function's lines!
});
// What happens when b = 0? Unchecked division by zero!
```

**Production Coverage Standard:**
- Prioritize **Branch Coverage** over Line Coverage.
- Target ~80%–85% branch coverage on core domain services.
- Remember: **"What is NOT covered in your coverage report is vastly more important than what is covered."**

### 7.2 Cyclomatic Complexity (McCabe Complexity)
- Formulated by Thomas McCabe, **Cyclomatic Complexity** quantifies the number of linearly independent paths through a function's source code (driven by `if`, `else`, `switch`, `for`, `while`, `&&`, `||`).
- **The Metric:**
  - $\text{Complexity} \le 10$: Simple, easy to test, low defect risk.
  - $\text{Complexity} > 15$: Difficult to test thoroughly; exponential branch combinations; high defect risk.
- Use static analysis tools (linters, SonarQube) in CI/CD to block pull requests introducing functions with excessive cyclomatic complexity.

## 8. When to Delete Tests

Tests are not free assets; **every test is liability code that must be maintained**:
- If a test tests private implementation details and breaks on every refactor $\rightarrow$ **Delete it.**
- If multiple unit tests test the identical branch covered by a comprehensive integration test $\rightarrow$ **Consolidate or delete.**
- If a test is intermittently flaky and cannot be stabilized $\rightarrow$ **Fix immediately or delete.** A flaky test ruins team confidence in the entire CI/CD pipeline.

---

## 9. Key Takeaways Summary

- **Structure test suites according to the Testing Pyramid:** Rely heavily on fast unit tests, anchor them with hermetic integration tests, and cap them with minimal E2E tests.
- **Know your Test Doubles:** Differentiate between Dummies, Stubs, Spies, Mocks, and Fakes.
- **Prefer State Verification over Interaction Verification** to prevent brittle, over-mocked tests.
- **Use real databases (via Testcontainers) with Transaction Rollbacks** for fast, reliable repository testing.
- **Practice TDD (Red-Green-Refactor)** on deterministic business logic and state machines.
- **Treat 100% coverage as a vanity metric:** Focus on high branch coverage on business rules and keep cyclomatic complexity under 10.
