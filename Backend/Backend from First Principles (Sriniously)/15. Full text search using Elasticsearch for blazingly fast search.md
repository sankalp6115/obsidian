# Full-Text Search Using Elasticsearch

---

## 1. The Scaling Problem of Relational Search (2005 Scenario)

### The Initial Setup

In a small-to-medium application (e.g., an early e-commerce platform with ~5,000 products), product search is typically implemented in a relational database (PostgreSQL/MySQL) using standard pattern matching:

```sql
SELECT * FROM products 
WHERE name ILIKE '%laptop%' 
   OR description ILIKE '%laptop%';

```

* **`ILIKE`:** Performs a case-insensitive match.
* **`%` Wildcards:** Match arbitrary leading and trailing character sequences.
* **Initial Performance:** Returns results in ~50 milliseconds across small datasets.

---

### The Breakdown at Scale

As product catalogs scale from thousands to millions of rows, relational wildcard queries break down:

```
Catalog: 5,000 Products ────► ~50 ms Latency (Acceptable)
Catalog: Millions of Products ──► ~30 seconds Latency (Unusable)

```

#### Why Wildcard SQL Queries Break Down

1. **Full Table Scans:** Leading wildcards (`%laptop%`) invalidate standard B-Tree indexes. The database engine must scan every row on disk sequentially, reading text character-by-character.
2. **High Latency:** Response times balloon from tens of milliseconds to 30+ seconds. In modern web applications, even a 2-second delay causes user drop-off and conversion losses.
3. **No Semantic Relevance:** Results return in arbitrary physical or sequential order. A product merely mentioning `"laptop"` on page 100 of its manual ranks equally with a product titled `"Laptop"`.
4. **Zero Typo Tolerance:** Searching for `"lptop"` yields zero records because wildcard matching requires exact substring correspondence.

## 2. The Librarian Analogy: Relational Database vs. Inverted Index

```
Relational Database (Sequential Shelf Walk):
[ Book 1: Harry Potter ] ──► Scan all pages ──► No match
[ Book 2: Game of Thrones ] ─► Scan all pages ──► No match
[ Book 3: Intro to ML ] ────► Scan all pages ──► Match found (Slow, unordered)

Inverted Index (Back-of-the-Book Index Walk):
Term: "machine"  ──► [Intro to ML (p.1, 15, 23), The Machine Age (p.5, 89), Coffee Manual (p.1)]
Term: "learning" ──► [Intro to ML (p.1, 16, 24), Learning to Cook (p.2), Deep Learning (p.1)]
                     ▲
                     └─ Direct lookup: Instantly intersects matching document IDs!

```

* **Relational Database as a Librarian:**
* To locate a topic, the librarian walks shelf by shelf, reading every book title and page sequentially.
* *Fatal Flaw:* It takes minutes or days to evaluate 10 million books, and results return in arbitrary order without relevance scoring (e.g., placing an irrelevant book with an offhand mention on the last page ahead of an introductory textbook).


* **Inverted Index Alternative:**
* Instead of inspecting documents to discover terms, **the mapping is inverted**: an index maps every unique word (term) to the exact list of documents (and page positions) containing it.
* When a user queries `"machine learning"`, the engine looks up `"machine"` and `"learning"` in the inverted index, intersects their document posting lists, and retrieves matching records in milliseconds.

## 3. Core Architecture: Apache Lucene & Elasticsearch

```
┌────────────────────────────────────────────────────────┐
│                     Elasticsearch                      │
│   (Distributed RESTful JSON DSL, Clustering, Scaling)  │
├────────────────────────────────────────────────────────┤
│                     Apache Lucene                      │
│         (Underlying Inverted Index Core Engine)        │
└────────────────────────────────────────────────────────┘

```

* **Apache Lucene:** An open-source, high-performance information retrieval software library developed from decades of text-search research (dating back to the 1960s). It provides the underlying inverted index and indexing data structures.
* **Elasticsearch:** A distributed, JSON-based search and analytics engine built directly on top of Apache Lucene. It wraps Lucene with horizontal clustering, sharding, replication, and a JSON-based Domain Specific Language (DSL).
* **Document Model:** Similar to MongoDB, Elasticsearch stores data entities as JSON **documents**.
* **Distributed Sharding & Clustering:**
  - An Elasticsearch index is horizontally partitioned into **Primary Shards**.
  - Each primary shard has one or more **Replica Shards** distributed across different cluster nodes.
  - Primary shards handle write operations and partition the dataset across machines; replica shards provide high-availability failover and multiply read search throughput.
* **The Text Analysis Pipeline (Analyzers):**
  Before text is stored in an Inverted Index, it passes through an **Analyzer** composed of three stages:
  1. **Character Filters:** Preprocesses the raw string (e.g., stripping HTML tags: `<b>Kubernetes</b>` $\rightarrow$ `Kubernetes`, mapping `&` $\rightarrow$ `and`).
  2. **Tokenizer:** Splits the string into discrete tokens/words based on whitespace and punctuation boundaries.
  3. **Token Filters:** Modifies, adds, or removes tokens:
     - **Lowercase Filter:** Converts all tokens to lowercase (`"Docker"` $\rightarrow$ `"docker"`), ensuring searches are case-insensitive.
     - **Stop Words Filter:** Removes high-frequency grammatical words carrying zero search value (`"the"`, `"is"`, `"at"`, `"and"`).
     - **Stemming Filter (Porter Stemmer):** Reduces inflected words to their root linguistic base (`"running"`, `"runs"`, `"ran"` $\rightarrow$ `"run"`). Searching for "run" will now match documents containing "running"!

## 4. Relevance Scoring & The BM25 Algorithm

Elasticsearch ranks results by calculating relevance scores rather than returning arbitrary rows. Its default ranking algorithm is **Okapi BM25**.

### Key Factors in Relevance Scoring

1. **Term Frequency (TF):** Measures how frequently a search term appears within a specific document. More occurrences generally indicate greater topical relevance.
2. **Inverse Document Frequency (IDF):** Measures how common or rare a term is across the entire corpus. Rare terms carry more statistical weight than ubiquitous words.
3. **Document Length Normalization:** Accounts for document size. A term appearing three times in a concise 50-word product description represents a higher topical concentration than three occurrences in a 500-page manual.
4. **Field Boosting:** Allows engineers to weight specific fields during search:

$$\text{Weight}(\text{title}) > \text{Weight}(\text{description}) > \text{Weight}(\text{content})$$


* Matching a query term inside a `title` field imparts a substantially higher relevance score than finding it buried in `description` or body text.
* Field boost multipliers are fully customizable in Elasticsearch JSON search queries.



---

## 5. Typo Tolerance & Typeahead Search

* **Typeahead (Search-as-you-type):** Suggests matching products, phrases, or entities incrementally with each keystroke as the user types.
* **Typo Tolerance (Fuzzy Matching):** Matches intended terms even when users introduce typing mistakes (e.g., querying `"what is treading today"` correctly surfaces documents matching `"what is trending today"`).
* Relational wildcards (`%treading%`) fail completely on typos; full-text search engines use string edit-distance metrics (e.g., Levenshtein distance) over the inverted index to correct inputs seamlessly.

## 6. The ELK Stack (Log Management)

Elasticsearch is widely used for full-text search as well as centralized logging and observability via the **ELK Stack**:

```
[ Application Logs ] ──► Logstash (Ingestion & Parsing) ──► Elasticsearch (Indexing & Search) ──► Kibana (Visualization UI)

```

* **Elasticsearch:** Indexes high-volume, timestamped log documents for full-text retrieval and aggregations.
* **Logstash:** Server-side data processing pipeline that ingests, parses, and normalizes log events.
* **Kibana:** Web-based visualization UI used to query logs, track system metrics, and monitor application health.
* **Strategic Advice:** If an engineering organization already runs an ELK stack for infrastructure logging, leveraging that existing cluster for application full-text search is often more efficient than introducing new search infrastructure.

## 7. Practical Benchmark: PostgreSQL vs. Elasticsearch

A side-by-side benchmark demonstrates the performance difference between relational `ILIKE` searches and full-text index queries over identical datasets.

### Experimental Setup

* **Dataset:** 50,000 real-world customer review records in a CSV file with two primary columns:
* `review` (long text)
* `sentiment` (`positive` / `negative`)


* **Infrastructure:**
* **PostgreSQL:** Cloud-hosted serverless PostgreSQL instance (Neon) in `US-West`.
* **Elasticsearch:** Managed Elastic Cloud cluster in `US-West` (both co-located to minimize network distance bias).


* **Ingestion Script (Node.js):**
* Populates the PostgreSQL `reviews` table in chunks of 1,000 records.
* Ingests documents into Elasticsearch via bulk insert.



### Elasticsearch Field Mapping

```json
{
  "mappings": {
    "properties": {
      "review": { "type": "text" },
      "sentiment": { "type": "keyword" }
    }
  }
}

```

* **`text` Type:** Analyzed, tokenized, and parsed into inverted index structures for fuzzy, full-text search.
* **`keyword` Type:** Preserved as an unanalyzed, exact string; optimized for strict filtering, exact matching, sorting, and aggregations.

### Query Implementation Comparison

#### PostgreSQL Search Query

```sql
SELECT id, review, sentiment 
FROM reviews 
WHERE review ILIKE '%laptop%';

```

#### Elasticsearch Query (JSON DSL)

```json
{
  "query": {
    "query_string": {
      "query": "*laptop*",
      "fields": ["review"]
    }
  }
}

```

### Observed Benchmark Metrics

| Query Target | Result Count | Elasticsearch Response Latency | PostgreSQL (`ILIKE`) Latency | Performance Delta |
| --- | --- | --- | --- | --- |
| `"laptop"` | Small set | **~1,000 ms (1.0 s)** | ~3,000 to 4,000 ms (3.0–4.0 s) | Elasticsearch is **3–4x faster** |
| `"something"` | ~8,000 matching rows | **~500 ms (0.5 s)** | ~7,500 ms (7.5 s) | Elasticsearch is **15x faster** |

*Even with wildcards applied, Elasticsearch's inverted index retrieves thousands of matches in ~500 ms, while PostgreSQL's full table scan spikes to ~7.5 seconds on just 50,000 rows.*

## 8. Backend Engineering Mindset & Takeaways

1. **Databases vs. Search Engines Priority:**
* **Relational Databases (PostgreSQL):** The operational backbone covering 90–99% of typical backend application needs. Engineers must deeply understand schema design, indexing, ACID transactions, and query plans.
* **Full-Text Search (Elasticsearch):** A specialized tool. You do not need to rewrite search engines from scratch or master every internal heuristic. Learning how to configure indexes, define mappings, use the query DSL, and apply boosting rules is sufficient for the vast majority of production use cases.


2. **When to Choose Full-Text Search:**
* Heavy text catalogs requiring sub-second search latency.
* Need for fuzzy matching, typeahead completion, and typo tolerance.
* Requirement for relevance-based ranking (e.g., BM25) over simple binary matches.
