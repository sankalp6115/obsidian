# 23. Object Storage: Everything You Need to Know (Part 1)

## 1. Introduction: Why Do Backends Need Object Storage?

Every production backend inevitably handles unstructured files: user avatars, PDF invoices, CSV data exports, audio files, video uploads, and system backups.

However, standard storage approaches fail at scale:

### 1.1 Why NOT Store Files on Local Server Disks?
- **Ephemeral Infrastructure:** In cloud environments (Docker, Kubernetes, AWS ECS/EC2), containers and virtual machines are disposable. When a pod restarts, deploys, or reschedules to another physical host, **the local disk is erased**.
- **Horizontal Scaling Mismatch:** A user uploads a profile photo that hits Server A. On the next request, the load balancer routes the user to Server B. Server B checks its local filesystem, cannot find the file, and returns `404 Not Found`.
- **Local Disk Exhaustion:** User uploads can easily consume hundreds of gigabytes, filling the OS root disk and crashing the entire server.

### 1.2 Why NOT Store Files Directly in Relational Databases (BLOBs)?
- **Database Bloat:** Storing multi-megabyte files inside `BYTEA` or `BLOB` columns dramatically increases database size and pollutes the database engine's shared memory buffer pools.
- **Backup Degradation:** Routine database backups (`pg_dump`) become impossibly slow and massive.
- **Network & Serialization Overhead:** Database drivers are designed for fast relational row queries, not streaming binary chunks over SQL protocols.

## 2. Storage Paradigms Compared: Block vs. File vs. Object

```
┌─────────────────┬──────────────────────────────────┬──────────────────────────────────┬──────────────────────────────────┐
│ Feature         │ Block Storage (AWS EBS)          │ File Storage (AWS EFS / NFS)     │ Object Storage (AWS S3, MinIO)   │
├─────────────────┼──────────────────────────────────┼──────────────────────────────────┼──────────────────────────────────┤
│ **Structure**   │ Raw blocks (no filesystem)       │ Hierarchical folder tree         │ Flat key-value object namespace  │
│ **Protocol**    │ SCSI, iSCSI, Fibre Channel, NVMe │ POSIX, NFS, SMB                  │ RESTful HTTP / HTTPS (S3 API)    │
│ **Access Mode** │ Attached to a single VM instance │ Mounted across multiple VMs      │ Accessed globally over HTTP      │
│ **Modification**│ Random byte-level writes in-place│ File-level in-place edits        │ **Immutable** (Full overwrite)   │
│ **Scalability** │ Up to tens of terabytes          │ Petabytes                        │ **Virtually Infinite (Exabytes)**│
│ **Cost**        │ High ($$$)                       │ Moderate ($$)                    │ Low ($)                          │
└─────────────────┴──────────────────────────────────┴──────────────────────────────────┴──────────────────────────────────┘
```

## 3. Core Architecture of Object Storage

### 3.1 Flat Key-Value Namespace & The Illusion of Folders
Object storage has **no hierarchical directories or folders**.
- When you see a key like `uploads/2026/users/avatar.png`, `uploads` and `2026` are not physical folders on a filesystem.
- The entire string `uploads/2026/users/avatar.png` is simply an **opaque string key** in a massive distributed key-value store.
- Object store UIs (like the AWS S3 Console) parse slashes (`/`) to render simulated folders for visual convenience.

### 3.2 Immutability
Objects in object storage are **immutable**:
- You cannot open an existing 500MB video object and modify 10 bytes in the middle.
- Any modification requires re-uploading the entire object (`PUT`), replacing the previous version completely.

### 3.3 Control Plane (Metadata) vs. Data Plane
Object storage engines (such as AWS S3 or open-source MinIO) split storage responsibilities:

```
                            Object Storage Architecture
                                         │
        ┌────────────────────────────────┴────────────────────────────────┐
        ▼                                                                 ▼
 [ Metadata Plane ]                                                [ Data Plane ]
 • Fast distributed Key-Value store                                • High-throughput commodity storage
 • RocksDB, LSM-Trees, distributed SQL                             • Splits object into binary chunks
 • Stores Key, Content-Type, Size, ETag,                           • Distributes chunks across nodes
   ACLs, and Chunk Map Pointers                                    • Applies Erasure Coding (e.g., 8+4)
```

### 3.4 Durability via Erasure Coding (vs. 3x Replication)
How does AWS S3 deliver **99.999999999% (11 nines) of durability**?
- **Traditional 3x Replication:** Stores 3 identical copies of every file across separate data centers. Highly durable, but incurs a **200% storage overhead** (storing 1GB costs 3GB of disk).
- **Erasure Coding (Reed-Solomon):**
  - An object is divided into $K$ data chunks, and mathematical algorithms generate $M$ parity chunks (e.g., $8 + 4$).
  - These $K + M$ chunks are distributed across distinct physical hard drives, racks, and availability zones.
  - The original file can be reconstructed with **any $K$ chunks**. Even if 4 entire storage racks fail or lose power simultaneously, zero data is lost.
  - Storage overhead is reduced to only **~30%–50%**, drastically cutting cloud infrastructure costs.

## 4. Key Naming Patterns & Security Pitfalls

### 4.1 Avoiding Hot Partitions
- Historically, S3 partitioned storage keys by the lexicographical prefix of the key name.
- **Anti-Pattern:** Prefixing keys with monotonically increasing timestamps or sequential IDs:
  - `logs/2026-11-02-0001.log`
  - `logs/2026-11-02-0002.log`
  - This concentrates all write traffic onto a single storage partition ("Hot Partition"), degrading throughput.
- **Best Practice:** Use high-entropy prefixes (UUIDs, hashes, or tenant IDs):
  - `tenants/usr_98124/uploads/f8a2c10b-4d92.pdf`

### 4.2 Overwrite Traps & Path Traversal
- In object storage, `PUT` requests silently overwrite existing objects without warning if the key matches.
- **Malicious Uploads:** If your backend allows a user to upload `avatar.png` directly, a user could upload `../../system.config` or overwrite another user’s `avatar.png`.
- **Golden Rule:** **Never use the client-provided filename as the S3 object key.**
  - Always generate a server-side cryptographically secure UUID (`crypto.randomUUID()`) or content hash (SHA-256) for the storage key.
  - Store the original human-readable filename in your database or in S3 user metadata (`x-amz-meta-original-filename`).

## 5. File Upload Architectures: The Evolution

### 5.1 Pattern 1: Proxy Upload (Through the Backend Server) — The Anti-Pattern

```
[ Client Browser ] ────── (Uploads 100MB File) ──────▶ [ Backend Server ] ────── (Forwards 100MB) ──────▶ [ S3 Bucket ]
```

**Why Proxy Uploads Break Production Backends:**
1. **Double Bandwidth Cost:** You pay ingress bandwidth from the user to your backend, and egress bandwidth from your backend to S3.
2. **Worker & Connection Starvation:** A user on a slow 3G mobile connection takes 90 seconds to upload a 50MB video. That user's connection holds a backend thread/socket open for the entire 90 seconds, causing load balancers to timeout (`504 Gateway Timeout`) and starving other users.
3. **Memory Pressure:** Buffering multipart file uploads in server RAM or temporary `/tmp` disks triggers Out-Of-Memory (OOM) crashes.

---

### 5.2 Pattern 2: Direct Upload via Pre-Signed URLs (The Production Standard)

Instead of passing files through the backend, the backend acts solely as an **authorization gatekeeper**, granting the client temporary cryptographic permissions to upload directly to object storage.

```
                  Direct Upload via Pre-Signed URL Workflow
                  ═════════════════════════════════════════

  [ Client ]               [ Backend API ]                  [ S3 Bucket ]
      │                            │                               │
   1. │ POST /uploads/presign      │                               │
      │ (file_type, size, name)    │                               │
      ├───────────────────────────▶│                               │
      │                            │ 2. Authenticate user          │
      │                            │    Validate file size & MIME  │
      │                            │    Generate Pre-Signed URL    │
      │                            │    (Expires in 10 minutes)    │
   3. │ Returns Pre-Signed PUT URL │                               │
      │◀───────────────────────────┤                               │
      │                                                            │
   4. │ HTTP PUT directly to S3 with Binary Body                   │
      ├───────────────────────────────────────────────────────────▶│
      │                                                            │
   5. │ HTTP 200 OK (ETag returned)                                │
      │◀───────────────────────────────────────────────────────────┤
      │                                                            │
   6. │ POST /uploads/complete (key, etag)                         │
      ├───────────────────────────▶│                               │
      │                            │ 7. S3 headObject() check      │
      │                            │    Update DB: status='ACTIVE' │
      │ HTTP 200 OK                │                               │
      │◀───────────────────────────┤                               │
```

#### Step-by-Step Breakdown:
1. **Request Grant:** Client informs the backend of intent: *"I want to upload a 4MB PNG image named avatar.png."*
2. **Backend Validation:** Backend verifies user permissions, validates that the MIME type is allowed (`image/png`), and ensures the file size does not exceed quota limits.
3. **Pre-Signed URL Generation:** Backend calls the AWS SDK to sign a temporary `PUT` URL containing an AWS signature token (`X-Amz-Signature`) and expiry timestamp (e.g., 10 minutes).
4. **Direct Browser Upload:** The client executes an HTTP `PUT` request with the binary payload directly against the S3 URL.
5. **Confirmation:** Once S3 returns `200 OK`, the client notifies the backend to mark the file as active in the database.

## 6. The "Phantom Upload" Race Condition & Robust Mitigation

What happens if the client receives the pre-signed URL, uploads the file, but loses internet connection before notifying the backend? Or what if a malicious user requests 1,000 pre-signed URLs and never uploads anything?

### Two-Phase Upload Pattern
1. When generating the pre-signed URL, create a record in your database with `status = 'PENDING'`.
2. When the client calls `/uploads/complete`, the backend executes `s3.headObject()` to verify:
   - Does the object actually exist in S3?
   - Does the actual byte size in S3 match what the client claimed?
   - Does the `Content-Type` match?
3. If valid, update the status to `ACTIVE`.
4. Run an automated background cleanup cron job (e.g., every 6 hours) that deletes records and S3 objects that remain in `PENDING` status for more than 24 hours.

## 7. Optimistic Concurrency with ETags & `If-Match`

When multiple clients concurrently modify or upload files:
- Every S3 object has an **ETag** (an entity tag, usually the MD5 hash of the object content).
- **Conditional Writes:** Clients can send HTTP headers:
  - `If-Match: "etag_value"`: The upload or update succeeds only if the current object in S3 matches the specified ETag. If another user modified the file in the interim, S3 returns `412 Precondition Failed`.
  - `If-None-Match: *`: Ensures the `PUT` operation succeeds only if the object does not already exist, preventing accidental overwrites.

---

## 8. Key Takeaways Summary

- **Never store persistent user files on local server disks or inside relational databases.**
- **Object storage provides flat, immutable, HTTP-native storage** with virtually unlimited elastic scaling and 11 nines of durability via erasure coding.
- **Never proxy large file uploads through backend servers:** Always use direct uploads via time-limited **Pre-Signed URLs**.
- **Always generate cryptographically random UUIDs for object keys** to prevent path traversal and unintentional file overwriting.
- **Implement a two-phase upload flow** (`PENDING` $\rightarrow$ `ACTIVE`) verified via `headObject()` to eliminate orphaned phantom files.
