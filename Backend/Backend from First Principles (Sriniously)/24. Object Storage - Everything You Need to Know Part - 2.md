## 2. Multipart Uploads: Handling Gigabyte & Terabyte Files

When uploading large files (e.g., > 100MB, videos, database backups, ISO images) over standard HTTP `PUT`, any network hiccup or TCP timeout at 99% causes the entire upload to fail, forcing the user to restart from byte zero.

Furthermore, **AWS S3 enforces a hard limit of 5 GB for any single standard HTTP `PUT` request**. Files up to the maximum object size of **5 TB** must use **Multipart Uploads**.

```
                           Multipart Upload Architecture
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
  [ Part 1: Bytes 0-10MB ]      [ Part 2: Bytes 10-20MB ]     [ Part 3: Bytes 20-30MB ]
  Uploads in parallel           Uploads in parallel           Uploads in parallel
  Returns ETag "a1b2..."        Returns ETag "c3d4..."        Returns ETag "e5f6..."
        │                                │                                │
        └────────────────────────────────┼────────────────────────────────┘
                                         ▼
                   [ S3 CompleteMultipartUpload Request ]
                   Stitches parts into a single atomic object
```

### 2.1 The Three-Phase Multipart Lifecycle

#### Phase 1: Initiation (`CreateMultipartUpload`)
- The client or backend calls S3 to declare intent to upload a large object.
- S3 responds with a globally unique **`UploadId`**.
- An internal staging area is created in S3 to receive future chunks.

#### Phase 2: Uploading Chunks in Parallel (`UploadPart`)
- The client divides the local file into discrete chunks:
  - **Constraints:** Minimum chunk size is **5 MB** (except for the final part); maximum part size is 5 GB. Supports up to **10,000 individual parts**.
- Each part is uploaded with its index (`PartNumber: 1, 2, 3...`) and the `UploadId`.
- Each part upload returns an **ETag** (MD5 checksum of that specific chunk).
- **Resilience:** If Part 4 fails due to a network drop, **only Part 4 is retried**. The remaining parts do not need to be re-transmitted!
- **Concurrency:** Chunks can be uploaded in parallel over multiple concurrent HTTP connections, saturating available bandwidth.

#### Phase 3: Completion (`CompleteMultipartUpload`)
- The client submits a manifest containing the ordered list of all parts: `[{ PartNumber: 1, ETag: "..." }, { PartNumber: 2, ETag: "..." }]`.
- S3 verifies all checksums, stitches the parts together into a single, cohesive object, and exposes the finalized file in the bucket namespace atomically.

## 3. The Hidden Cost Trap: Incomplete Multipart Uploads

> [!CAUTION]
> **The Zombie Storage Leak:** If a multipart upload is initiated and 4 GB of parts are uploaded, but the client disconnects or aborts before sending `CompleteMultipartUpload`, **those 4 GB of chunk data remain stored in S3 forever**.

### Why This Is Dangerous:
1. **Invisible in Standard Listings:** Incomplete multipart chunks **do not appear in standard `ListObjectsV2` API calls or in the AWS S3 Console file browser**.
2. **Billing Continues Indefinitely:** Cloud providers bill you for every gigabyte of abandoned parts month after month. In active production apps, abandoned multipart uploads frequently accumulate terabytes of zombie storage costs.

### The Production Solution: S3 Lifecycle Cleanup Rule
Configure a mandatory bucket lifecycle rule in your Terraform, CloudFormation, or AWS Console:

```json
{
  "Rules": [
    {
      "ID": "AbortIncompleteMultipartUploadsAfter7Days",
      "Status": "Enabled",
      "Filter": { "Prefix": "" },
      "AbortIncompleteMultipartUpload": {
        "DaysAfterInitiation": 7
      }
    }
  ]
}
```
This guarantees that any multipart upload not completed within 7 days is permanently purged by AWS storage garbage collectors.

## 4. Serving Files: Streaming & HTTP 206 Range Requests

### 4.1 Memory-Safe File Streaming
When an application server proxies a download from S3 to a client, **never buffer the entire file in RAM**:

```typescript
// ❌ FATAL ANTI-PATTERN: Loads entire 2GB file into server RAM
const fileBuffer = await s3.getObject({ Bucket, Key }).promise();
res.send(fileBuffer.Body); // Crashes server with Out-Of-Memory (OOM)

// ✅ PRODUCTION PATTERN: Pipe readable stream to writable response
const s3Stream = s3.getObject({ Bucket, Key }).createReadStream();
s3Stream.pipe(res); // Memory usage remains constant (~64KB chunk buffer)
```

### 4.2 HTTP 206 Partial Content & Byte-Range Requests
Byte-range requests allow clients to ask for specific slice boundaries of an object rather than downloading the entire file from start to finish.

```
Client Request:
GET /videos/podcast.mp4 HTTP/1.1
Host: cdn.example.com
Range: bytes=1048576-2097151   <-- Requesting exactly 1 MB (Byte 1,048,576 to 2,097,151)

Server / S3 Response:
HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-2097151/52428800   <-- (Current chunk / Total file size 50MB)
Content-Length: 1048576
Content-Type: video/mp4

[ 1 MB of raw binary video data ]
```

### Core Capabilities Enabled by Range Requests:
1. **Instant Video/Audio Seeking:** When a user scrubs a video progress bar to minute 35, the browser does not download minutes 0 through 34; it fires a Range request directly for the video keyframe at minute 35.
2. **Resumable Downloads:** If a 10 GB file download disconnects after 6 GB, download managers resume from byte 6,000,000,001 rather than starting over.
3. **Multi-Threaded Parallel Downloads:** Download tools (like aria2 or IDM) split a file into 8 ranges and download all 8 ranges concurrently across separate connections, reconstructing the file locally.

## 5. High-Performance Distribution: CDNs & Origin Access Control

Serving files directly out of an S3 bucket to global users is both slow and financially inefficient:
- **High Egress Costs:** Direct AWS S3 data transfer to the internet costs ~$0.09/GB.
- **High Latency:** Global users suffer physical speed-of-light delays routing to a single AWS region.

```
                  Secure Edge Distribution Architecture
                  ═════════════════════════════════════

   [ Global Users ] ──▶ [ CloudFront CDN Edge PoPs ] ──(OAC Private)──▶ [ Private S3 Bucket ]
   • Cached in PoP      • Origin Access Control (OAC)                    • Public Access: BLOCKED
   • Sub-20ms latency   • Slashes egress bandwidth costs                 • Accessible ONLY via CDN
   • SSL termination    • Geo-distributed caching
```

### 5.1 Origin Access Control (OAC) / Origin Access Identity (OAI)
- **Security Best Practice:** **Block all public access on the S3 bucket.**
- Configure an S3 Bucket Policy granting read permissions exclusively to the CloudFront distribution via **Origin Access Control (OAC)**.
- No client can bypass your CDN, rate limiters, or web application firewall (WAF).

### 5.2 Edge Caching with Pre-Signed URLs
If you protect assets with S3 pre-signed URLs, the URL contains cryptographic query parameters (`X-Amz-Signature`, `X-Amz-Expires`) that change with every request:
- **The Problem:** Changing query parameters breaks CDN edge caching because each request looks like a unique URL, causing a 0% cache hit ratio!
- **Solutions:**
  1. **Normalize Expiration Times:** Round expiration timestamps up to the nearest hour (e.g., expiry set to top of the next hour) so all users accessing the file during that hour share the identical cached URL.
  2. **CloudFront Signed Cookies:** Grant access via signed HTTP cookies rather than URL query parameters, preserving clean, fully-cacheable file paths (`/media/lesson-1.mp4`).

## 6. Asynchronous Media Pipelines & Transcoding

Raw video and audio uploaded by users are rarely suitable for direct streaming (files are huge, uncompressed, and lack multi-device bitrate compatibility).

```
                 Asynchronous Transcoding Pipeline Workflow
                 ══════════════════════════════════════════

1. [ Client Upload ] ──(Pre-Signed)──▶ [ S3 Ingest Bucket ]
                                             │
2. [ S3 ObjectCreated Event Notification ] ──┘
   │
   ▼
3. [ SQS Message Queue ]
   │
   ▼
4. [ Transcoding Worker (FFmpeg / AWS MediaConvert) ]
   ├─ Generates 1080p, 720p, 480p, 360p bitrate renditions
   ├─ Generates HLS (.m3u8) playlist & segmented .ts chunks
   └─ Generates thumbnail preview sprites
   │
   ▼
5. [ S3 Production CDN Bucket ] ──▶ [ CloudFront ] ──▶ [ End Users ]
```

- **Adaptive Bitrate Streaming (HLS / DASH):** The video is sliced into 6-second `.ts` segments across multiple resolutions. The video player automatically adjusts resolution in real-time based on the user’s fluctuating network bandwidth.

## 7. Master Production Checklist for Object Storage

- [ ] All direct user uploads use **Pre-Signed URLs** or **Pre-Signed POST** schemas; zero large file proxying through application memory.
- [ ] Multipart uploads enabled for all files exceeding **100 MB**.
- [ ] Mandatory **S3 Lifecycle Rule** active to automatically abort incomplete multipart uploads after 7 days.
- [ ] All public bucket access permanently disabled; S3 locked down behind **CloudFront CDN with Origin Access Control (OAC)**.
- [ ] Downloads served via **streaming pipes**; buffered full-file reads strictly forbidden.
- [ ] Media endpoints support **HTTP 206 Partial Content / Range Requests** for video scrubbing and resumable downloads.
- [ ] Object keys use random UUIDs/hashes to prevent path traversal and unintentional overwriting.
- [ ] Automated asynchronous worker pipelines (FFmpeg / MediaConvert) convert raw uploads into web-optimized, adaptive-bitrate formats.
