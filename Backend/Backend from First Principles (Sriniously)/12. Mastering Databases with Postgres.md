## 1. Why Do We Need Databases? (Persistence)

* **Definition of Persistence:** Storing data in a manner that ensures it survives even after the program, process, or machine that created it has stopped.
* **The Problem Without Persistence:** Think of a to-do list application. Without persistent storage, every time you close the app or restart your computer, your progress, tasks, and state are lost, requiring you to recreate them on every visit.
* **Broad Meaning of "Database":** Any structured collection of data used across sessions can be loosely termed a database:
* Smartphone contact lists.
* Browser storage mechanisms: Local Storage (key-value store), Session Storage, Cookies.
* A simple plain text file where notes are written and referenced later.


* **Core High-Level Pattern:** Any persistent system providing basic **CRUD** operations:
* **C**reate
* **R**ead
* **U**pdate
* **D**elete

## 2. Disk Storage vs. RAM (Primary vs. Secondary Memory)

In the context of backend systems and servers, when developers refer to a "database," they almost always mean a **disk-based database**.

```
                    ┌─────────────────────────┐
                    │           CPU           │
                    └────────────┬────────────┘
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
┌──────────────────┐                           ┌──────────────────┐
│   Main Memory    │                           │ Secondary Memory │
│      (RAM)       │                           │   (Disks: SSD)   │
├──────────────────┤                           ├──────────────────┤
│ • Ultra fast     │                           │ • Relatively slow│
│ • Expensive/GB   │                           │ • Cheap/GB       │
│ • Small capacity │                           │ • Huge capacity  │
│   (8GB - 64GB)   │                           │   (512GB - 2TB+) │
│ • Caching (Redis)│                           │ • DBs (Postgres) │
└──────────────────┘                           └──────────────────┘

```

* **Capacity vs. Cost Trade-Off:**
* **RAM (Primary / Main Memory):** Fast execution, but expensive with limited hardware capacity (typically 8 GB, 16 GB, 32 GB, or 64 GB in standard setups). Used for caching layers like **Redis** or in-memory stores.
* **Disk (Secondary Storage - HDD / SSD):** Slower read/write access times compared to RAM, but far cheaper per gigabyte, providing large storage capacity (512 GB to 2 TB+).


* **The Backend Architectural Trade-Off:** Traditional production databases (PostgreSQL, MongoDB, MySQL) trade access speed for storage capacity and durability by saving primary data records to disk.

## 3. Database Management Systems (DBMS)

A **DBMS** is dedicated software whose primary responsibility is to store data on disk and provide efficient, reliable mechanisms for running CRUD operations across hundreds or thousands of gigabytes.

### Key Responsibilities of a DBMS

1. **Data Organization:** Structures records physically and logically to make reads, writes, and modifications fast and efficient.
2. **Access Control:** Exposes standardized interfaces and query mechanisms to perform CRUD operations.
3. **Data Integrity:** Ensures that data is accurate, valid, and non-corrupt:
* *Example:* If an e-commerce platform defines an order payment amount as a numerical type, the DBMS rejects any attempt to insert an arbitrary string.


4. **Security:** Protects data through role-based access control (RBAC), user authentication, and permission management.

---

### Why Not Just Store Data in Plain Text Files?

Early computer systems attempted to store data in flat files. This approach breaks down quickly due to three major limitations:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Flat Text File Failures                         │
├──────────────────┬──────────────────────┬──────────────────────────────┤
│ 1. Parsing Cost  │ 2. Lack of Structure │ 3. Concurrency / Race Hazard │
├──────────────────┼──────────────────────┼──────────────────────────────┤
│ Must read lines, │ Cannot enforce data  │ Simultaneous reads & writes  │
│ split strings,   │ types or field rules.│ overwrite each other blindly.│
│ slow & brittle in│ Prone to data        │ Unpredictable CPU-cycle race │
│ high-level langs.│ corruption.          │ conditions.                  │
└──────────────────┴──────────────────────┴──────────────────────────────┘

```

1. **Parsing Overhead & Brittleness:**
* Locating a single record requires custom application code to open the file, read lines sequentially, split strings, and compare fields.
* This is slow and CPU-heavy (especially in interpreted languages like Python or JavaScript compared to systems languages like Rust), and parsing logic is prone to breaking and corrupting files.


2. **Lack of Enforced Structure:**
* Text files are unstructured text streams. They cannot natively enforce column types, mandatory values, or constraints (e.g., preventing a non-numeric string in an amount column).


3. **Concurrency Issues (Race Conditions):**
* If two users attempt to modify the same record concurrently:
* *Initial balance:* `40`
* User A reads `40`, intends to add `20` (writes `60`).
* User B reads `40` at the exact same moment, intends to subtract `20` (writes `20`).
* Depending on which write operation executes last at the operating system/disk level, the final value will be arbitrarily set to either `60` or `20`.


* Flat files have no native locking, transactions, or concurrency control to ensure consistent state.

## 4. Relational (SQL) vs. Non-Relational (NoSQL) Databases

```
Relational (RDBMS / SQL)              Non-Relational (NoSQL / Document)
┌───────────────────────────────┐     ┌───────────────────────────────┐
│ Database                      │     │ Database                      │
│  └── Table                    │     │  └── Collection               │
│       └── Rows (Fixed Schema) │     │       └── Documents (Dynamic) │
│            └── Columns        │     │            └── Key-Value JSON │
└───────────────────────────────┘     └───────────────────────────────┘

```

| Feature / Trait | Relational Databases (RDBMS / SQL) | Non-Relational Databases (NoSQL / Document) |
| --- | --- | --- |
| **Data Organization** | Tables, Rows, Columns | Collections, Documents (JSON-like structures) |
| **Schema Strictness** | **Predefined, rigid schema.** Columns and types must be established prior to inserting data. | **Flexible, dynamic schema.** Individual documents inside the same collection can have differing structures. |
| **Primary Query Tool** | Structured Query Language (**SQL**) | Proprietary APIs, JSON-based query interfaces |
| **Core Advantage** | High **data integrity**, strong foreign key relationships, complex joins. | Rapid prototyping, zero schema friction, handles unstructured/dynamic data easily. |
| **Core Drawback** | Less forgiving of rapid, unpredictable structural pivots without migrations. | Data validation moves to application code; prone to subtle structural bugs and inconsistencies. |
| **Ideal Use Cases** | **CRM Systems:** Managing structured customer contacts, sales pipelines, billing, and transactional data. | **Content Management Systems (CMS):** Dynamic articles with varied media payloads (markdown, embeds, images). |
| **Examples** | PostgreSQL, MySQL, SQLite, Microsoft SQL Server | MongoDB, CouchDB |

## 5. Why Choose PostgreSQL?

1. **Free and Open-Source:** No proprietary license lock-in; can be hosted freely on local servers, virtual machines, or managed cloud instances.
2. **SQL Standards Compliant:** Closely adheres to the ANSI SQL standard. Writing standard SQL minimizes vendor lock-in, making future database migrations (e.g., moving to MySQL) relatively straightforward.
3. **Extensibility & Maturity:** Stable, battle-tested, highly scalable, and backed by comprehensive documentation (~1,400+ pages) supporting rich extensions and custom types.
4. **First-Class JSON/JSONB Support:**
* PostgreSQL natively supports both `JSON` (plain text storage) and `JSONB` (decomposed binary format).
* It provides deep indexing and querying capabilities inside nested JSON fields.
* *Strategic Implication:* You rarely need to introduce a separate NoSQL database like MongoDB solely to handle unstructured, dynamic data (e.g., user-generated custom fields or rich CMS content). PostgreSQL handles both relational schemas and dynamic JSON documents within the same instance.

## 6. PostgreSQL Data Types Reference

```
                             Common PostgreSQL Data Types
  ┌──────────────────┬─────────────────┬─────────────────┬────────────────────┐
  │     Numeric      │   Characters    │  Temporal / Date│   Specialized      │
  ├──────────────────┼─────────────────┼─────────────────┼────────────────────┤
  │ • serial         │ • char(n)       │ • date          │ • boolean          │
  │ • smallint       │ • varchar(n)    │ • time          │ • uuid             │
  │ • integer        │ • text          │ • timestamp     │ • json / jsonb     │
  │ • bigint         │                 │ • timestamptz   │ • array            │
  │ • decimal(p, s)  │                 │ • interval      │ • inet, macaddr,   │
  │ • real / double  │                 │                 │   point, xml       │
  └──────────────────┴─────────────────┴─────────────────┴────────────────────┘

```

### Numeric Types

* `serial` / `bigserial`: Auto-incrementing integers (defaults to starting at 1, increasing with each insert). Ideal for synthetic primary keys. `bigserial` supports larger numerical ranges for high-volume production tables.
* `smallint` < `integer` < `bigint`: Standard signed integers with increasing storage sizes and value limits.
* `decimal(precision, scale)` / `numeric(precision, scale)`:
* Exact numeric representation.
* `decimal(10, 2)` means up to 10 total digits across the entire number, with exactly 2 digits to the right of the decimal point (e.g., `12345678.90`).
* **When to use:** Whenever mathematical precision is non-negotiable, such as financial transactions, prices, and account balances.


* `real` / `double precision` / `float`:
* Inexact, floating-point numbers.
* Faster for calculations and scientific processing, but subject to minor rounding/representation discrepancies across hardware architectures.
* **When to use:** Scientific metrics, spatial/area measurements, where minor fractional variance causes no domain problems.



### String / Character Types

* `char(n)`: Fixed-length string. If you store a 2-character string in `char(10)`, PostgreSQL right-pads it with 8 blank spaces.
* *When to use:* Only when string length is completely static across every row (e.g., 2-letter country codes or two-letter day codes like `'MO'`, `'TU'`). Otherwise, avoid it.


* `varchar(n)`: Variable-length string with an enforced maximum character length limit of `n`. It does not waste space with padding.
* `text`: Variable-length string with unlimited capacity (up to PostgreSQL's technical limit of ~1 GB, practically cited as ~250 MB+).
* **Best Practice:** The official PostgreSQL documentation states there is **no performance difference** between `varchar(n)`, `varchar`, and `text`.
* The widespread convention of `varchar(255)` is an old carryover from MySQL. In PostgreSQL, `255` is an arbitrary number.
* Prefer `text` for strings. Enforce length constraints in your application logic or via explicit `CHECK` constraints to avoid database migrations down the line if limits expand.



### Temporal, Boolean & Structured Types

* `boolean`: `true` or `false`.
* `date`: Calendar date (`YYYY-MM-DD`) without time-of-day.
* `time`: Time of day (`HH:MM:SS`) without calendar date.
* `timestamp`: Date and time combined without time-zone context.
* `timestamptz`: Date and time **with time-zone** offset. Preferred for production systems to track exact global temporal points.
* `interval`: Represents spans of time (e.g., `'10 days'`, `'1 week'`).
* `uuid`: 128-bit Universally Unique Identifier, ideal for globally distributed, non-guessable primary keys.
* `json` vs. `jsonb`:
* `json`: Stored as raw text. Preserves whitespace and key order, but must be reparsed every time it is queried.
* `jsonb`: Parsed into a decomposed binary format on write. Slightly slower to write, but much faster to process, index, and query. **Default to `jsonb`.**


* `array`: Native array wrappers over any data type (e.g., `integer[]`, `text[]`).
* *Other types:* Geometric data types (`point`), network address types (`inet`, `macaddr`), and `xml`.

## 7. Database Migrations

### What Are Migrations?

A migration is a version-controlled, reproducible SQL script used to evolve a database schema over time across different development, staging, and production environments.

* **The Anti-Pattern:** Opening a graphical SQL client (such as TablePlus) and manually running schema change queries. This cannot be audited, versioned, or tracked across teams.
* **The Migration Setup:**
* Files reside in a project repository (e.g., `db/migrations/`).
* Named sequentially using incremental numbers or UTC timestamps (e.g., `20261102120000_create_users_table.sql`).
* Managed via a command-line interface (CLI) migration tool (such as `dbmate` or `golang-migrate`).



### Up vs. Down Migrations

* **Up Migration:** Defines the forward SQL statements needed to apply new schema changes (e.g., `CREATE TABLE`, `CREATE TYPE`, `CREATE INDEX`).
* **Down Migration:** Defines the exact reverse SQL statements needed to cleanly undo/revert the changes applied by the corresponding Up migration (e.g., `DROP TABLE`, `DROP TYPE`, `DROP INDEX`).
* **Rollbacks:** Down migrations allow automated rollbacks if an error occurs during deployment.
* **Tracking Schema State:**
* Tools like `dbmate` automatically inject a tracking table named `schema_migrations` containing a `version` column.
* Before executing, the CLI inspects `schema_migrations` to determine which scripts have already run, executing only newer versions to avoid duplicate execution errors.

## 8. Relational Data Modeling: Project Management System

The data model for a production-style Project Management application consists of:

1. **Users** (Core identity)
2. **User Profiles** (1:1 with Users)
3. **Projects** (1:N with Users)
4. **Tasks** (1:N with Projects, N:1 with User Assignees)
5. **Project Members** (N:M linking table between Users and Projects)

```
       ┌────────────────────────┐
       │     user_profiles      │
       └───────────┬────────────┘
                   │ 1:1 (user_id PK/FK)
                   ▼
┌───────────────────────────────────────────────┐
│                     users                     │
└──────────────┬─────────────────┬──────────────┘
               │ 1:N (owner_id)  │
               │                 │ N:M (via project_members)
               ▼                 ▼
       ┌──────────────┐   ┌───────────────┐
       │   projects   │◄──┤project_members│
       └───────┬──────┘   └───────────────┘
               │ 1:N (project_id)
               ▼
       ┌──────────────┐
       │    tasks     │
       └──────────────┘

```

### Custom Types (Enums)

Enums define an explicit whitelist of allowed string values for a column.

```sql
-- Migration: Creating Enums
CREATE TYPE project_status AS ENUM ('active', 'completed', 'archived');
CREATE TYPE task_status AS ENUM ('pending', 'in_progress', 'completed', 'cancelled');
CREATE TYPE member_role AS ENUM ('owner', 'admin', 'member');

```

* **Why Use Enums?**
1. **Database-Level Data Integrity:** Rejects invalid values at the database layer without relying solely on application validation.
2. **Living Schema Documentation:** New engineers can inspect the enum definitions directly to see all valid states for a column.

### Table Modeling & Relationships

#### 1. General Schema Conventions

* **Plural table names:** `users`, `projects`, `tasks` (industry standard).
* **Naming casing:** Lowercase and `snake_case` (e.g., `full_name`, `created_at`).
* *Reason:* PostgreSQL treats unquoted identifiers as case-insensitive (folding them to lowercase). Using camelCase forces you to use escaped double quotes (`"fullName"`) in queries.


* **Standard metadata fields:** Every primary entity includes an `id`, `created_at` (`timestamptz DEFAULT now()`), and `updated_at` (`timestamptz DEFAULT now()`).
* **`NOT NULL` as default:** Unless a column explicitly needs to allow nulls (e.g., `bio`, `due_date`), make it `NOT NULL` to maintain data integrity.

---

#### 2. The Users Table

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email TEXT NOT NULL UNIQUE,
    full_name TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

```

* `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`: Automatically generates a random UUID on insertion. Primary keys are implicitly `NOT NULL` and `UNIQUE`.
* `email TEXT NOT NULL UNIQUE`: Guarantees no two users can register using the same email address.
* `password_hash TEXT NOT NULL`: Stores the one-way cryptographic hash of the password, never plain text.

---

#### 3. One-to-One (1:1) Relationship: `user_profiles`

* **Why separate this from `users`?** User profile metadata (avatars, bios, secondary phone numbers) changes frequently and may expand over time. Isolating these attributes prevents the core authentication table from growing unnecessarily wide.

```sql
CREATE TABLE user_profiles (
    user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    avatar_url TEXT,
    bio TEXT,
    phone TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

```

* **Implementation:** The `user_id` column acts simultaneously as the table's **Primary Key** and as a **Foreign Key** referencing `users(id)`. This guarantees that each user profile row matches exactly one user.

---

#### 4. One-to-Many (1:N) Relationship: `projects` & `tasks`

* A user owns multiple projects; a project contains multiple tasks.

```sql
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name TEXT NOT NULL,
    description TEXT,
    status project_status NOT NULL DEFAULT 'active',
    owner_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tasks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    description TEXT,
    priority INTEGER NOT NULL DEFAULT 1 CHECK (priority >= 1 AND priority <= 5),
    status task_status NOT NULL DEFAULT 'pending',
    due_date DATE,
    assigned_to UUID REFERENCES users(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

```

##### Referencing Primary Keys Without Column Specification:

* Writing `REFERENCES users` automatically binds to the target table's primary key (`id`).

##### Understanding Referential Integrity Actions:

* `ON DELETE RESTRICT`: Blocks the deletion of a parent record if dependent child rows exist. (e.g., A user cannot be deleted if they still own active projects).
* `ON DELETE CASCADE`: Deleting the parent record automatically deletes all associated child rows. (e.g., Deleting a project removes all of its associated tasks).
* `ON DELETE SET NULL`: Deleting the referenced record updates the foreign key field to `NULL`. (e.g., Deleting an assigned user unassigns their tasks without deleting the tasks themselves).
* `ON DELETE SET DEFAULT`: Reverts the foreign key to its configured default value.

##### Constraints Highlight:

* `CHECK (priority >= 1 AND priority <= 5)`: Ensures the `priority` integer falls strictly within the 1–5 range. Any insert or update outside this range is rejected by the database.

---

#### 5. Many-to-Many (N:M) Relationship: `project_members`

* A user can belong to multiple projects, and a project can include multiple users.
* This relationship requires an intermediate **linking table** (also called a junction or bridge table).

```sql
CREATE TABLE project_members (
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role member_role NOT NULL DEFAULT 'member',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (project_id, user_id)
);

```

* **Composite Primary Key (`PRIMARY KEY (project_id, user_id)`):**
* Uses the combination of `project_id` and `user_id` as the primary key.
* This guarantees that a user can only be added to a given project once, preventing duplicate membership records.


* The `role` column stores project-specific permissions (`owner`, `admin`, or `member`) for that user.

## 10. Query Patterns for Common Backend APIs

### A. List All Users with Embedded Profile (`GET /v1/users`)

* Fetch all users along with their associated 1:1 profile data in a single query, avoiding multiple round-trip network calls.

```sql
SELECT 
    u.*,
    to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
ORDER BY u.created_at DESC;

```

* **Query Structure Best Practice:** Write SQL queries starting from the `FROM` and `JOIN` clauses first to establish where data originates, then define the `SELECT` columns.
* **Why `LEFT JOIN` instead of `INNER JOIN`?**
* If a user has not configured their profile yet, an `INNER JOIN` would drop that user from the results entirely.
* A `LEFT JOIN` returns the user row regardless, populating the `profile` field with `NULL` if no profile record exists.


* **`to_jsonb(up.*)`:** Uses PostgreSQL's native JSON function to convert the joined profile row into a nested JSON object on the parent row.
* **`ORDER BY u.created_at DESC`:** Relational databases do not guarantee record return order. List queries should always enforce an explicit sort order (newest first by default).

---

### B. Parameterized Queries & Preventing SQL Injection

* **The Vulnerability (SQL Injection):** Constructing queries using raw string concatenation (e.g., `"SELECT * FROM users WHERE id = '" + input + "'"` ) allows attackers to inject malicious SQL commands (such as `' OR '1'='1` or `; DROP TABLE users;`).
* **The Solution (Parameterized Queries):**
* Send the query structure with placeholder parameters (slots like `$1`, `:userId`, or `?`).
* Pass the user-supplied values separately. The database treats these inputs strictly as literal string values, escaping them automatically and preventing SQL injection.



```sql
-- Query to fetch a single user (GET /v1/users/:userId)
SELECT 
    u.*,
    to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.id = :user_id;

```

---

### C. List Queries with Filtering, Dynamic Sorting & Offset Pagination

* Dynamic list endpoints (e.g., `GET /v1/users?letter=J&sortBy=email&sortOrder=asc&page=1&limit=10`) combine filtering, sorting, and pagination.

```sql
SELECT 
    u.*,
    to_jsonb(up.*) AS profile
FROM users u
LEFT JOIN user_profiles up ON u.id = up.user_id
WHERE u.full_name ILIKE (:letter || '%')
ORDER BY 
    CASE WHEN :sort_by = 'u.email' AND :sort_order = 'asc' THEN u.email END ASC,
    CASE WHEN :sort_by = 'u.email' AND :sort_order = 'desc' THEN u.email END DESC,
    u.created_at DESC
LIMIT :limit OFFSET :offset;

```

* **`ILIKE (:letter || '%')`:** Case-insensitive string prefix matching (e.g., `'J%'` matches both "John" and "jane").
* **Sane Defaults:** If query parameters are omitted by the client, application code should default to:
* `page = 1` ($\to$ `offset = 0`, where $\text{offset} = (\text{page} - 1) \times \text{limit}$)
* `limit = 10`
* `sort_by = 'created_at'`
* `sort_order = 'desc'`



---

### D. Inserting a New User (`POST /v1/users`)

```sql
INSERT INTO users (email, full_name, password_hash)
VALUES (:email, :full_name, :password_hash)
RETURNING *;

```

* **`RETURNING *`:** Returns the newly created row—including database-generated values like `id`, `created_at`, and `updated_at`—directly from the insert operation, removing the need for a separate `SELECT` query.

---

### E. Partial Updates (`PATCH /v1/users/:userId`)

* Applications handle partial updates by constructing dynamic `UPDATE` statements that modify only the fields provided in the request payload.

```sql
UPDATE user_profiles
SET 
    bio = :bio,
    phone = :phone
WHERE user_id = :user_id
RETURNING *;

```

## 11. Database Indexes

### How Indexes Work

By default, table rows are stored on disk in arbitrary, non-sequential physical locations.

* **Sequential Scan (Full Table Scan):** Without an index, finding a row matching a condition requires reading every page off disk and checking each row one by one. While manageable across small tables, this becomes a significant bottleneck as tables grow to millions of rows.
* **The Book Index Analogy:** Instead of reading an entire 100-page book to find where "Chapter 4" starts, you consult the index at the back, find that Chapter 4 is on page 54, and jump directly to that page.
* **The Index Structure:** A database index is an ordered lookup data structure (typically a **B-Tree**) that maps indexed column values directly to the physical disk location (pointer) of their corresponding table row.

```
                    Query: WHERE project_id = 'p_42'
                                   │
                                   ▼
                   Index on tasks(project_id) [B-Tree]
                    ┌───────────────────────────────┐
                    │  Project ID   │ Disk Pointer  │
                    ├───────────────┼───────────────┤
                    │  'p_10'       │ Block 102, #2 │
                    │  'p_42'       │ Block 508, #4 ├───► Direct fetch to disk
                    │  'p_99'       │ Block 911, #1 │
                    └───────────────────────────────┘

```

---

### When to Create an Index

Evaluate candidate fields using these three main query patterns:

1. Columns frequently used in **`JOIN` conditions** (especially foreign keys like `tasks.project_id` or `tasks.assigned_to`).
2. Columns frequently targeted in **`WHERE` clauses** (e.g., `users.email` or `tasks.status`).
3. Columns targeted for sorting in **`ORDER BY` clauses** (e.g., `created_at DESC`).

> **Note on Primary Keys:** Relational database systems automatically create unique indexes for primary key columns. You do not need to index primary keys manually.

### Index Maintenance Overhead

* Indexes are not free. Every time a row is **inserted**, **updated**, or **deleted**, the database must also update the corresponding index structures on disk.
* Unnecessary indexes increase disk usage and degrade write performance. Only add indexes to columns that are queried frequently and show clear performance gains.

## 12. Automated Timestamp Tracking via Triggers

### The Problem

When updating a record, columns like `updated_at` do not update automatically. Relying on application developers to remember to pass `updated_at = now()` in every update query is error-prone.

### The PostgreSQL Solution

We can use a custom PostgreSQL function and table-level **Triggers** to update the timestamp automatically at the database level on every `UPDATE` operation.

```
Table UPDATE occurs ──► Trigger fires BEFORE UPDATE ──► Function sets NEW.updated_at = now()

```

#### Step 1: Create the Reusable Trigger Function

```sql
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

```

* `NEW`: A special record variable in PostgreSQL trigger functions holding the incoming updated row data.

#### Step 2: Attach the Trigger to Tables

```sql
CREATE TRIGGER update_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_user_profiles_updated_at
BEFORE UPDATE ON user_profiles
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_projects_updated_at
BEFORE UPDATE ON projects
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_tasks_updated_at
BEFORE UPDATE ON tasks
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER update_project_members_updated_at
BEFORE UPDATE ON project_members
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

```

* **Result:** Whenever an `UPDATE` runs against any of these tables, the trigger intercepts the operation before it writes to disk, sets `updated_at` to the current timestamp, and returns the modified row.

## 13. Transactions & Transaction Isolation Levels

### 13.1 ACID Guarantees
- **Atomicity:** All statements inside a `BEGIN ... COMMIT` block succeed together, or all fail and roll back (`ROLLBACK`).
- **Consistency:** Transactions transition the database from one valid state to another, enforcing all foreign keys, unique constraints, and check rules.
- **Isolation:** Concurrent transactions execute without interfering with one another.
- **Durability:** Once committed, changes survive server crashes, power failures, or OS restarts (via the WAL).

### 13.2 Concurrency Anomalies & Isolation Levels
When multiple transactions execute concurrently, four potential anomalies can occur:
1. **Dirty Read:** Transaction A reads uncommitted modifications made by Transaction B. If B rolls back, A read data that never existed.
2. **Non-Repeatable Read (Fuzzy Read):** Transaction A reads a row. Transaction B updates that row and commits. Transaction A re-reads the row and observes altered data.
3. **Phantom Read:** Transaction A queries rows matching a filter (`WHERE status = 'ACTIVE'`). Transaction B inserts a new row matching that filter and commits. Transaction A re-queries and sees a new "phantom" row.
4. **Serialization Anomaly:** The result of executing a group of concurrent transactions is different from running them sequentially in any order.

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly |
| :--- | :---: | :---: | :---: | :---: |
| **Read Uncommitted** (Postgres treats as Read Committed) | ❌ | Allowed | Allowed | Allowed |
| **Read Committed** (*PostgreSQL Default*) | Prevented | Allowed | Allowed | Allowed |
| **Repeatable Read** | Prevented | Prevented | Prevented (in PG) | Allowed |
| **Serializable** | Prevented | Prevented | Prevented | Prevented |

- **PostgreSQL Default:** `READ COMMITTED`. Each SQL statement sees a snapshot of committed rows as of the instant *that statement started*.
- **Pessimistic Locking:** Use `SELECT ... FOR UPDATE` inside a transaction to acquire row-level locks and prevent concurrent modification.

## 14. The Write-Ahead Log (WAL) & Durability

How does PostgreSQL guarantee **Durability** without forcing slow, random disk writes on every single `INSERT`?

```
               Write Path in PostgreSQL (WAL-First)
                                 │
           1. Modifying Query (INSERT / UPDATE)
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       [ 2. Append to WAL Buffer ]     [ 3. Update Shared Buffer ]
                 │                               │ (Dirty Page in RAM)
                 ▼                               ▼
       [ 4. fsync() to WAL on Disk ]     (Background Checkpointer flushes
       (Fast sequential append-only)      dirty pages to table data files
                 │                        periodically every 5-15 mins)
                 ▼
       [ 5. Transaction Commits ]
```

1. **Sequential Append-Only Writes:** Randomly writing modified pages to different table and index files on disk is extremely slow. Instead, Postgres writes change records to an append-only sequential log called the **Write-Ahead Log (WAL)**.
2. **The `fsync` Flush:** When a transaction commits, Postgres calls `fsync()` on the WAL file. Once the WAL entry is safely flushed to persistent storage, the transaction commits successfully.
3. **Crash Recovery:** If power is cut immediately after commit, the modified table data in RAM is lost, but during reboot Postgres reads the WAL from disk, replays the uncheckpointed changes, and restores the database to complete consistency.
4. **Replication Streaming:** PostgreSQL streaming replication works by continuously streaming these WAL records to Read Replicas!
