## 1. The Setup: Client and Server

- A **client** (e.g. a browser such as Chrome — the "frontend") communicates with a **server** running on localhost or somewhere remote (AWS, GCP, Azure, etc.).
- They communicate over a network through some means: **HTTP** (traditional REST API endpoints), **gRPC**, **WebSocket**, etc.
- For this video and the series, the focus is **HTTP / REST-style communication**, and the client is assumed to be a **JavaScript app** (React, Angular, Vue or any JavaScript framework/library — most client-side apps are highly interactive JavaScript apps).
- The client sends an **HTTP request** (covered in earlier videos): URL, headers and a request body (for POST). This is how the frontend sends all the information it wants to the server. The server responds with a response which the client is able to parse and make sense of.

## 2. The Problem

How do the client and server **make sense of the data** being sent/received?

- **Example:** the client is a JavaScript app sending an object (e.g. with a `name` string) in the request body; the server is a **Rust** app.
  - JavaScript is a completely **dynamic**, non-compiled language. Rust is very **strict about types** and compiled. Their data types are completely different.
  - So how does data transmitted over a network reach another machine somewhere on the internet, get understood in that machine's own data types, have business logic performed on it, get a response sent back, and have the client make sense of that response to show UI or run logic?

### Background: OSI model (high-level only)
- It helps to have a high-level understanding of the **OSI model** (CS students may already know it): the different network layers communicating to transmit data over hardware.
- You don't need to master every aspect (IP packets, data frames, etc.). Going deeper is out of scope; better resources exist elsewhere.
- The top layer is the **application layer**; the bottom is the **physical layer**, with layers in between — on both the client and the server side.

## 3. The Solution: A Common Standard

- Imagine being asked to solve this: two machines in different locations connected over the internet need a technique/protocol so that one can send data to the other and the data can be parsed and understood in a **language-agnostic** way.
- An obvious solution: figure out a **common standard** — a set of rules (a format) that both client and server agree to use for sending/receiving data.
- **Flow:**
  1. The client converts its data from its own language (e.g. JavaScript) into this standard format and sends it over the network.
  2. The server takes the data from that standard and converts it into its own representation (e.g. a **struct** in Rust), then does whatever it needs to do.
  3. When responding, the server converts its data (e.g. a Rust struct) into the common format and sends it.
  4. The client reads/parses it back into JavaScript and does what it needs to do.
- This solution is a **serialization standard**.

> **Summary:** **Serialization and deserialization** = converting data **to and from a common format** during transmission (or storage — to be covered), so it's **domain/language-agnostic** and machines, servers and clients from different languages and environments can make sense of the data and respond to it.

## 6. JSON

- **JSON = JavaScript Object Notation.** Its look and behavior are very similar to a JavaScript object (hence the name), but it is **not limited to JavaScript** and is used everywhere:
  - **Configuration files**
  - **HTTP REST API transmission** between clients and servers
  - **Log files** — a very popular choice for logging application/server data at runtime
- (The speaker suggests reading other resources for JSON's history and evolution. Here the focus is transmission.)
- JSON is **completely human-readable** — one of its strong points; it was made to be human readable. Its data types are pretty fundamental.

### Rules / structure
1. Starts with an opening curly brace and ends with a closing curly brace.
2. **Keys are inside double quotes** and must be **strings** — no other data type can be a key.
3. **Values** can be: a **string**, a **number**, a **boolean**, an **array**, or another **object**.
4. JSON can be **nested**. Example: an `address` field whose value is another object (with its own braces) containing e.g. `country` (string, "India") and `phone number` (a number). The nested object follows the same rules — double-quoted string keys and values of the allowed types.

## 7. Demo (Burp Suite)

Reusing the earlier demo, but focusing on the **request and response data format**.

**Request:** `POST /api/books`
- The body is JSON: curly braces, double-quoted string keys, and values — a **number** and **two strings** (`id`, `title`, `author`).
- This is what gets transmitted over the network.

**Mental model for a backend engineer**
- In the OSI model, the application-layer data gets converted into data frames, IP packets, and eventually **bits (0s and 1s)** transmitted as voltage signals over optical fiber, etc.
- As a backend engineer you can assume: the **client adheres to a standard (JSON)** and the **server understands that standard**. At the application layer, the data is JSON; **whatever intermediary formats it's converted into after that is not your concern**.
- On the receiving end, after the network layers read all the bits, the data is again **JSON** — the server only gets to read JSON. You don't need to worry about the intermediary steps.

**Response**
- The server takes the ID and other information from the request JSON and responds with another JSON: an opening brace, **one key whose value is an array**, where each element is an object. Again all keys are double-quoted, with values in number and string formats.
- The client receives it, understands it, parses it and **renders it** (here in JavaScript; "it can be PHP also").

## 8. Summary

- In real-life scenarios serialization/deserialization doesn't involve a lot of concepts; it's a **phenomenon in the backend world** that you need to know exists.
- Flow: the client sends JSON → the server parses/understands it and performs business logic → the server responds with appropriate data in JSON → the client parses and understands it. **This whole flow is serialization and deserialization.**
- **Serialization and deserialization are techniques that convert data into a common, standard format**, so clients can send data to the server in that format, the server can receive/parse it, perform business logic and send data back in the same format, and the client can do the same — making data **understandable across domains and languages**.
