## 1. What is Caching?

* **One-Sentence Definition:** A mechanism used to reduce the amount of time and effort required to perform a specific piece of work.
* **Technical Definition:** Storing a **subset** of primary data in a location that is significantly faster and less resource-intensive to access.
* Which subset is kept depends on usage patterns, access frequency, future request probability, and time elapsed.


* **Impact:** A critical architectural strategy for high-performance applications that measure target latency in two-digit milliseconds or microseconds.

```
                    Without Caching
Client ────────► Server ────────► Database / Heavy Compute (Slow, Costly)
Client ◄──────── Server ◄──────── (High Latency)

                     With Caching
Client ────────► Server ──── Cache Hit? ────► [ Fast In-Memory Cache ] ──► (Instant Return)
                    │
                Cache Miss?
                    └───► Database / Compute ───► Store in Cache ───► Return to Client

```

## 2. Real-World Case Studies

### A. Google Search

* **The Cost:** A single query (e.g., *"What is the weather today?"*) involves crawling, indexing, and ranking algorithms evaluating billions of web pages. Performing this computation for every search would overload CPU and memory.
* **The Solution:** A globally distributed, in-memory caching system stores search results.
* **Flow:**
* **Cache Hit:** The query matches cached results; data returns to the user instantly.
* **Cache Miss:** The full ranking and retrieval pipeline executes, returns the fresh response, and writes that result to the cache for future users.



### B. Netflix & Global Video Streaming

* **The Challenge:** Streaming multi-terabyte libraries globally to millions of concurrent users with minimal buffering while avoiding server crashes.
* **Encoding Optimization:** Prior to delivery, videos are pre-encoded into multiple resolution ladders (1080p, 720p, 480p) to match dynamic bandwidth constraints and device capabilities.
* **Content Delivery Networks (CDNs):**
* Origin servers (e.g., in US data centers) hold the primary master content.
* Content is cached at **Edge locations** positioned close to end users worldwide.
* Local users stream directly from nearby edge nodes rather than routing traffic across transatlantic fiber cables, reducing latency and transit costs.
* *Selective Subsetting:* Storing the entire catalog at every edge node would be prohibitively expensive. ML algorithms analyze regional viewing trends to cache only localized subsets.



### C. X (Twitter) Trending Topics

* **The Problem:** Computing real-time trending topics requires analyzing millions of tweets with machine learning models and GPUs. Running this computation on every user page load would cause server failures within seconds.
* **The Strategy:**
* Trends do not fluctuate every second; major events (e.g., national elections) remain relevant across hours or days.
* Heavy trend-detection jobs run periodically (e.g., every few minutes).
* The computed ranking is written to an in-memory key-value cache (like **Redis**).
* User requests are served directly from this in-memory cache with near-zero latency.

## 3. The Underlying Hardware: RAM vs. Disk

The performance delta between caching layers and databases stems directly from memory architecture:

```
┌────────────────────────────────────────────────────────────────────────┐
│ CPU Registers & On-Chip Caches (L1, L2, L3)                           │
├────────────────────────────────────────────────────────────────────────┤
│ Primary Memory: RAM (Main Memory) ──► In-Memory Caches (Redis, Memcached)│
│ • Electronic / Solid-State (Capacitors, constant addressing)           │
│ • Volatile: Wiped on power loss                                        │
│ • Limited Capacity (GBs) & High Cost/GB                                │
├────────────────────────────────────────────────────────────────────────┤
│ Secondary Memory: Disks (HDD, SSD) ──► Traditional DBs (Postgres, MySQL)│
│ • Mechanical / Flash Block Storage                                     │
│ • Non-Volatile: Persistent across restarts                             │
│ • Large Capacity (TBs) & Low Cost/GB                                   │
└────────────────────────────────────────────────────────────────────────┘

```

* **Hardware Caching (L1, L2, L3):** Small SRAM caches residing on the CPU die. For example, when traversing arrays sequentially, CPU prefetchers predictively load contiguous memory blocks into L1/L2 caches to maximize memory throughput.
* **Why RAM is Called "Random Access":** Relies on electrical signals to read any memory address via capacitor grids in near-constant time ($O(1)$ addressing), regardless of read order. By contrast, traditional disks rely on physical heads seeking sectors, making sequential access vastly different from random access.
* **Volatile vs. Persistent:** RAM loses state immediately when unpowered. Secondary disks physically retain state.
* **Persistence Handling in Redis/Memcached:** In-memory databases operate out of RAM for ultra-fast data retrieval, while writing snapshots or append logs to secondary disk storage in the background to rehydrate memory on system restarts.

## 4. The Three Levels of Caching in Backend Engineering

```
                          Three Levels of Caching
      ┌──────────────────────────────┼──────────────────────────────┐
      ▼                              ▼                              ▼
[ Network Level ]              [ Hardware Level ]             [ Software Level ]
• CDN (Edge/PoP)               • CPU Caches (L1/L2/L3)        • In-Memory Stores
• DNS Hierarchy                • RAM / Main Memory              (Redis, Memcached)
                                                              • App-level caches

```

### Level 1: Network-Level Caching

#### 1. Content Delivery Networks (CDNs)

* **Goal:** Cache static web assets (images, videos, JS, CSS, HTML) geographically close to the requester.
* **Edge Nodes & PoPs:** A **PoP (Point of Presence)** is a regional data center hosting multiple **Edge Servers**.
* **Request Lifecycle:**
1. A user enters a URL into their browser.
2. The CDN's DNS routes the request to the nearest geographical PoP based on user IP and real-time network conditions.
3. The Edge server checks local storage:
* **Cache Hit:** Serves asset directly.
* **Cache Miss:** Pulls the asset from the remote Origin Server, stores it locally, and delivers it to the user.


4. Assets are bound by a **TTL (Time to Live)** to prevent serving stale versions indefinitely.



#### 2. Domain Name System (DNS) Caching

Resolving domain names (`example.com`) to IP addresses is computationally and operationally expensive. To eliminate repetitive multi-hop lookups, caching exists at every tier:

```
User types "example.com"
        │
        ▼
1. Operating System Cache  ──(Hit?)──► Returns IP
        │ (Miss)
        ▼
2. Browser DNS Cache       ──(Hit?)──► Returns IP
        │ (Miss)
        ▼
3. Recursive Resolver      ──(Hit?)──► Returns IP (Maintained by ISP, Google 8.8.8.8, Cloudflare 1.1.1.1)
        │ (Miss)
        ▼
[ Uncached Full Resolution Walk ]
   ├─► Root Server (Returns TLD server pointer, e.g., for .com)
   ├─► Top-Level Domain (TLD) Server (Returns Authoritative Name Server pointer)
   └─► Authoritative Name Server (Returns final A/AAAA record IP address)

```

---

### Level 2: Hardware-Level Caching

* **L1, L2, and L3 CPU Caches:** Ultra-fast on-die SRAM caches designed to keep the CPU execution units supplied with instructions and data without stalling on relatively slow main-memory fetches.
* **Main Memory (RAM):** Serves as the high-speed data canvas utilized by software-level caching engines.

---

### Level 3: Software-Level (In-Memory) Caching

* **Technologies:** **Redis**, **Memcached**, managed cloud services like **AWS ElastiCache**.
* **Characteristics:** Categorized as **in-memory key-value NoSQL databases**.
* Free from the rigid schema validation and complex table-locking mechanisms of SQL databases.
* Simple, atomic operations over keys mapping to strings, hashes, lists, sets, or JSON structures.

## 5. Caching Strategies & Mutation Patterns

### 1. Lazy Caching (Cache-Aside)

The application handles cache reads and cache writes lazily:

```
Client Read Request
       │
       ▼
[ Application ] ──1. Check Cache──► [ Redis ]
       │                               │
       ├─────── 2a. Cache Hit (Return) ◄─┘
       │
       ▼ (2b. Cache Miss)
 [ Database ]
       │
       ├─────── 3. Return Fresh Data to App
       │
       ▼
 [ Application ] ──4. Write to Cache (with TTL)──► [ Redis ]

```

* **Pros:** Only requested data is cached (avoids filling memory with unread records); survives cache node failures (system falls back to the database).
* **Cons:** Cache miss penalty on first access; risks serving stale data if the underlying database is mutated without an explicit cache invalidation step.

### 2. Write-Through Caching

The application writes data to both the primary storage and the cache within the same update transaction:

```
Client Write Request
       │
       ▼
[ Application ] ──► Write to [ Database ] AND Update [ Cache ] simultaneously

```

* **Pros:** Cache is never stale; read operations immediately encounter warm, fresh data.
* **Cons:** Introduces write latency overhead (two storage round-trips per write); caches cold data that might never be read again unless paired with aggressive TTLs.

## 6. Cache Eviction Policies

Because RAM is bounded and expensive, caches eventually run out of capacity. An **eviction policy** dictates which keys are purged to accommodate new writes.

| Eviction Policy | Full Name | Eviction Mechanism & Logic |
| --- | --- | --- |
| **No Eviction** | No Eviction | Rejects new write requests with memory limit errors once capacity is saturated. |
| **LRU** | **Least Recently Used** | Evicts keys based on **recency**. Evaluates timestamps to discard the key whose last access occurred furthest in the past. |
| **LFU** | **Least Frequently Used** | Evicts keys based on **access count**. Tracks an access counter and purges keys with the lowest lifetime read frequency. |
| **TTL-based** | Volatile-TTL | Selects and evicts keys with the shortest remaining Time-to-Live (keys closest to natural expiration). |

## 7. Core Backend Use Cases for In-Memory Caching

### A. Database Query Caching

* **Problem:** Complex SQL queries with multi-table joins, subqueries, and large aggregations consume massive CPU and I/O resources on relational databases.
* **Application:** Cache query outputs inside Redis with a balanced TTL (e.g., 1 hour).
* **Real-World Examples:**
* **Amazon Product Pages:** Core specifications of a laptop rarely change; serving these pages via cache during flash sales shields primary inventory and order-processing databases from read exhaustion.
* **Social Media User Profiles:** Profile data for high-profile accounts (which may be requested millions of times per day) is read-heavy and updated infrequently, making it ideal for cache-aside patterns.



### B. User Session Storage

* **Workflow:** Upon login verification, the server issues a unique session identifier or token.
* **Why Redis?** Every subsequent authenticated request requires looking up the user's active session state. Reading session metadata from disk-bound relational databases introduces 20–30 ms of unnecessary latency per request. Moving session storage to Redis keeps lookup times in the single-digit microsecond/millisecond range.

### C. External API Caching & Cost Reduction

* **Problem:** Downstream services or third-party APIs (e.g., Weather data, stock tickers) often impose strict rate limits and charge per-request fees.
* **Application:** Fetch dynamic third-party data once, set a reasonable TTL (e.g., 30–60 minutes), and serve all incoming client requests from the local cache to stay within vendor quotas and reduce billing costs.

### D. Distributed Rate Limiting

* **Problem:** Protecting backend infrastructure from bots and brute-force traffic by enforcing limits (e.g., maximum 50 requests per minute per IP address).
* **Architecture:** Implemented as a high-performance **middleware** at the application entry point.

```
Client Request
      │
      ▼
[ Rate Limit Middleware ]
      │
      ├─► Extract Client IP from Header (e.g., X-Forwarded-For)
      │
      ├─► Atomic Increment in Redis: INCR ratelimit:<ip>
      │
      ├── Counter > 50? ──► Terminate Request: Return 429 Too Many Requests
      │
      └── Counter <= 50 ──► Call next() ──► Route Handler / Controller

```

* **Why Redis over SQL?**
* Rate-limiting checks execute on every single incoming HTTP call.
* Performing transactional reads, row locks, and increments against relational databases (like PostgreSQL or MySQL) for every request creates severe I/O bottlenecks and introduces measurable latency.
* Redis executes in-memory key increments with sub-millisecond round trips, handling rate-limiting counters without degrading database resources.

## 8. The Cache Stampede (Dogpiling) & Advanced Mitigations

### 8.1 The Phenomenon
When a highly popular cached key (e.g. homepage product feed or trending topics) expires during peak traffic:
1. At timestamp $T$, the cache key TTL expires.
2. Over the next 100 milliseconds, 5,000 concurrent requests arrive.
3. Every single request experiences a **Cache Miss**.
4. All 5,000 threads simultaneously query the primary database with the exact same heavy SQL query.
5. The database CPU spikes to 100%, connection pools exhaust, and the system crashes (**Dogpiling / Cache Stampede**).

```
                                  The Cache Stampede
5,000 Concurrent Requests ──▶ [ Cache Key Expired! (Miss) ]
                                            │
                                            ▼
                       💥 5,000 Simultaneous Heavy SQL Queries 💥
                                            │
                                            ▼
                               [ Database Overload & Crash ]
```

### 8.2 Production Mitigations

#### 1. Distributed Mutex (Locking)
When a cache miss occurs, the worker attempts to acquire a distributed lock in Redis (`SET lock:key value NX EX 5`):
- The single thread that acquires the lock queries the database and repopulates the cache.
- All other threads wait briefly (e.g., sleep 50ms) and retry reading from the cache.

#### 2. Probabilistic Early Expiration (XFetch Algorithm)
Instead of waiting for the TTL to expire, workers compute a probability of refreshing the cache in the background slightly before the deadline:
$$\text{Refresh if } -\beta \times \delta \times \ln(\text{random}()) > \text{remaining\_ttl}$$
(where $\delta$ is the computation compute time, $\beta > 0$ is an aggressiveness factor). A single client refreshes the cache asynchronously while other clients continue receiving valid cached data.

#### 3. Stale-While-Revalidate
The cache serves slightly stale data to incoming clients immediately, while triggering an asynchronous background worker to fetch fresh data from the database and update the cache. Zero user-facing latency and zero database stampedes.
