# HTTP Protocol – Backend Notes

**Scope:** Backend is huge, so only topics used in ~90% of codebases are covered. HTTP is the medium through which browsers talk to servers (to send or receive data). There are other protocols too, but HTTP is one of the most used.

---

## 1. Two Core Ideas of HTTP

### 1.1 Statelessness

- HTTP has **no memory of past interactions**.
- Each request carries all the information the server needs to process it (headers, URL, method, etc.).
- After the server responds, it **forgets** the request. A new request from the same client is treated as a new, unrelated event.
- **Self-contained requests:** each request must include all necessary data, e.g. authentication tokens or session information.
    - Example: to access a user profile, the client must send credentials (cookies or tokens) on _every_ request so the server knows which user is asking.

**Benefits of the stateless model**

- **Simplicity** – server doesn't store session information (which would need extra resources and complexity).
- **Scalability** – requests are easy to distribute across multiple servers since no single server tracks a session. If a server crashes, client interaction state isn't affected because there's no session to restore.

Because HTTP is stateless, developers implement **state management techniques** (cookies, sessions, tokens) where continuity is needed, e.g. user logins or shopping carts (to be explored later in the series).

### 1.2 Client–Server Model

- There is always a **client** and a **server**.
- **Client:** typically a web browser or an application. It **initiates** communication by sending a request, and is responsible for providing all info the server needs (URL, headers, etc.).
- **Server:** hosts resources (websites, APIs, other content) and waits for incoming requests. It processes a request and sends back a response: a web page, data, an error message, a JSON file, a text file, or any other content.
- **HTTP states that communication is always initiated by the client.**

---

## 2. HTTP vs HTTPS, TCP and the OSI Model

- HTTP and HTTPS can be treated as interchangeable for this series. HTTPS is (oversimplified) a more secure version of HTTP, with the same underlying principles plus encryption, security certificates, TLS, etc. (which borders on network engineering).
- The client and server need to establish a **connection mechanism** first. HTTP uses **TCP**.
    - HTTP doesn't require the transport protocol to be connection-based; it only requires it to be **reliable** and not lose messages (at minimum, presenting an error in such cases).
    - Of the two most common transport protocols (TCP and UDP), **TCP is more reliable**, so HTTP relies on TCP, which is connection-based.
- **OSI model:** often referenced when talking about sending/receiving data over a network. Backend engineers mostly deal with the top layer, **Layer 7 – the application layer**.
    - Topics like the TCP handshake, establishing connections and TLS encryption are mostly network-engineering concepts. Good to know, but a rabbit hole.
    - Focus is on the application layer, with a brief note that TCP uses a **3-way handshake** (look it up if curious).

### HTTP Versions

|Version|Key points|
|---|---|
|**HTTP/1.0**|Each request opened a new connection → inefficient, since a connection had to be established and closed for every request/response.|
|**HTTP/1.1**|**Persistent connections** – multiple requests/responses over the same TCP connection, significantly improving performance. Also added chunked transfer encoding and better caching mechanisms. (Currently the most used.)|
|**HTTP/2**|**Multiplexing** – multiple requests/responses over a single connection. Uses **binary framing** instead of text, **header compression** (HPACK), and **server push** (server can send resources before the client requests them).|
|**HTTP/3**|Built on the **QUIC** protocol, a transport-layer protocol over **UDP** instead of TCP. Faster connection establishment, reduced latency, better handling of packet loss. Supports multiplexing **without head-of-line blocking** (which is still an issue in HTTP/2).|

**Takeaway:** the client and server establish some kind of network connection and messages are sent and received. That's all that needs to be remembered for now.

## 3. HTTP Messages

- **Request message** – sent by the client.
- **Response message** – received by the client from the server.

### Request message structure

1. **Request method** (e.g. GET, POST)
2. **Resource URL** – the resource requested from the server
3. **HTTP version** (e.g. 1.1)
4. **Host** – the domain
5. **Headers** – key-value pairs
6. **Blank line** – signals the headers are over and the body starts
7. **Request body** – information the client wants to send to the server

### Response message structure

1. **HTTP version**
2. **Status code** and its value (e.g. 200 = OK)
3. **Response headers**
4. **Blank line**
5. **Response body**

## 4. HTTP Headers

**Definition:** key-value pairs of parameters sent in a request or received in a response — i.e. **metadata** about the request/response.

### Why separate headers (instead of URL or body)?

**Parcel analogy:** the recipient's address, phone number, state, PIN code, etc. are written on the _outside_ of a parcel, not inside. Couriers handling the parcel need this info to transmit it through different modes of transport; if it were inside, they'd have to open the parcel every time someone needs to check the address. Headers give a quick way of checking metadata without opening the "package" (body). Headers also have more uses than this.

### Categories of headers

**1. Request headers** – sent by the client to give info about the request itself. Help the server understand the client's environment, preferences and capabilities.

- `User-Agent` – identifies the client (browser, Postman, a server, a mobile app…)
- `Authorization` – credentials such as a Bearer token, to identify the user
- `Accept` – the kind of content expected (JSON, text, HTML…)

**2. General headers** – used in both requests and responses; metadata about the message itself.

- Date of the message
- Caching mechanisms like `no-cache`, `max-age`
- Connection information (keep alive or close)

**3. Representation headers** – deal with the representation of the resource being transmitted (request body or response body). Ensure clients and servers know how to interpret/process the body.

- `Content-Type` – media type (JSON, HTML…)
- `Content-Length` – size of the resource in bytes
- `Content-Encoding` – encoding such as gzip or deflate
- `ETag` – unique identifier, mostly used for caching

**4. Security headers** – enhance security of requests/responses by controlling behaviors like content loading, cookies and encryption.

- `HSTS` (Strict-Transport-Security) – ensures the client only communicates over HTTPS, preventing protocol downgrade attacks
- `Content-Security-Policy` – restricts sources from which content like JavaScript, CSS and images can be loaded; helps prevent cross-site scripting (XSS)
- `X-Frame-Options` – prevents the page from being embedded in an iframe; mitigates clickjacking
- `X-Content-Type-Options` – stops the browser from guessing the MIME type; prevents MIME-type sniffing attacks
- `Set-Cookie` with `HttpOnly` / `Secure` flags – makes cookies inaccessible to JavaScript and ensures they're sent over HTTPS only

### Two ideas behind headers

**Extensibility**

- HTTP is highly extensible: headers can be added/customized **without altering the underlying protocol**. Adding some metadata can change the whole flow of the interaction.
- Headers can be defined for various purposes, making HTTP adaptable to new technologies and use cases:
    - **Security enhancements** – e.g. Strict-Transport-Security to force secure connections
    - **Custom headers** – e.g. `X-Custom-Header` for an application's own use cases
    - **Content negotiation** – `Accept`, `Accept-Language`, `Accept-Encoding` let servers serve different versions of content depending on client preference

**Remote control**

- Headers act like a **remote control on the server side**: the client sends instructions/preferences that influence how the server responds or processes requests.
    - **Content negotiation** – client requests a format via `Accept` (HTML → server sends HTML; JSON → server sends JSON)
    - **Caching and expiration control** – server uses `Cache-Control` or `Expires` to control how long a resource is cached by the client
    - **Authentication** – client authenticates via the `Authorization` header, influencing access-control decisions

## 5. HTTP Methods

Methods represent different kinds of actions a client (browser or API consumer) can request on a server. They define the **intent** of the interaction and give clear semantic meaning to each action.

|Method|Purpose|Notes|
|---|---|---|
|**GET**|Fetch data from the server|Should not modify anything on the server|
|**POST**|Create data on the server|Has a request body (how else would user data be sent)|
|**PATCH**|Update data|Has a request body. Example: user updates their name on a profile page. Can be thought of as an _append_ or _selective replacement_|
|**PUT**|Update data|Data in the request body **completely replaces** the previous instance|
|**DELETE**|Delete a resource from the server||
|**OPTIONS**|Fetch the capabilities of the server for a cross-origin request|Rarely used directly by developers; seen in the browser Network tab in **pre-flight requests**|

- Developers often use PUT when they should use PATCH (going against semantics). **Rule of thumb: always use PATCH unless you have a specific use case for PUT.**

### Idempotency

Idempotent = the method can be called multiple times and you can expect the **same result**.

- **GET** – idempotent. Fetching any number of times gives the same data; it doesn't modify anything.
- **PUT** – idempotent. It completely replaces the resource, so replacing repeatedly with the same data gives the same result.
- **DELETE** – idempotent. A resource can only be deleted once; after that the result is always the same.
- **POST** – usually considered **non-idempotent**. Example: submitting a request to create a note creates a new note; submitting it again creates _another_ note — different results for the same request.

## 6. CORS (Cross-Origin Resource Sharing)

### Background

- Browsers follow the **Same-Origin Policy**: by default, web pages can't make requests to a domain different from the one serving the page.
- **CORS** is a security mechanism enforced by browsers to control how web apps interact with resources hosted on **different domains (cross-origin)**.
- Without CORS, browsers block requests from e.g. `example.com` to `api.example.com` for security reasons. CORS lets servers specify **who can access their resources and how**.
- Two flows: **simple request flow** and **pre-flighted request flow**.

### 6.1 Simple Request Flow

Example: client (frontend) at `example.com`, server at `api.example.com`, making a GET request.

1. The client sends the request; the browser automatically adds the **`Origin`** header.
2. The request uses a simple method (usually **GET, POST or HEAD**) and reaches the server.
3. The server checks the `Origin` against its CORS policy.
4. If the origin is allowed, the server includes **`Access-Control-Allow-Origin`** in the response and sends the resource.
5. The browser sees the client's domain differs from the host domain, so it checks the response for that header. The value must be either the **client's domain** (e.g. `example.com`) or **`*`** (allow all origins).
6. If either condition is true, the browser lets the response through to the JavaScript client.

If the server didn't add the CORS headers (or didn't allow that domain), the header is absent → the browser **blocks the response** → a **CORS error** appears in the console and Network tab.

### 6.2 Pre-flighted Request Flow

A pre-flight request is an extra request made **before** the original one, to inquire about the server's capabilities and let the server know what's coming.

**A request is pre-flighted when:**

- It is a **cross-origin** request (client and server domains differ), **AND at least one** of the following is true:
    1. The method is **not** GET, POST or HEAD (e.g. PUT or DELETE)
    2. The request includes **non-simple headers** (anything apart from general/simple request headers — e.g. `Authorization` or custom headers)
    3. The `Content-Type` is something other than `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain` (the "simple" content types)

Since most apps deal with **JSON** (`application/json`), most requests end up being pre-flighted.

**The pre-flight request**

- Uses the **OPTIONS** method, the resource URL and HTTP version.
- Headers include: `Host` (the API), `Origin` (the frontend domain), **`Access-Control-Request-Method`** (asks: "do you support this method, e.g. PUT, for this route?"), and **`Access-Control-Request-Headers`** (asks if particular headers are supported).
- Has **no request body** — just a general inquiry.

**The server's pre-flight response** (if it handles CORS; otherwise the browser blocks the request)

- Status **204 No Content**
- Four important headers:
    1. **`Access-Control-Allow-Origin`** – the client's domain, or `*`
    2. **`Access-Control-Allow-Methods`** – e.g. PUT, DELETE (methods allowed for this route)
    3. **`Access-Control-Allow-Headers`** – e.g. `Authorization`
    4. **`Access-Control-Max-Age`** – tells the browser not to make more pre-flight requests for that period (e.g. 24 hours), since the config stays the same. Saves bandwidth for both server and client.

The browser checks off all of these conditions, then sends the **original request**, and the server responds as usual.

### Demo (using Burp Suite)

- **Burp Suite** is a tool used by ethical hackers; here it's used for HTTP intercepting / visualizing HTTP traffic. No code is shown — the focus is on concepts first (how the underlying mechanism works), and the server language/framework doesn't matter.
- Frontend at `localhost:5173`, API at `localhost:3000` (different ports = different origins → cross-origin).

**Simple request demo**

- Request headers to focus on: `Origin` (frontend origin) and `Host` (the API).
- Response contains `Access-Control-Allow-Origin` with the frontend's origin (or `*`), so the browser lets it through and the front end can render it.
- After **removing** `Access-Control-Allow-Origin` from the server (caching disabled), the browser blocks the response with a **CORS error**, since the header is absent.

**Pre-flight demo**

- CORS re-enabled. First the **OPTIONS** (pre-flight) request went through, then the original request.
- Pre-flight response: **204 No Content** (no request/response bodies), with `Access-Control-Allow-Origin` (frontend domain/port).
- Why it was pre-flighted: the method was **PUT** (not simple), it had an **Authorization** header, and the content type was **application/json** with a JSON body. (Any _one_ of these would have been enough.)
- Server responded with allowed methods (GET, POST, PUT, DELETE) and allowed headers (`Content-Type`, `Authorization`), answering what the client asked in `Access-Control-Request-Method: PUT` and the request headers.
- `Access-Control-Max-Age` was set to **0** for testing purposes (otherwise the pre-flight would be cached and not fired again); `Content-Length` was 0.
- After the successful 204, the browser fired the original PUT request with resource URL, Origin, Authorization header, Host and request body, and got a response body back.

## 7. HTTP Response (Status) Codes

**Why they exist**

- Communicate the **result of a request in a standardized way** — you can tell whether it succeeded or what state the server is in without inspecting the body or guessing from a message structure.
- Help clients **handle errors** with specific codes:
    - `401` → client can log the user out ("log in again")
    - `400` (e.g. invalid form values) → client can ask the user to fix the form and resubmit
- **Standardization** across all web services regardless of platform/language (Python, Go, Rust, JavaScript, Ruby…): success → 200, something created → 201, etc.
- Before status codes, clients had to guess the outcome from response content, causing inconsistency and inefficiency. Status codes provide a universal language.

**Categories** (three-digit numbers, by first digit)

|Range|Meaning|
|---|---|
|1xx|Informational|
|2xx|Success|
|3xx|Redirection|
|4xx|Client errors|
|5xx|Server errors|

### 1xx – Informational (not commonly encountered day-to-day)

- **100 Continue** – server has received the headers and the client can proceed to send the body. Commonly used in large uploads: client sends headers first, and if the server is okay with the request it sends 100 Continue so the client sends the body.
- **Switching Protocols** – server is switching protocols as requested by the client, e.g. upgrading from HTTP to WebSocket.

### 2xx – Success (most used: 200, 201, 204)

- **200 OK** – most common; request successful, server returns the requested resource or performs the action (e.g. successful GET).
- **201 Created** – request fulfilled and resulted in a **new resource** (e.g. POST, new form submissions).
- **204 No Content** – request successful but no content to return. Seen in the CORS pre-flight (info in headers only). Also sometimes used for DELETE (resource deleted, nothing to return).

### 3xx – Redirection (most used: 301, 302, 304)

- **301 Moved Permanently** – resource permanently moved to a new URL; future requests should use the new URL. Example: route `/user` moved to `/person`; add a 301 redirect to keep backwards compatibility for old users/applications.
- **302 Found (temporary redirect)** – resource is temporarily at a different URL; the client should keep using the original URL in future. Example: running a campaign for a couple of hours, redirecting a route to a new one, then reverting.
- **304 Not Modified** – resource hasn't been modified since the client last requested it. Mostly used with **conditional GET requests** for efficient caching (with ETags): the client should use its cached response instead of downloading a new one.

### 4xx – Client Errors (the ones backend engineers deal with most)

- **400 Bad Request** – invalid or illogical data from the client (e.g. expecting a number but got an array/string; expecting an email but got a phone number). Tells the client its request format is wrong: fix it and retry.
- **401 Unauthorized** – authentication is required but the client failed to provide valid credentials or isn't authenticated. E.g. JWT token expired or not sent.
- **403 Forbidden** – server understood the request but refuses to authorize it, **even if the client is authenticated**. E.g. user A tries to delete user B's resource.
- **404 Not Found** – requested resource is unavailable (incorrect URL, or the resource was deleted).
- **405 Method Not Allowed** – invalid HTTP method used (e.g. PUT to a resource that only accepts GET or POST). Often caused by typos, e.g. PATCH instead of PUT, or PUT instead of POST.
- **409 Conflict** – many use cases. Example: folder names must be unique; a POST to create a folder whose name already exists → 409, so the client knows to try a new name.
- **429 Too Many Requests** – used for **rate limiting**. Example: server configured to allow at most 60 requests per client per second; exceeding it returns 429.

### 5xx – Server Errors

- **500 Internal Server Error** – unexpected condition on the server (a process broke, or an exception was not handled). Instead of returning an empty response, breaking or hanging, respond with 500 so the client knows something went wrong on the server.
- **501 Not Implemented** – server doesn't support the requested HTTP method/functionality, but may in the future (e.g. planned to be added soon).
- **502 Bad Gateway** – seen in proxies like Nginx: a server acting as a proxy (load balancer / reverse proxy) got an invalid response from the upstream server. Not returned intentionally; mostly handled by proxies and load balancers.
- **503 Service Unavailable** – service is temporarily unable to handle the request (high traffic or maintenance). Tells the client to try again later.
- **504 Gateway Timeout** – like 502, but specifically the upstream server failed to respond within the timeout period (e.g. Nginx got no response from the origin server running behind it).

> These are pretty much all the response codes needed for ~95% of use cases.

### Demo – Status Codes

A frontend app fires requests to a server that responds with different status codes (each original request preceded by an OPTIONS pre-flight because they're cross-origin). Mock responses observed:

- **200** – successful request
- **201** – created (resource created successfully; POST)
- **400** – bad request, missing required data
- **401** – unauthorized (no token/cookie/other auth, or it's expired/invalid)
- **403** – forbidden, you don't have access
- **404** – not found, requested resource could not be found
- **409** – conflict, resource already exists (e.g. folder with same name)
- **500** – internal server error (message kept generic without giving the client too much info, for security reasons)
- **503** – service unavailable, please try again later

## 8. HTTP Caching

**Definition:** storing copies of responses for reuse, reducing repeated requests to the server. Improves load time, reduces bandwidth and decreases server load — the client doesn't need to download data that hasn't changed; it reuses the old data.

### Important caching headers

- **`Cache-Control`** – e.g. maintain the cache for this resource for a maximum of **10 seconds**.
- **`ETag`** – basically a **hash**. (In the demo a random number is used; normally it's computed from the response, e.g. the server hashes the response and sends that hash.)
- **`Last-Modified`** – the last time the resource was modified; used to decide whether to use the cached resource or request a new one.

### Demo flow

1. **Initial GET** – server responds **200** with the resource plus `Cache-Control`, `ETag`, `Last-Modified`.
2. **Second fetch of the same resource** – client sends **`If-None-Match`** (the ETag) and **`If-Modified-Since`**: "if the ETag doesn't match or the resource has been modified after this time, send the updated resource; otherwise I'll use my cached version." Server checks and responds **304 Not Modified** → client uses its cached version.
3. **Update resource** (a POST was used for the demo; ideally it'd be PATCH/PUT) – server responds 200 and sends a **new ETag** (`3141` → `2943` in the demo).
4. **Next GET** – client sends the **old ETag** (3141) and last-modified; since the resource changed, server responds **200** with the updated resource and the new ETag (2943).
5. **Another fetch** – client sends the new ETag and last-modified; the resource is the latest version, so the server responds **304** again.

### Caveats

- In production it gets complicated: the server must manually implement and manage ETags. If an ETag is accidentally not updated, the client keeps using the cached, **outdated** resource.
- Nowadays there are better solutions, e.g. **React Query** (complete client-side caching), where the client has full power over when to use a cached resource and when to refetch, and at what interval — in the speaker's opinion a much better solution than traditional HTTP-based caching.
- Still good to know HTTP caching exists; if the use case is simple enough, HTTP-based caching can be used.

## 9. Content Negotiation

A mechanism by which client and server **agree on the best format** to exchange data (type, encoding, representation). The client indicates its preferred format (JSON, XML, HTML); the server tries to respond with a compatible format, or a fallback format if unavailable.

### Three types

1. **Media type** – client specifies desired format via `Accept` (e.g. `application/json`, XML).
2. **Language** – client requests content in a specific language via `Accept-Language` (e.g. English, Spanish).
3. **Encoding** – client specifies supported encodings via `Accept-Encoding` (e.g. gzip, deflate); server responds with that compression format.

### Demo

- Default: language **English**, format **JSON**, encoding **gzip**. The request is a GET with `Accept-Language`, `Accept: application/json`, and `Accept-Encoding` (browser supports gzip, deflate, br, zstd). Server responds with English JSON.
- Changed to **Spanish** – only the `Accept-Language` header changed; the server responded in Spanish.
- Changed format to **XML** (with Spanish) – server responded with XML in Spanish.
- **Benefit:** clients let the server know their preferences (data format, language), and the server can respond accordingly, making the client's life easier.

### HTTP Compression (falls under the same umbrella)

- Options include **gzip**, **deflate**, and others.
- Demo: the JSON response was replaced with a very large file of **11,000 entries**.
    - With gzip compression (response header `Content-Encoding: gzip`, because the client said it accepts gzip): size **3.8 MB**.
    - After disabling compression on the server: same file, size **26 MB**.
- **Why it matters:** a huge saving in bandwidth. The server compresses large responses, and the browser decompresses on the client side to get the same response.

## 10. Persistent Connections / Keep-Alive

- **HTTP/1.0:** each request/response cycle needed a separate connection → inefficient, since establishing and closing TCP connections is resource-intensive and slow.
- **HTTP/1.1:** **persistent connections** — a single TCP connection can be reused for multiple requests/responses, avoiding the overhead of opening/closing a connection for each interaction.
- **`Keep-Alive`** is the mechanism that enables persistent connections; client and server reuse the same connection until one of them decides to close it.

**Key points**

- In HTTP/1.1 connections are **persistent by default** (nothing to do explicitly); they stay open unless explicitly closed. Multiple requests/responses go over one connection, reducing latency and saving resources.
- The `Connection: keep-alive` header is still sometimes used to explicitly ask the server to keep the connection open. It can include options like a **timeout** (how long the connection remains open) and **max** (how many requests can be sent before it closes).
- When `Connection: close` is specified, the connection is closed after the response is sent. This is the default behavior in HTTP/1.0, and can still be enforced explicitly in HTTP/1.1.
- Usually you won't work with these directly; default values work fine.

## 11. Handling Large Requests and Responses

### 11.1 Sending large requests – Multipart

- **Multipart requests** are used to send large files (images, videos, audio, etc.) to the server.
- Unlike a typical JSON body, the file's **binary data is transferred in parts** — hence "multipart".
- Demo: a picture is selected and uploaded via a **POST** request with:
    - `Content-Length`
    - `Content-Type: multipart/form-data`
    - **`boundary`** – the **delimiter** that separates the parts. It appears at the start of the binary data and again at its end in the request body.
- The server reads the file and responds with some file details to confirm the upload succeeded.
- **Rule:** to transfer large files to the server, use multipart requests.

### 11.2 Receiving large responses – Chunked / Streaming

- Demo: a large text file on the server is streamed to the client in **chunks**. The request is a normal GET.
- Important response headers:
    - **`Content-Type: text/event-stream`** – not plain text; data is streamed through events
    - **`Connection: keep-alive`** – keeps the connection open until all the data is sent
- The client keeps receiving chunks and appending them, constructing the whole text file. The server keeps sending chunks until the file is completely transferred.

## 12. SSL, TLS and HTTPS (brief)

Not worked with explicitly, but good to know.

- **SSL** – the original protocol for securing communication between a client (e.g. browser) and server. Encrypts data so sensitive info (passwords, credit card numbers) can't be intercepted. Now **outdated due to security vulnerabilities**, replaced by TLS.
- **TLS** – the modern, more secure version of SSL. Encrypts data in transit, protecting it from interception and tampering. Uses **certificates** to authenticate the server and establish an encrypted connection, preventing eavesdropping and data breaches. Continuously updated, with newer versions offering better security (the current recommended version is TLS 1.x — exact version unclear in the transcript).
- **HTTPS** – HTTP with the extra security features provided by SSL/TLS (initially SSL, now TLS). When visiting a website over HTTPS, TLS encrypts communication between browser and server, protecting sensitive data like login credentials from attackers.
