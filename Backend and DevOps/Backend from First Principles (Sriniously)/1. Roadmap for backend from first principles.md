## 1. Introduction / Motivation

- Backend engineering is a very wide scope and much more than building a set of CRUD APIs.
- The speaker's view: backend engineering is about building **reliable, scalable, fault-tolerant, maintainable code bases and efficient systems**.
- Starting today, there are 1,000+ resources, so: how do you decide what to learn, prioritize, and see the big picture of how concepts come together?
- This is why it takes people years to grasp these concepts. People usually start with a limited scope of training (college, bootcamp, a simple course) and build on it with trial and error and help from other developers.
- The speaker is a backend engineer who faced this struggle: constantly searching for resources, learning from other developers, reading many books on backend development, and studying hundreds of open-source code bases to see how the industry builds things. It was very time-consuming.

### The language/framework problem

- People often start backend development from a particular language or framework (Express, Spring Boot, Ruby on Rails) and then view problems through the lens of that language/ecosystem, which creates **blind spots**.
- Example: after years with Ruby on Rails, your company decides to migrate to Golang for performance reasons. How much knowledge can you transfer if you don't understand the underlying systems?

### The goal

- A comprehensive list of videos based on **foundational concepts** of a backend system, drawn from books the speaker has read over the years and from open-source code bases.
- Starts with a very high-level understanding of how backend systems work behind the scenes: how a request from the browser flows through different hops (network, firewalls, over the internet), is routed to a backend server on a remote AWS server, and how it responds, plus what the response looks like. This gives a vivid idea of how a client and a server communicate.
- Scope: "all the concepts we are going to cover in the next 30 or 40 videos."

## 2. Topic Roadmap

### 2.1 HTTP Protocol

- Role of HTTP and how communication is established; what raw HTTP messages look like.
- **HTTP headers** and their role. Types: request headers, representation headers, general headers, security headers.
- **HTTP methods:** GET, POST, PUT, DELETE — when to use them, their semantics and the principles behind them.
- **CORS flow:** how a simple request differs from a pre-flight request, and what a pre-flight flow looks like from browser to server and back.
- **HTTP responses:** structure and different status codes, when to return which, and the most commonly used ones.
- **HTTP caching:** different caching techniques using HTTP (ETags, max-age headers).
- Differences between **HTTP/1.1, HTTP/2.0 and HTTP/3.0**.
- **Content negotiation** between client and server using different headers.
- **Persistent connections** in HTTP.
- **HTTP compression:** gzip, deflate, BR; which is commonly used.
- Security aspect: **SSL, TLS and HTTPS**.

### 2.2 Routing

- How routing maps URLs to server-side logic; the connection between routing and HTTP methods.
- Components of routes: **path parameters** and **query parameters**.
- Route types: static, dynamic, nested, hierarchical, catch-all/wildcard, and regular-expression-based routes.
- **API versioning** using HTTP: different versioning techniques, the best way to deprecate, and industry best practices.
- Benefits of **route grouping** and how it helps with versioning, permissions and shared middleware.
- How to secure routes; how to optimize route-matching performance.

### 2.3 Serialization and Deserialization

- What it means: before sending data over the network, the server translates data into a particular format (serialization); after receiving data from the client, it translates it back into its own native format (deserialization).
- The need for it and how it helps with **interoperability**.
- Formats: **text-based** (JSON, XML) and **binary** (protobuf); performance differences and when to use which.
- How different programming languages implement serialization/deserialization.
- **JSON** deep dive:
    - Structure and data types: strings, numbers, booleans, arrays, objects.
    - How nested objects and collections are handled.
    - Deserializing into native data structures (Python dictionary, Go structs, JavaScript object).
    - Common errors: missing or extra fields, null values, date serialization issues, time zone issues.
    - Implementing custom serialization before sending/serializing data into JSON.
- **Error handling:** invalid data, data conversion errors, unknown fields.
- **Security concerns:** injection attacks; why to validate before deserialization; validating JSON schemas before processing data using JSON Schema validation.
- **Performance:** reducing serialized data through compression and eliminating unnecessary fields; text vs binary (JSON vs protobuf).
- **Trade-off: readability vs performance** — in text-based formats you can easily check the payload, which doesn't work in binary formats, but binary formats are faster. When to use which is a valid trade-off.

### 2.4 Authentication and Authorization

- Why they are used; types of authentication: **stateful, stateless**, basic authentication, bearer token authentication.
- Sessions, JWTs, cookies.
- Deep dive on **OAuth** protocol and **OpenID Connect**.
- How **API keys** work; how **multi-factor authentication** works.
- **Salting, hashing** and other cryptographic techniques used in authorization.
- Authorization models: ACL/RBAC-style models (transcript reads "aack, rback, reback"; transcribed unclearly).
- Security best practices: securing cookies; avoiding **CSRF, XSS, MITM**.
- **Audit logging:** recording authentication/authorization events for audits and monitoring — failed login attempts, privilege escalation, access to sensitive resources.
- **Obfuscating authentication-related error messages:** preventing information leakage to attackers through detailed error messages.
- Edge cases: consistency in responses across different failure modes; rate limiting and account lockout.
- **Avoiding timing attacks:** attackers can exploit time differences in error responses to infer valid credentials. Example: an error for a wrong password might take longer than an error for an invalid username because checking a password requires hashing/a cryptographic technique that takes a little time. People could use that tiny timing difference to guess passwords (very difficult, but no security holes should be left).

### 2.5 Validation and Transformation

**Types of validation**

- **Syntactic** – e.g. is a string an email, a valid phone number, a valid date format.
- **Semantic** – e.g. date of birth can't be in the future; age should be between 1 and 120.
- **Type** – input values match expected types (string, integer, array, object).

**Best practices**

- Client-side vs server-side validation: client-side improves UX with instant feedback; **server-side validation is the true security implementation** because it is the gateway to business logic. Server-side validation matters even when client-side validation exists.
- **Fail fast:** reduce unnecessary processing by returning early.
- Keep **consistency** between frontend and backend validation.

**Transformations**

- **Type casting** – e.g. string → number. Query/path parameters arrive as strings; if an ID is expected as a number, convert it before it reaches handlers (part of the validation pipeline).
- **Date formats** – the frontend may send a different format, or a timestamp may be expected; handled in the validation pipeline.
- **Normalization** – e.g. email to lowercase, trimming whitespace, adding country code to a phone number.
- **Sanitization** – for security, e.g. sanitizing user-submitted strings to prevent attacks like SQL injection.

**Complex validation logic**

- **Relationship validation** – e.g. password and confirm password must match.
- **Conditional validation** – e.g. a partner-name field required only if `married` is true.
- **Chain validation** – e.g. convert to lowercase → remove special characters → check length.

**Error handling in validation**

- Meaningful error messages to the frontend so users can fix them.
- Aggregating all validation errors in one response for client-side display.
- Obfuscating error messages — e.g. "invalid credentials" instead of "invalid password" to prevent attacks.
- Gracefully handling failed transformations (invalid JSON, failed date conversion) with meaningful messages.
- Performance trade-offs of validation; optimizing by returning early and avoiding redundant validations.

### 2.6 Middleware

- What middleware is, when to use it, and common use cases.
- Role in the request cycle: **pre-request** vs **post-response** middleware.
- **Flow:** chaining — middleware executes in sequence, passing control to the next until the request reaches its final handler.
- **Ordering:** log the request → check authentication → validation → route handling → error handling. Order matters.
- How the **`next` function** works; **exiting middleware early** (short-circuiting the request pipeline), e.g. handling 404 errors.
- **Common middlewares:**
    - Security: adding security headers (X-Content-Type, Strict-Transport-Security, Content-Security-Policy), CORS headers on every request/response, CSRF protection, rate limiting.
    - Authentication: reuse route-protecting logic across the app.
    - Logging and monitoring: request logging, structured logging for observability/easier production debugging.
    - Error handling: catches and formats application-level errors for consistent API responses.
    - Compression/performance: compress response bodies to reduce data sent over the network.
    - Data parsing: parsing request bodies (JSON, URL-encoded forms, file uploads; handles multipart data for uploads).
- **Performance and scalability:** keep middlewares lightweight and efficient; apply in the correct order; middleware order can affect performance and security.

### 2.7 Request Context

- Metadata passed through middlewares, controllers and services — a **request-scoped state**, valid only for that request.
- Topics: life cycle of a request; maintaining state for the duration of a request; sharing data across layers without coupling; how context provides temporary request-scoped state.
- **Components of request context:**
    - Request metadata: HTTP method, URL, headers, query parameters, body.
    - Session and user information (e.g. the authentication middleware fetches user info and injects it into the context for that request).
    - Tracking/logging information: unique request IDs or trace IDs.
    - Request-specific data: custom data injected during the life cycle (e.g. caching data, permission checks).
- **Use cases:** authentication, rate limiting, tracing, logging.
- Connection between middlewares and request context.
- Timeouts: request timeouts, custom timeouts, cancellation signals.
- **Best practices:** keep it lightweight (prevent memory overhead); clean up context data after the request life cycle (prevent memory leaks); avoid tightly coupling components through context or over-relying on it for passing data.

### 2.8 Handlers and Controllers

- The **MVC pattern**; responsibilities of handlers, controllers and services; reducing code with middleware.
- Centralized error handling in handlers; consistent success/error message formats and how to implement them in controllers.
- **CRUD operations** and how they map to HTTP methods, with common APIs per method:
    - POST – creation/submissions; status usually **201 Created**, or **400** if bad request.
    - GET – fetching a list of resources or a single resource.
    - PUT and PATCH – update resources.
    - DELETE – delete resources.
- How to implement **pagination**, **search API**, **sorting**, **filtering**.
- Best practices: strict validation, consistent response formatting, limiting payload, redacting sensitive fields, error handling, authentication and authorization.

### 2.9 RESTful Architecture

- Designing APIs around **resources**; sticking to HTTP semantics; best practices for filtering and pagination.
- Versioning types: **URI versioning, header versioning, query string, media type**.
- Designing APIs with the **OpenAPI spec** in mind.
- Content negotiation; capturing exceptions and providing meaningful messages; supporting client-side caching (ETags); optimizing large requests and responses.

### 2.10 Databases

- Basic querying and joins.

### 2.11 Business Logic Layer (BLL)

- Role of the BLL and the layers of a request cycle:
    - **Presentation layer** – validation layer, routing, middlewares, handlers and controllers (they deal with user data, accepting or sending it).
    - **Business logic layer** – the middle layer; deals with core business logic.
    - **Data access layer** – deals with databases (queries, inserts, deletions). The BLL uses the data access layer behind the scenes.
- Design principles: **separation of concerns, single responsibility, open/closed, dependency inversion**.
- Components of the BLL: **services**; **domain models** (core entities such as a user or an order); business rules (transcribed as "business tools"); business validation logic.
- Service layer design best practices; handling errors properly and propagating them from the service layer to the presentation layer.

### 2.12 Caching

- Need for caching and how it differs from database persistence.
- Types: **memory caching, browser caching, database caching**; client-side vs server-side caching.
- Strategies: **cache-aside, write-through, write-behind/write-back, read-through** (as transcribed: "right through, right behind or right back").
- Eviction strategies: **LRU, LFU, TTL, FIFO**.
- Cache invalidation: manual, Time-To-Live, event-based.
- Levels: **Level 1** (in-memory), **Level 2** (network/distributed), and **hierarchical caching** combining both — frequently used data in a fast, small L1 cache; less frequently used data in a slower, larger L2 cache.
- Caching for web apps: static assets; API responses using headers.
- Caching with databases: query caching (e.g. storing results of heavy joins in Redis).
- Cache hit and miss ratio, and how to optimize them.

### 2.14 Task Queuing and Scheduling

- **Common use cases for queuing:** sending emails, processing image files, third-party API integration (payment processing, webhooks), offloading heavy computation like batch processing.
    - Example: a user clicks "clear all my data" → clearing requires queries on different tables and may take time → return the response instantly and trigger a background job by pushing it into the task queue instead of blocking the request.
- **Scheduling use cases:** database backups, recurring notifications and reminders, data synchronization, maintenance (clearing logs or caches).
- **Components of a task queue:** producer, queue, consumer, broker, backend.
- Task dependencies: chain dependency or parent-child relationship.
- Task groups: executing multiple tasks concurrently and waiting for all to complete.
- Error handling and implementing **retries**.
- **Task prioritization** and **rate limiting** (e.g. payment processing before sending notifications).

### 2.21 Scaling and Performance

- Performance metrics: response time, resource utilization; identifying bottlenecks.
- Caching and database optimization: avoiding **N+1 query** problems, proper use of joins, lazy loading where appropriate.
- Database indexes to speed up reads on frequently queried fields (indexing foreign keys or search fields).
- Processing data in **batches** to minimize database load for large data sets.
- Avoiding memory leaks (closing file handles, database connections, cleaning up after long processes).
- Minimizing network overhead via smaller payloads and compression.
- Performance testing and profiling.
- Best practices: write clear, maintainable code first without premature optimization; write modular code so individual components can be optimized without affecting the system; degrade gracefully (no crashing) when resources under load are unavailable; offload non-critical tasks (emails, logging) to background processes or task queues to free resources for critical operations.
