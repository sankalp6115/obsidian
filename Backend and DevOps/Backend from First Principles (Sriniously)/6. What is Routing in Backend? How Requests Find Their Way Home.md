## 1. What Routing Is

- The previous video covered **HTTP methods**, which describe your **intent** — they express the **"what"** of a request: your action on a resource (fetch, add, update or delete data).
- **Routing** expresses the **"where"** of a request: *where* or on *which resource* you want to perform that action. You need to tell the server where you want to go.
- **Example:** method **GET** (intent: fetch data) + route path **`/users`** → the server sends back an array of users. "I want to fetch some data" (action) + "from where / what kind of data" (the resource/route).
- The server takes the combination of **intent (method) + route (URL path)** and **maps it to a particular handler** (a set of instructions), which performs the business logic, database operations and whatever else is needed, then returns the data.

> **Summary:** Routing is basically **mapping URL parameters to server-side logic**.

## 2. Basic Routing: Method + Route = Unique Key

- **Demo request 1:** `GET /api/books`
  - `GET` is the intent/action. `/api/books` is the **route** — the address in the server. `books` is called a **resource** (to be covered later in REST API concepts; for now, treat it as a route).
  - Typical flow: you send a request, the server does authentication if there is any, then sends the data. (In the demo, filler data is returned.)
- **Demo request 2:** `POST /api/books` — same route, different method. It creates another book (or whatever the resource is) and returns the resources again.
- **Key point:** the **method and the route together act like a key that maps to a particular handler**. The server first checks the method, then the route, and concatenates the two to form a **unique routing path**.
  - `GET /api/books` and `POST /api/books` are two unique paths that **never clash** — the methods differentiate them.

## 3. Types of Routes

### 3.1 Static Routes
- Examples: `GET /api/books` and `POST /api/books`.
- Called **static** because they have **no variable parameters** inside the route. `/api/books` is a constant string, used the same way every time, and always returns the same kind of data.

### 3.2 Dynamic Routes
- Example: `GET /api/users/123` — here `123` is the **ID of the user**. The API lets you fetch details of one particular user using the ID in the route.
- The server **extracts the ID from the route path** and can do whatever it needs (e.g. fetch the user from the database and return details). In the demo the server just returns the extracted user ID to show it got it from the route.
- **How route matching looks in a server** (conceptually, not tied to a language): a handler like `R.get("/api/users/:id")`
  - The `get` part matches the **method**; the string part matches the **route**.
  - `:id` — the **colon** marks a **dynamic parameter**: any string in that position matches and is routed to this handler.
  - This colon convention is found in servers in any language (Java, Python, Node.js, Go, Rust) — the speaker calls it an industry-wide practice.
- For `GET /api/users/123`: it matches `get`, then `/api`, then `/users`, and `123` goes into the dynamic `id` slot.
  - **Route parameters are always strings** — numbers, special characters, everything is converted to a string, even if it looks like a number.
- **Readability:** `GET /api/users/123` reads as "fetch me the data of the user with ID 123". This is the whole idea of **REST APIs**: a **human-readable construct** for routing.
- This part is called a **route parameter** or **path parameter** — it goes right after the forward slash and is part of the route.

### 3.3 Query Parameters (the second type of parameter)
- Example: `/api/search?query=some+value`
  - The **route** is `/api/search` — this is what the server uses (with the method) to match a handler.
  - The part after `?` — a **key and value** — is called a **query parameter**.

**Why query parameters?**
- POST and PUT requests have a **body** to carry user-defined values. In REST APIs, **GET requests don't have a body**, so how do you send values?
- You could use path parameters, but they serve a **semantic purpose**: `/api/users/123` semantically means "fetch the user whose ID is 123".
- Sending a search value as a path parameter (`/api/search/some value`) is technically possible but **hard to maintain and defeats the purpose of REST** (providing semantic expressions in API endpoints).
- So we have **query parameters**: a set of **key-value pairs** sent to the server, typically with GET requests, to carry **metadata about the request**.

**Example: pagination**
- Endpoint `GET /api/books` returns JSON with `data` (an array of books) plus **metadata**: `total`, `current page`, `total pages` (and a `limit`). The exact shape depends on the implementation.
- The server paginates the response and sends a chunk. Suppose a default limit of 20: it sends 20 books from the start and reports the total (say 100), the current page (page 1) and total pages (100 ÷ 20 = 5).
- The client uses this metadata to make subsequent requests. By default the server sends page 1 (no query params needed). To get page 2: `GET /api/books?page=2`.
- Other typical uses: **filtering** by a user-defined parameter, **sorting** (ascending or descending). All go in query parameters as key-value pairs.

### 3.4 Nested Routes
- Not really a "type of routing" — it's a **practice** seen everywhere. In REST APIs, for semantic expression, we often **nest different resources**.
- **Example:** `GET /api/users/123/posts/456`
  - `/api/users` — the **static part**
  - `123` — first dynamic (path) parameter
  - `456` — second dynamic (path) parameter
- Each level is a **different route** matching a **different handler**, with a different meaning:
  | Route | Meaning |
  |---|---|
  | `/api/users` | Returns the list of all users |
  | `/api/users/123` | Details of the user with ID 123 |
  | `/api/users/123/posts` | All posts of the user with ID 123 |
  | `/api/users/123/posts/456` | A particular post (ID 456) of the user with ID 123 |
- Nested because different kinds of information are nested at different levels to express different semantic meanings, resulting in different responses.
- Very convenient, and used almost everywhere if the API has even a medium level of complexity.

## 4. Route Versioning and Deprecation

- **Demo:** `GET /api/v1/products` and `GET /api/v2/products`.
- Route versioning is a very common practice in REST API servers.
- **Example responses:**
  - v1 → `data` array of objects with `id`, `name`, `price`
  - v2 → `data` array of objects with `id`, `title`, `price`
  - (A trivial example; the point is that the response format differs between versions.)

**Why use versioning?**
- Say you return data in a particular format, and new requirements come in — e.g. you were serving a web app, and later you serve a React Native, Android or Flutter app, so the response needs to change.
- **Option 1:** change the whole route (e.g. `/api/new-products`).
- **Option 2 (versioning):** v1 serves the old format, v2 the new one.
  1. It **expresses your intention very clearly** (version 1 response vs version 2 response).
  2. You **don't have to change the whole route** (no `/api/new-products`).
  3. You can eventually **deprecate v1**: tell frontend engineers that after v2 is released v1 is deprecated, giving them a **window to migrate** their requests to the v2 format. Eventually v1 is removed completely. (The speaker also says "make the V2 to V1" — meaning unclear in the transcript.)
- Result: a **stable and complete workflow** for adding new structure and **breaking changes** to API endpoints, while clients have time to migrate.

## 5. Catch-All Routes

- **Demo:** sending a request to `/api/v3/products` — a route the server doesn't serve; it has no handler for it.
- Typically, **after all the other routes and their methods**, the server defines a final route: **`/*`** (slash star).
  - Any request that reaches it after going through all previous route-matching is mapped to a handler that sends a **user-friendly message**: this route doesn't exist / not found.
  - Without catch-all handling, the default behavior is just sending a null response; the catch-all lets the client know the server doesn't cater to that endpoint.
